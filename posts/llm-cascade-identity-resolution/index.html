Hightouch가 고객 데이터 신원 확인(identity resolution) 품질을 LLM으로 채점하는 실험을 공개했습니다. 싸고 빠른 판정 모델이 먼저 보고, 확신이 애매한 건만 Claude Opus에 넘기는 '계단식' 구성으로 Opus 단독과 비슷한 정확도를 훨씬 싸게 냈어요. 숫자와 함께 한계, 우리 파이프라인에 적용할 때 볼 점을 정리합니다.

2026년 11월 4일, 고객 데이터 플랫폼 회사 Hightouch의 블로그에 LLM으로 신원 확인 결과를 채점하는 실험 글이 올라왔습니다. 핵심은 이렇습니다. 아주 싸고 빠른 판정 모델이 모든 건을 먼저 보고, “확신이 애매하다"고 답한 건만 비싼 최상위 모델(Claude Opus 5.5)에 다시 물어봤더니, 쉬운 데이터에서 Opus 단독과 거의 같은 정확도(98.8% 대 99.0%)를 약 4.4배 싼 비용으로 냈다는 거예요.

해커뉴스에서도 화제가 됐습니다. 신원 확인이라는 특정 업무 이야기지만, 실제로 쓸모 있는 교훈은 더 넓습니다. “모든 요청을 가장 좋은 모델에 보낼 필요는 없고, 싼 모델이 자기 불확실성을 정직하게 말해 주기만 하면 된다” 는 것이죠. LLM 비용이 고민인 데이터·백엔드 개발자라면 한 번 볼 만한 실험입니다.

방법LLM에게 한 사람으로 묶인 기록 묶음을 보여 주고 “정말 한 사람인가?“를 판정하게 함
비교한 모델Claude Opus 5.5, Gemini 3.1 Pro, GPT-6 Sol(최상위급) / GPT-6 Luna, Jev(저가 판정 모델)

결론저가 모델 + 애매한 건만 Opus로 넘기는 구성이 Opus 단독 정확도에 근접하거나 같음

먼저 용어 몇 가지

  • 신원 확인(identity resolution, IDR): 회원가입·구매·배송지처럼 흩어진 기록을 보고 “이 기록들이 같은 사람인가"를 판단해 한 사람당 하나의 프로필로 묶는 작업입니다.
  • 과병합(over-merge): 다른 사람의 기록이 한 프로필로 잘못 합쳐진 상태예요. 쌍둥이, 같은 이름의 부자(父子), 같은 이메일을 쓰는 가족 등에서 잘 생깁니다. 마케팅 메시지가 엉뚱한 사람에게 가는 식의 사고로 이어집니다.
  • LLM 판정(LLM-as-a-judge): 사람 대신 LLM이 결과물의 품질을 채점하게 하는 방식입니다.
  • 판정 모델(decision model): 이 글에서는 긴 답변 대신 “조건이 참일 확률"을 0~1 사이 숫자로만 돌려주는 싸고 빠른 모델을 말합니다. Jev와 GPT-6 Luna가 여기에 해당해요.
  • 보정(calibration): 모델이 말하는 확신도가 실제 정답률과 맞는 정도입니다. “90% 확신"이라고 한 답이 실제로 열에 아홉 맞으면 보정이 잘된 모델이에요.
  • 계단식 구성(cascade): 싼 모델이 먼저 처리하고, 필요한 경우에만 비싼 모델로 넘기는(에스컬레이션) 구조입니다.

왜 LLM으로 채점하려 했나

신원 확인은 정답지가 없다는 게 가장 큰 문제입니다. 그래서 보통은 프로필 일부를 뽑아 사람이 직접 들여다보는데, 글에 따르면 한 시간에 50건 정도가 한계라고 해요. 과병합처럼 드문 오류의 비율을 ±1% 범위로 추정하려면 1,000건 넘게 봐야 하니, 사람 손으로는 자주 점검하기 어렵습니다. LLM이 이 채점을 대신할 수 있다면 10만 건 표본도 금방 볼 수 있죠.

프롬프트에서 효과가 컸던 건 하나였습니다. 흔한 입력 실수 목록(오타, 이사로 바뀐 주소, 별명 등)을 예시로 넣는 것이에요. 이게 없으면 모델이 오타 하나에도 “다른 사람"이라고 판단하기 쉬웠고, 모든 모델에서 이 예시가 가장 크게 도움이 됐다고 합니다.

계단식 구성 결과

구성세트정확도1,000건당 비용Opus 단독 대비
Jev → (30~90%면) Opus쉬운 세트98.8%$0.88약 4.4배 저렴, 22%만 Opus로
Luna → (10~90%면) Opus쉬운 세트98.5%$0.336%만 Opus로
Opus 단독어려운 세트95.1%$5.39—
Jev → (30~90%면) Opus어려운 세트95.3%$2.94약 1.8배 저렴

규칙은 단순합니다. 저가 모델이 “한 사람일 확률"을 30~90% 사이로 답하면, 즉 스스로 애매하다고 하면 Opus에게 다시 묻고, 그 밖이면 저가 모델 답을 그대로 씁니다. 아래는 이 흐름을 설명하려고 쓴 의사 코드예요(실제 API 호출은 빠져 있습니다).

LOW, HIGH = 0.30, 0.90  # 이 구간이면 "애매함"으로 보고 넘긴다

def judge(profile, cheap_model, strong_model):
    p = cheap_model(profile)          # 0~1: 한 사람일 확률
    if LOW <= p <= HIGH:
        return strong_model(profile)  # 애매한 건만 비싼 모델로
    return p > HIGH                   # 90% 초과면 한 사람, 30% 미만이면 다른 사람

진짜 교훈: 단독 성능보다 ‘보정’

흥미로운 건 Luna와 Jev의 역전입니다. 쉬운 세트에선 Luna 단독이 Jev보다 정확했어요. 그런데 어려운 세트에서 계단식으로 묶자 Jev 쪽이 95.3%로 Opus를 따라잡은 반면, Luna 쪽은 91.6%에 그쳤습니다.

이유는 보정입니다. Jev는 틀린 답이 대부분 확신도 50% 근처에 몰려 있었어요. “모르겠다"고 할 때 실제로 틀리는 경우가 많으니, 그 구간만 Opus에 넘기면 오답이 잘 걸러집니다. 반면 Luna는 90~100% 확신으로 틀리는 경우가 많았습니다. 자신만만하게 틀린 답은 애초에 Opus로 넘어가지 않으니 고칠 기회가 없죠. 계단식 구성에선 “얼마나 맞히냐"보다 “틀릴 때 티를 내냐” 가 더 중요하다는 얘기입니다.

한계와 주의할 점

  • “4배"는 쉬운 세트 기준입니다. 어려운 세트에선 비용 절감이 약 1.8배였고, 속도도 1.56초 대 2.6초로 차이가 크지 않았어요. 어려운 세트에서 몇 %가 Opus로 넘어갔는지는 공개되지 않았습니다.
  • 합성 데이터입니다. 가상 도시 데이터라 실제 고객 데이터의 오류 패턴과 다를 수 있다고 저자들도 밝혔습니다.
  • 표본이 작습니다. 1,000건 규모라 모델 간 차이가 몇 건에 불과한 경우가 많아요.
  • 문턱값을 같은 데이터로 골랐습니다. 60%·70% 기준과 넘기는 구간을 평가 데이터에서 튜닝했기 때문에 성능이 실제보다 좋게 보였을 가능성이 있습니다.
  • 과병합만 봤습니다. 같은 사람이 여러 프로필로 쪼개지는 반대 방향 오류(과소병합)는 다루지 않았어요.
  • 이해관계가 있는 회사의 글입니다. Hightouch는 신원 확인 제품을 파는 회사이고, 비용·속도는 그들 환경 기준입니다.

독자가 할 일

  1. 우리 LLM 호출 중 “판정형” 작업을 찾아보세요. 분류, 중복 판단, 품질 채점처럼 예/아니오로 끝나는 일이라면 계단식 구성 후보입니다.
  2. 저가 모델의 확신도와 실제 정답률을 함께 기록하세요. 사람이 라벨을 단 수백 건만 있어도 확신도 구간별 정답률을 그려 볼 수 있어요. 높은 확신에서 자주 틀린다면 계단식 구성에 맞지 않는 모델입니다.
  3. 문턱값은 평가용과 튜닝용 데이터를 나눠서 정하세요. 이 실험의 약점을 그대로 따라 하지 않는 방법입니다.
  4. 에스컬레이션 비율을 지표로 두세요. 비싼 모델로 넘어가는 비율이 갑자기 오르면 데이터가 어려워졌거나 저가 모델이 흔들린다는 신호입니다.
  5. 프롬프트에 “흔한 실수 예시"를 넣어 보세요. 이 실험에서 모든 모델에 가장 크게 효과가 있었던 부분이에요.

정리

  • Hightouch는 신원 확인 품질을 LLM으로 채점하면서, 싼 판정 모델이 먼저 보고 애매한 건만 Claude Opus에 넘기는 구성을 시험했습니다.
  • 쉬운 세트에선 22%만 넘기고 정확도 98.8%(Opus 단독 99.0%)를 약 4.4배 싸게, 어려운 세트에선 Opus보다 조금 높은 정확도를 약 1.8배 싸게 냈습니다.
  • 계단식 구성의 성패는 저가 모델의 단독 정확도보다 보정, 즉 틀릴 때 확신도가 낮게 나오는지에 달려 있었습니다.
  • 합성 데이터·작은 표본·같은 데이터로 튜닝한 문턱값이라는 한계가 있으니, 우리 데이터로 직접 확인하는 게 먼저입니다.
