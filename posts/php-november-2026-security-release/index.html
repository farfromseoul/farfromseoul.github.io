PHP 프로젝트가 2026년 11월 19일(UTC) 지원 중인 모든 버전에 보안 업데이트를 내놨습니다. 하루 전 “치명적(critical) 등급이 포함된 보안 릴리스가 나온다"고 미리 예고한 뒤 나온 묶음이라, 워드프레스·라라벨처럼 PHP 위에서 도는 서비스를 운영한다면 이번 주 안에 확인해야 할 업데이트입니다.

수정 버전은 8.2.36 · 8.3.37 · 8.4.28 · 8.5.13 이고, 같은 날 나온 8.6.0에도 수정이 들어 있습니다.

php.net 공식 공지와 GitHub 보안 권고 페이지는 이 환경에서 직접 열리지 않아, The Hacker News·Wiz·Semgrep의 릴리스 후 분석과 Aikido·Security Affairs의 사전 공지 보도를 교차 확인해 썼습니다. 한 곳에만 나온 수치는 넣지 않았습니다. (2026-11-20 확인 기준)

무슨 일이 있었나

  • 11월 18일: PHP가 “모든 지원 버전에 영향을 주는 보안 릴리스를 19일에 낸다"고 사전 공지했습니다. 이때 미리 공개된 건 세션 관련 CVE-2026-115560 하나였고, PHP는 “기본값이 아닌 설정이나 흔치 않은 구성에서만 문제가 된다"고 설명했습니다.
  • 11월 19일 14시(UTC)쯤: 수정 버전이 나왔습니다. Wiz와 Semgrep 분석 기준으로 PHP 자체 CVE는 17개, 그중 7개가 CVSS 9.2(치명적) 입니다. (Semgrep은 PHP에 묶여 들어가는 uriparser 라이브러리 취약점 1건을 더해 18건으로 셉니다.)
  • 보도 시점까지 실제 공격에 쓰였다는 보고는 확인하지 못했습니다. 다만 한 달 전 고쳐진 PHP 세션 취약점(PHP2Shell)은 패치 뒤 실제 악용 사례가 나왔기 때문에, “아직 공격이 없다"를 미룰 이유로 삼기는 어렵습니다.

용어한 줄 풀이
CVSS취약점 심각도를 0~10점으로 매기는 국제 기준. 9.0 이상이 ‘치명적’입니다. 이번 PHP 점수는 v4 기준입니다.
PHP-FPM웹 서버(nginx·Apache) 뒤에서 PHP 코드를 실행하는 별도 프로세스 묶음. 요즘 PHP 서버 대부분이 이 구조입니다.
FastCGI웹 서버와 PHP-FPM이 요청을 주고받는 통신 규약.
연결 재사용(keep-alive)요청마다 연결을 새로 만들지 않고 한 연결로 여러 요청을 보내는 방식. 빠르지만, 요청 경계가 어긋나면 남의 요청에 내 데이터가 섞일 수 있습니다.
요청 스머글링서버 두 대가 “요청이 어디서 끝나는지"를 다르게 해석하는 틈을 이용해 몰래 요청을 끼워 넣는 공격.
use-after-free(UAF)이미 반납한 메모리를 다시 쓰는 버그. 메모리를 조작해 코드 실행으로 이어질 수 있습니다.
세션 직렬화 핸들러$_SESSION 내용을 파일·저장소에 쓸 때 쓰는 변환 형식(php, php_binary, php_serialize). 읽을 때와 쓸 때 형식이 다르면 데이터가 엉뚱하게 해석됩니다.
업로드 진행률(upload progress)파일 업로드 진행 상황을 세션에 기록하는 PHP 기능. 기본값으로 켜져 있습니다.

이 밖에 높음(High) 등급 4건(FPM 워커→마스터 권한 상승, 접힌 헤더 처리 서비스 거부, HTTPS/FTPS 대소문자 처리로 평문 전송, Phar 서명 다운그레이드)과 중간 등급 6건(SOAP·DOM·URI·php-cgi·FPM 상태 페이지 등)이 함께 고쳐졌습니다.

눈여겨볼 점 두 가지

  1. 세션 쪽이 또 문제입니다. 지난달 PHP2Shell도 세션 처리였고, 이번 7건 중 3건이 세션과 얽혀 있으며 그중 하나는 지난달 수정이 불완전했던 부분입니다. 세션을 많이 쓰는 로그인·장바구니 기능이 있는 서비스라면 우선순위를 높이세요.
  2. 성능 튜닝 설정이 공격 조건이 됩니다. CVE-2026-129289는 PHP 기본 설정이 아니라 웹 서버 쪽 연결 재사용 설정에 달려 있습니다. 기본 nginx·Apache 설정은 요청마다 FPM 연결을 닫기 때문에 분석에서 시연된 경로에는 해당하지 않지만, 성능을 위해 keep-alive를 켜 둔 곳이라면 해당될 수 있습니다.

한계와 주의할 점

  • “비기본 설정에서만"이라는 말을 너무 믿지 마세요. 업로드 진행률은 기본으로 켜져 있고, 연결 재사용은 성능 가이드에서 흔히 권하는 설정입니다. 내 서버가 기본값인지 직접 확인하는 게 먼저입니다.
  • 취약점 수 집계가 출처마다 다릅니다. 17건(PHP 자체 CVE)과 18건(번들 라이브러리 포함)이 섞여 보도되고 있습니다. 숫자보다 “내 버전이 수정 버전 이상인가"가 중요합니다.
  • PHP 8.1 이하는 지원이 끝난 버전입니다. 이번 수정 대상에 없으니, 배포판이 따로 패치를 내주지 않는 한 업그레이드 말고는 답이 없습니다.
  • 배포판 패키지는 버전 숫자가 다를 수 있습니다. Ubuntu·Debian·RHEL 계열은 상위 버전 번호를 그대로 따르지 않고 자체 패치 번호를 붙이기도 합니다. 배포판 보안 공지에서 위 CVE 번호로 확인하세요.

지금 할 일

1. 버전 확인

php -v

CLI와 FPM이 다른 PHP를 쓰는 서버도 있으니, FPM 쪽은 phpinfo() 결과나 패키지 관리자에서 따로 확인하세요.

2. 수정 버전으로 올리고 PHP-FPM을 재시작

  • 8.2 → 8.2.36, 8.3 → 8.3.37, 8.4 → 8.4.28, 8.5 → 8.5.13 (또는 8.6.0)
  • 컨테이너라면 베이스 이미지 태그를 새 버전으로 올려 다시 빌드·배포해야 합니다. 이미지 안의 PHP는 호스트 업데이트로 바뀌지 않습니다.
  • 업데이트 후 FPM 워커가 모두 새 바이너리로 다시 떠야 적용됩니다.

3. 당장 못 올린다면 임시 조치 (여러 분석이 공통으로 권한 내용)

  • 세션 업로드 진행률 끄기: php.ini(또는 FPM 풀 설정)에 session.upload_progress.enabled = 0. 코드의 ini_set()이나 .user.ini로는 효과가 없으니 서버 설정에서 바꾸고 워커를 재시작해야 합니다. 업로드 진행률 표시 기능을 쓰는 앱이라면 그 기능이 멈춥니다.
  • FastCGI 연결 재사용 끄기: nginx는 fastcgi_keep_conn off;, Apache mod_proxy_fcgi는 enablereuse=off. 성능이 조금 떨어질 수 있으니 업데이트 후 원래대로 돌릴지 판단하세요.
  • PHP 8.5를 쓴다면 zend.exception_ignore_args가 On(1)인지 확인하세요. 운영 환경 권장값이기도 합니다.

4. 코드 점검(여유가 있다면)

  • ini_set('session.serialize_handler', ...)처럼 코드에서 세션 직렬화 형식을 바꾸는 곳이 있는지 검색해 보세요. 있다면 서버 설정과 형식을 하나로 맞추는 편이 안전합니다.

정리

  • PHP 지원 버전 전부에 치명적 7건을 포함한 보안 수정이 나왔고, 수정 버전은 8.2.36 · 8.3.37 · 8.4.28 · 8.5.13 · 8.6.0 입니다.
  • 핵심은 세션 처리와 PHP-FPM 연결 재사용입니다. 기본값으로 켜진 업로드 진행률, 성능용 keep-alive 설정이 조건이 될 수 있습니다.
  • 업데이트 후 FPM 재시작까지 해야 끝나고, 당장 못 올리면 업로드 진행률·FastCGI 연결 재사용을 꺼 두세요.
