GitHub가 Git 저장소 구조를 새로 짰다: 한 레포에 초당 7,200번 푸시를 버틴 'Rubicon'

AI 에이전트 수천 개가 한 레포에 동시에 푸시하는 시대를 대비해 GitHub가 새 Git 저장 구조 'Project Rubicon'을 공개했습니다. 내부 테스트에서 에이전트 5,000개, 초당 7,200번 푸시를 처리했어요. 핵심 아이디어인 '참조만 합의하기'와 우리 팀이 지금 챙길 점을 정리합니다.

2026년 11월 5일, GitHub 엔지니어링 블로그에 새 Git 저장 구조(코드명 Project Rubicon) 를 설명하는 글이 올라왔습니다. 내부 테스트에서 에이전트 5,000개가 한 레포에서 동시에 작업하고, 한 레포에 초당 7,200번 푸시를 보내는 동안에도 읽기 지연이 낮게 유지됐다고 해요. 지금 GitHub.com에서 가장 바쁜 레포도 쓰기는 초당 많아야 수십 번 수준이라고 하니, 100배 넘게 끌어올린 셈입니다.

해커뉴스에서도 화제가 됐는데, 관심이 몰린 이유는 숫자보다 배경입니다. 사람이 아니라 AI 코딩 에이전트가 하루 종일 브랜치를 만들고 푸시하는 상황이 현실이 되면서, Git 서버의 병목이 바뀌고 있다는 거예요. 이 글에서는 Rubicon이 어떤 문제를 풀었는지, 그 바탕에 깔린 설계 아이디어는 무엇인지, 그리고 에이전트를 쓰는 팀이 지금 챙길 점을 정리합니다.

무슨 일이 있었나

항목내용
발표GitHub 엔지니어링 블로그, 2026-11-05 (Karthik Raman, Brian Celenza)
이름Project Rubicon — 2026년 5월, Azure 이전 직후 착수
목표레포 하나가 감당하는 규모를 최소 100배(두 자릿수 배) 키우기
내부 테스트 결과동시 에이전트 5,000개, 레포 하나에 초당 7,200번 푸시, 읽기 지연은 낮게 유지
참조 저장 서비스초당 수만 건의 참조 트랜잭션 처리
공개 상태제한된 비공개 프리뷰, 더 넓은 배포는 “내년 초” 예정
사용자 영향푸시·페치·브랜치 방식과 보호 규칙은 그대로라고 설명

GitHub가 든 예시도 흥미롭습니다. 어떤 레포 하나는 하루 요청 수가 3월 평균 약 4,400만 건에서 5월 평균 약 1억 8,100만 건으로 두 달 만에 4배 가까이 늘었다고 해요. 푸시 한 번이 CI 실행, 배포용 풀, 다른 에이전트의 페치를 줄줄이 부르기 때문에 쓰기가 늘면 읽기는 훨씬 더 늘어납니다. GitHub는 지금은 순간적으로 몰리는 쓰기가 1년 안에 “계속되는 부하"가 될 거라고 내다봤습니다.

먼저 용어 몇 가지

  • Git 객체(object): 커밋·파일 내용·폴더 구조를 담은 데이터 조각. 내용으로 계산한 해시가 곧 이름이라서(콘텐츠 주소 방식), 한 번 만들어지면 바뀌지 않습니다.
  • 참조(reference, ref): main, feature/login 같은 브랜치·태그 이름이 “지금 어느 커밋을 가리키는지” 적어 둔 포인터. 푸시는 결국 객체를 올리고 참조를 옮기는 일입니다.
  • 팩 파일(packfile): 여러 객체를 압축해 한 파일로 묶은 것. 푸시할 때 오가는 데이터 단위예요.
  • 레플리카(replica): 같은 데이터를 여러 서버에 복제해 둔 사본. 한 대가 죽어도 서비스가 이어지게 합니다.
  • CAS(Compare-And-Swap): “값이 내가 알던 그대로일 때만 새 값으로 바꾼다"는 연산. 두 사람이 동시에 고쳐도 한 명만 성공하고 나머지는 다시 시도하게 만들어 충돌을 막습니다.
  • 합의(consensus)·과반 기록: 여러 서버가 “이 변경을 확정한다"고 맞추는 과정. 과반이 기록하면 확정으로 봅니다.
  • 컴팩션(compaction): 잘게 쌓인 팩 파일을 큰 파일로 합쳐 정리하는 작업. 안 하면 파일 수가 늘어 읽기가 느려집니다.

핵심 아이디어: 합의가 필요한 건 ‘참조’뿐이다

Rubicon의 출발점은 단순한 관찰입니다. Git 객체는 내용이 곧 이름이고 바뀌지 않으니, 여러 서버가 동시에 저장해도 서로 부딪힐 일이 없다. 같은 내용이면 같은 이름이 나오고, 다른 내용이면 다른 이름이 나오니까요. 정말로 순서를 맞춰야 하는 건 “main이 이제 어느 커밋을 가리키나” 같은 작은 참조 변경뿐입니다.

그래서 데이터를 두 갈래로 나눴습니다.

구성 요소하는 일
Azure Blob Storage팩 파일, 인덱스, 읽기 가속용 데이터(멀티팩 인덱스·도달성 비트맵), 캐시된 페치 응답 등 큰 데이터 보관
Ref-CAS참조와 “어떤 팩 파일이 있는지” 목록(매니페스트)만 담는 복제 로그 서비스. 객체 데이터는 절대 넣지 않음
가상 레플리카읽기·쓰기를 처리하는 일회용 서버 묶음. 로컬 디스크는 언제든 다시 채울 수 있는 캐시일 뿐
컴팩션 노드팩 파일 정리를 서비스 서버와 떼어 뒤에서 따로 실행
Spokes기존처럼 요청 라우팅·부하 분산·배치를 담당

푸시(쓰기)는 이렇게 흘러갑니다

  1. 레플리카가 들어온 팩 파일을 색인합니다.
  2. 팩 파일을 Blob Storage에 올립니다. 여기까지는 다른 쓰기와 조율할 필요가 없어요.
  3. Ref-CAS 트랜잭션 한 번으로 “매니페스트에 이 팩 추가 + 참조 이동"을 함께 확정합니다. 로그 레플리카 과반이 기록하면 끝입니다.

트랜잭션은 자기가 건드리는 참조만 잠급니다. 에이전트 A가 agent/a-123 브랜치를, 에이전트 B가 agent/b-456 브랜치를 푸시하면 둘은 서로 기다리지 않아요. 또 참조는 항상 이미 안전하게 저장된 객체만 가리키도록 순서를 지켜서, “브랜치는 옮겨졌는데 커밋 데이터가 없다” 같은 상태가 생기지 않습니다.

페치(읽기)는 이렇게 가벼워집니다

확정된 변경마다 로그 순번(LSN) 이 붙고, 레포의 버전은 가장 최근 순번입니다. 레플리카는 읽기 요청이 오면 Ref-CAS에 “지금 버전이 몇이야?“를 묻고, 자기 캐시가 최신이면 비교 한 번으로 끝냅니다. 바뀐 게 있을 때만 필요한 팩을 받아 와요. 변경이 없는 페치가 압도적으로 많은 CI·에이전트 환경에서 특히 효과가 큽니다.

왜 이 설계까지 왔나

GitHub는 시행착오도 공개했습니다.

시도결과
모든 참조를 블롭 하나에 기록쓰기가 초당 수백 번 중반에서 막힘
참조를 여러 블롭 조각으로 분산쓰기는 빨라졌지만, 읽을 때 모든 조각을 확인해야 해서 읽기가 느려짐
참조 전용 복제 로그(Ref-CAS) 분리처리량을 가장 많이 끌어올리면서 정확성·내구성·가용성·지연을 함께 지킴 → 채택

예전 구조에서는 컴팩션이 트래픽을 받는 레플리카마다 돌아야 했는데, 이제는 전용 노드가 한 번만 해서 결과를 공유합니다. 서비스 서버는 요청 처리에만 집중할 수 있어요.

주의할 점과 한계

  • 숫자는 GitHub 내부 테스트 결과입니다. 하드웨어·부하 패턴 같은 측정 방법은 공개되지 않았어요. 실제 서비스에서 같은 수치가 나온다는 보장은 아닙니다.
  • 아직 비공개 프리뷰입니다. 넓은 배포는 “내년 초” 예정이라, 지금 대부분의 레포는 이 구조 위에 있지 않습니다.
  • 같은 참조를 두고는 여전히 줄을 섭니다. 참조 단위로 잠그기 때문에, 에이전트 100개가 모두 main에 직접 푸시하면 한 번에 하나만 성공하고 나머지는 거절됩니다. 이건 Git의 원래 동작이기도 해요.
  • 로드맵은 로드맵입니다. 부분·전역 레플리카, 클론 없이 작업하는 기능, 원자적 커밋 API, 이벤트 스트림 등은 계획으로만 소개됐습니다.
  • Git 쪽 숙제도 남았습니다. 글쓴이들도 부분 클론·얕은 클론·스파스 체크아웃이 서로 잘 맞물리지 않는 부분이 있다고 인정했어요.
  • GitHub.com 이야기입니다. 사내에 직접 운영하는 Git 서버(GitHub Enterprise Server, GitLab 등)에 적용된다는 언급은 없습니다.

독자가 할 일

에이전트를 돌리는 팀이라면

  • 에이전트마다 자기 브랜치를 쓰게 하세요. 참조 단위로 잠그는 구조에서는 브랜치를 나누는 것이 곧 병렬성입니다. 지금 구조에서도 같은 브랜치 경쟁은 거절·재시도만 늘립니다.
  • main으로 합치는 길은 하나로 모으세요. 머지 큐나 PR 리뷰를 거치게 하면 같은 참조에 대한 경쟁을 서버가 아니라 절차가 정리해 줍니다.
  • 푸시 한 번이 몇 개의 읽기를 부르는지 세어 보세요. CI 트리거, 미러링, 다른 에이전트의 폴링이 쌓이면 요청 수가 쓰기의 몇 배가 됩니다. 변경이 없을 때 굳이 클론을 새로 받지 않게 하는 것만으로도 부하가 줄어요.

분산 시스템을 공부하는 분이라면

  • “바뀌지 않는 큰 데이터는 아무 데나 동시에 쓰고, 작은 포인터만 합의한다“는 패턴을 기억해 두세요. 객체 스토리지 위의 테이블 포맷(Iceberg·Delta Lake)이 메타데이터 포인터만 원자적으로 바꾸는 방식과 같은 계열의 아이디어입니다.
  • 내 PC의 Git에도 CAS가 있습니다. git update-ref는 기존 값을 함께 주면 그 값일 때만 참조를 바꾸고, git push --force-with-lease는 “원격 브랜치가 내가 마지막으로 본 상태일 때만 덮어쓰기"를 합니다. 강제 푸시가 꼭 필요할 때는 --force 대신 이쪽을 쓰는 습관을 들이면 동료의 커밋을 날릴 일이 줄어요.

정리

  • GitHub가 AI 에이전트 시대를 대비해 Git 저장 구조를 새로 만들었고, 내부 테스트에서 에이전트 5,000개·초당 푸시 7,200번을 처리했습니다.
  • 비결은 바뀌지 않는 객체는 조율 없이 저장하고, 참조 변경만 합의하는 것. 큰 데이터(Blob Storage)와 작은 포인터(Ref-CAS)를 갈라놓았습니다.
  • 지금은 제한된 비공개 프리뷰이고, 넓은 배포는 내년 초 예정입니다. 수치는 내부 테스트 기준이라는 점도 함께 기억해 두세요.
  • 당장 할 수 있는 건 구조와 상관없이 통하는 습관입니다. 에이전트별 브랜치, main으로 가는 길은 하나, 불필요한 읽기 줄이기.
