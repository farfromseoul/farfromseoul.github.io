  • 감시에 필요한 데이터는 Anthropic이 아니라 고객의 클라우드 저장소(Amazon S3 또는 Google Cloud Storage) 에 고객이 관리하는 키로 암호화해 둡니다.
  • 위험이 감지되면 입력·출력 원문이 빠진 ‘세이프티 케이스(Safety Case)’ 가 만들어지고, 저장소나 API로 읽어 회사 보안관제(SIEM)에 붙일 수 있습니다.
  • Anthropic·클라우드 회사 직원이 데이터를 들여다보는 사람 검토는 없고, 학습에도 쓰지 않는다고 밝혔습니다.
  • Anthropic이 따로 요금을 받지는 않지만 저장·키 사용·전송 비용은 고객의 클라우드 청구서에 붙습니다.
  • 대상 플랫폼은 Claude Platform, Claude Platform on AWS, Amazon Bedrock, Claude on Google Cloud이고 Microsoft Foundry는 “곧 지원” 입니다.
  • 성능 벤치마크 같은 수치는 이번 발표에 없습니다(2026-11-25 확인 기준).

먼저 용어 몇 가지

  • ZDR(Zero Data Retention, 데이터 무보존): AI 회사가 요청과 응답을 처리만 하고 저장하지 않기로 하는 계약입니다. 금융·의료처럼 규제가 까다로운 회사가 주로 씁니다.
  • 오남용(misuse) 감시: 모델이 사이버 공격, 사기, 위험한 생물학 정보 등에 쓰이는지 살피는 일입니다.
  • 분류기(classifier): 요청 하나하나를 보고 위험한지 판정하는 작은 AI 모델입니다.
  • CMEK(Customer-Managed Encryption Keys, 고객 관리 암호화 키): 데이터를 암호화하는 키를 클라우드 회사가 아니라 고객이 직접 만들고 관리하는 방식입니다.
  • SIEM(Security Information and Event Management): 회사 안의 보안 로그를 한곳에 모아 경보를 띄우는 보안관제 시스템입니다(Splunk, Microsoft Sentinel 등).

무슨 일이 있었나: ZDR과 안전 감시의 충돌

배경은 9월 1일 Anthropic 공지(10월 21일 수정)에 나와 있습니다. Mythos급·Fable 같은 고성능 모델은 사기, 사이버 공격, 훔친 기업 계정 악용에 쓰일 위험이 더 크고, 이런 공격은 여러 세션·여러 계정에 나눠 진행되기 때문에 요청 하나만 봐서는 잡기 어렵습니다. 그래서 Anthropic은 Fable 5부터 30일 데이터 보존을 도입했는데, 규제를 받는 고객들은 이를 받아들이기 어려웠습니다.

EFS는 이 충돌을 풀려는 시도입니다. “데이터를 보관해야 여러 요청을 이어서 볼 수 있다"는 조건은 그대로 두고, 보관 장소를 고객 쪽으로 옮긴 것이 핵심입니다. 9월 공지에서는 EFS가 준비될 때까지 자격을 갖춘 고객에게 Fable 5·5.1의 ZDR을 한시적으로 열어 두었다고 밝혔습니다.

11월 23일 베타 안내에서는 실제 사례로, 9월 위협 보고서에 실린 공격을 들었습니다. 한 에이전트가 약 50개 조직을 노린 공격을 여러 병렬 에이전트로 쪼개 돌리고, 훔친 계정 정보를 세션 사이에 저장해 두었다는 내용입니다. 요청 단위 분류기로는 조각 하나하나가 평범해 보여 놓치기 쉬운 유형입니다.

한계·주의할 점

  • “무보존"의 뜻이 바뀝니다. Anthropic 쪽에는 남지 않지만, 감시용 데이터는 우리 회사 클라우드에 남습니다. 사내 보안팀과 감사팀 입장에서는 “누구도 보관하지 않는다"가 아니라 “우리가 보관한다"가 됩니다. 저장소 접근 권한과 보관 기간 정책을 직접 정해야 합니다.
  • 비용이 숨어 있습니다. Anthropic은 요금을 받지 않지만 트래픽이 많은 서비스라면 저장·키 호출·네트워크 전송 비용이 꾸준히 쌓입니다. 베타 전에 트래픽 기준으로 추정해 보세요.
  • 보관 기간·복호화 조건은 공개 기사에 나오지 않습니다. 보관 기간이 며칠인지, 어떤 조건에서 누가 세이프티 케이스를 열람하는지는 이번에 확인한 공지·보도에는 구체적으로 없습니다. 개발자 문서와 보안 백서에서 직접 확인해야 합니다.
  • 자동 감시의 오탐. 사람 검토가 없다는 것은 개인정보 측면에선 장점이지만, 오탐(정상 업무를 위험으로 판정)이 나오면 대응은 고객 보안팀 몫입니다. 침투 테스트·보안 연구처럼 공격과 비슷해 보이는 업무를 하는 팀은 특히 확인이 필요합니다.
  • 출처가 회사 발표뿐입니다. 이번 내용을 다룬 기사들도 Anthropic 발표를 정리한 수준이고, 독립된 보안 검증이나 비판적 분석은 아직 보이지 않습니다.
  • Azure 사용자는 기다려야 합니다. 9월 공지에는 Azure Blob Storage도 언급됐지만, 11월 베타 안내에서는 S3와 Google Cloud Storage만 나오고 Microsoft Foundry는 “곧 지원"입니다.

도입 전 확인할 6가지

  1. 우리 계약이 대상인지: ZDR 계약이 있는지, 쓰려는 플랫폼이 베타 목록에 있는지 계정 담당 팀에 확인합니다.
  2. 저장소 위치와 지역: 어느 클라우드·어느 리전에 둘지 정합니다. 데이터 국외 이전 규정이 있다면 리전 선택이 중요합니다.
  3. 키와 접근 권한: 키를 누가 관리하고, 저장소에 누가 접근할 수 있는지, 감사 로그를 켜는지 정합니다.
  4. 보관 기간: 공식 문서에 나온 보관 요구 사항과 사내 정책이 맞는지 비교합니다.
  5. SIEM 연동과 대응 절차: 세이프티 케이스가 들어오면 누가 보고 어떻게 대응할지, 오탐일 때 어떻게 처리할지 정해 둡니다.
  6. 비용 추정: 하루 요청량 기준으로 저장·전송 비용을 미리 계산합니다.

나에게 맞는 선택

  • 입문자·학생: 개인 요금제와는 직접 관계가 없습니다. 다만 “AI 회사가 내 데이터를 저장하느냐"와 “AI가 나쁜 일에 쓰이는지 감시하느냐"가 서로 부딪치는 문제라는 점, 그리고 이를 보관 장소를 바꾸는 방식으로 풀려 한다는 점은 AI 보안·개인정보를 공부할 때 좋은 사례입니다.
  • 개발자: API로 Claude를 쓰는 서비스라도 회사가 ZDR 계약을 맺지 않았다면 이번 변화와는 관련이 적습니다. ZDR 계약이 있다면, 고성능 모델을 쓰려 할 때 EFS 설정이 조건이 되는지 계정 담당 팀에 확인해 두세요.
  • 보안·인프라 담당자: 실제 작업은 대부분 이쪽입니다. 클라우드 저장소, 키 관리, SIEM 연동, 보관 정책을 사내 기준에 맞춰 설계해야 하므로, 베타 단계에서 작은 범위로 먼저 시험해 보는 것이 안전합니다.

정리

Enterprise Frontier Safeguards는 “데이터를 남기지 말라"는 규제 고객의 요구와 “여러 요청을 이어서 봐야 공격을 잡는다"는 안전 요구 사이의 절충안입니다. 감시용 데이터를 고객 클라우드에 고객 키로 두고, 원문 없는 탐지 결과만 넘기는 구조입니다. 다만 탐지 성능 수치와 보관 기간 같은 세부 조건은 아직 공개 자료로 확인되지 않았고, 저장 비용과 운영 책임이 고객 쪽으로 넘어온다는 점을 함께 따져 봐야 합니다.
