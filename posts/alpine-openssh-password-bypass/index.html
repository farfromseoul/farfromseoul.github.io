Alpine Linux에서 비밀번호 없이 SSH 로그인이 되던 문제, 내 서버도 해당될까

musl의 crypt()와 OpenSSH의 오래된 방어 코드가 맞물려, 긴 비밀번호 하나로 로그인이 뚫렸습니다. 해당 조건과 점검·조치 방법을 정리합니다.

2026년 11월 5일, Alpine Linux가 openssh-server의 비밀번호 인증 우회 보안 공지를 냈습니다. 같은 날 OpenSSH도 긴급 패치인 10.6p2를 공개했어요. 해커뉴스 1·2위를 나란히 차지할 만큼 반응이 컸던 이 문제를, 무슨 일이 있었고 내 서버가 해당되는지, 무엇을 하면 되는지 순서대로 정리합니다.

한 줄 요약

조건이 맞는 Alpine 서버에서는 257~1024바이트 길이의 아무 문자열을 비밀번호로 보내면, 비밀번호가 없는 계정으로 로그인할 수 있었습니다. 접속 한 번이면 되고, 매번 성공합니다.

왜 이런 일이 생겼나

세 가지가 겹쳐서 생긴 문제입니다.

  1. 비밀번호 없는 계정은 *로 저장됩니다. 리눅스는 계정 비밀번호를 해시(hash, 원래 값을 알 수 없게 바꾼 문자열)로 /etc/shadow에 저장하는데, 비밀번호 로그인을 쓰지 않는 계정은 해시 자리에 *만 넣어 둡니다. Alpine 기본 이미지의 root, SSH 키로만 들어오는 계정이 대표적입니다.
  2. OpenSSH는 이런 계정에도 “가짜 검사"를 합니다. 계정이 있는지 없는지를 응답 시간으로 알아내는 공격(2016년 CVE-2016-6210)을 막으려고, 비밀번호가 없는 계정이어도 다른 계정의 해시 설정(salt)을 빌려 와서 똑같이 계산하는 척합니다.
  3. musl의 crypt()는 너무 긴 비밀번호에 *를 돌려줍니다. Alpine이 쓰는 C 라이브러리 musl은 SHA 계열 해시($5$, $6$)를 계산할 때 256바이트를 넘는 입력을 거부하고, 실패 표시로 *를 반환합니다.

결국 “계산 결과 *“와 “저장된 값 *“가 같다고 판정되어 로그인이 통과된 거예요. 각각은 2012년과 2016년에 합리적인 이유로 들어간 동작이었는데, 함께 놓였을 때 구멍이 됐다는 점이 이 사건의 핵심입니다.

내 서버가 해당되는지 확인하기

아래 네 가지가 모두 맞아야 영향을 받습니다.

조건확인 방법
PAM 없이 비밀번호를 검사함 (openssh-server, 또는 openssh-server-pam에 UsePAM no)apk info -e openssh-server-pam, sshd -T | grep -i usepam
비밀번호 로그인이 켜져 있음 (PasswordAuthentication yes, OpenSSH 기본값)sshd -T | grep -i passwordauthentication
비밀번호 칸이 *인 계정이 있음awk -F: '$2=="*"{print $1}' /etc/shadow
다른 계정 중 $5$·$6$ 해시가 하나라도 있음awk -F: '$2 ~ /^\$[56]\$/{print $1}' /etc/shadow

root로 로그인하려면 PermitRootLogin yes까지 필요합니다. 기본값인 prohibit-password라면 root는 안전합니다.

영향이 없는 경우

  • glibc를 쓰는 배포판(Ubuntu, Debian, RHEL 등)과 리눅스가 아닌 시스템
  • PAM으로 비밀번호를 검사하는 경우 (UsePAM yes)
  • PasswordAuthentication no로 비밀번호 로그인을 꺼 둔 경우
  • 계정이 !로 잠겨 있는 경우
  • sshd가 없는 컨테이너, OpenWrt 기본 SSH 서버(Dropbear)

특히 주의할 곳: Alpine의 tiny-cloud 이미지(3.18.11 ~ 3.24.3)는 alpine 사용자에게 비밀번호 없이 관리자 권한(doas)을 줍니다. 이 서버에 $6$ 해시를 가진 계정이 하나라도 생기면 곧바로 위험해집니다.

조치 방법

1. 업데이트하고 sshd를 재시작합니다.

apk upgrade -U -a
rc-service sshd restart

패키지만 올리고 재시작하지 않으면 이전 sshd가 계속 돌고 있어서 효과가 없습니다. 고쳐진 버전은 브랜치마다 다릅니다.

Alpine 브랜치고쳐진 openssh 버전
edge10.6_p2-r0
3.2410.3_p1-r2
3.2310.2_p1-r1
3.2210.0_p1-r11
3.219.9_p2-r1

지원이 끝난 3.16 ~ 3.20에도 수정 패키지가 나왔습니다. 패치된 Alpine 서버의 OpenSSH 버전이 꼭 10.6p2로 표시되지는 않으니, 버전 문자열이 아니라 위 패키지 버전으로 확인하세요.

2. 당장 업데이트가 어렵다면 비밀번호 로그인을 끕니다.

echo "PasswordAuthentication no" > /etc/ssh/sshd_config.d/00-no-passwords.conf
sshd -t && rc-service sshd restart
sshd -T | grep -i passwordauthentication   # passwordauthentication no 가 나오면 적용됨

sshd_config.d 폴더는 Alpine 3.19부터 읽습니다. 끄기 전에 SSH 키로 로그인되는지 먼저 확인하고, 기존 접속 창 하나는 열어 둔 채로 진행하세요. 실수하면 서버에 다시 못 들어갈 수 있습니다.

3. 이미 뚫렸는지 확인합니다.

grep "Accepted password for" /var/log/messages

root, alpine, 키 전용 계정처럼 비밀번호가 없어야 하는 계정에 이 기록이 있다면 침입을 의심해야 합니다. doas 사용 기록, 최근 생긴 사용자와 파일, authorized_keys 변경도 함께 보세요. 침입이 아니라고 확신할 수 없다면 서버를 새로 만드는 게 안전합니다.

OpenSSH 10.6p2는 무엇을 바꿨나

저장된 비밀번호 칸이 네 글자보다 짧으면 아예 일치로 보지 않게 했습니다. OpenSSH는 이 수정을 임시방편이라고 밝혔고, 근본 원인은 sshd 바깥(crypt()의 실패 표시 방식)에 있다고 봤습니다. 공지 시점에는 CVE 번호가 없었고, 실제 공격 사례도 보고되지 않았습니다.

정리

  • Alpine에서 sshd를 운영한다면 업데이트 후 반드시 재시작하세요.
  • 비밀번호 로그인이 필요 없다면 이번 기회에 PasswordAuthentication no를 기본으로 두는 걸 권합니다. 이번 문제도 그 한 줄이면 막혔습니다.
  • 서로 다른 시기에 각자 맞는 이유로 들어간 동작이 함께 놓이면 보안 구멍이 될 수 있다는 점, 실패를 나타내는 값이 정상 값과 겹치지 않는지 따져 봐야 한다는 점이 이번 사건에서 얻을 교훈입니다.
