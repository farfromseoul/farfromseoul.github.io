“데이터베이스 버전은 잘 돌아가면 건드리지 않는다"는 말이 있습니다. 그런데 오늘부터 PostgreSQL 14를 쓰는 곳은 그 원칙을 다시 따져 봐야 합니다.

PostgreSQL 개발 그룹은 2026년 11월 12일 정기 업데이트(18.7, 17.12, 16.16, 15.20, 14.25)를 내면서 **“PostgreSQL 14의 마지막 릴리스”**라고 밝혔습니다. 이후로는 14 버전에 보안 패치도, 버그 수정도 나오지 않습니다.

이 글은 서비스·사내 시스템·사이드 프로젝트에서 PostgreSQL을 쓰는 개발자와, 데이터베이스 운영을 처음 맡게 된 분을 위한 정리입니다.

이 글은 PostgreSQL 공식 버전 정책 페이지와 11월 12일 릴리스 공지(메일링 리스트에 올라온 공지 원고), endoflife.date, AWS·Google Cloud·Azure 공식 문서를 교차 확인해 썼습니다. (2026-11-12 확인 기준. 공식 사이트 뉴스 게시는 한국 시각 기준 밤에 올라오므로, 확인 시점에는 버전 정책 표가 아직 이전 버전으로 표시돼 있었습니다.)

무슨 일이 있었나

PostgreSQL은 메이저 버전마다 첫 출시 후 5년 동안 지원합니다. 14는 2021년 9월 30일에 나왔으니, 정책대로라면 올해 11월에 수명이 끝납니다.

먼저 용어 몇 가지

  • EOL(End of Life, 지원 종료): 개발 측이 더 이상 수정 버전을 내지 않는 상태입니다. 프로그램이 멈추는 것은 아니지만, 새로 발견된 취약점이 영영 고쳐지지 않습니다.
  • 메이저 / 마이너 버전: PostgreSQL에서 14.25의 앞자리 14가 메이저, 뒷자리 25가 마이너입니다. 마이너 업데이트는 실행 파일만 바꾸고 재시작하면 되지만, 메이저 업그레이드는 데이터 저장 형식이 달라질 수 있어 별도 절차가 필요합니다.
  • pg_upgrade: 데이터를 덤프하지 않고 기존 데이터 디렉터리를 새 메이저 버전 형식으로 옮겨 주는 공식 도구입니다.
  • 논리 복제(logical replication): 테이블의 변경 내용을 행 단위로 다른 서버에 실시간 전달하는 기능입니다. 버전이 다른 서버 사이에서도 쓸 수 있어 무중단에 가까운 이전에 쓰입니다.
  • 확장 지원(Extended Support): 클라우드 회사가 커뮤니티 지원이 끝난 버전을 추가 요금을 받고 일정 기간 더 패치해 주는 상품입니다.

1단계: 지금 쓰는 버전이 무엇이든, 이번 마이너 업데이트부터

이번 릴리스는 140개가 넘는 버그를 고쳤고, 그중 상당수가 데이터 손상이나 잘못된 조회 결과와 관련돼 있습니다. 공지가 짚은 항목 가운데 업데이트 후 따로 손봐야 하는 것만 추리면 아래와 같습니다.

해당되는 경우문제업데이트 후 할 일
GIN 인덱스(배열·JSONB·전문 검색에 주로 씀)가 손상된 것 같을 때조회 시 행이 빠지거나 엉뚱한 행이 나올 수 있음해당 인덱스 재생성(REINDEX)
pg_trgm 확장의 GiST 인덱스(gist_trgm_ops)를 쓸 때검색에서 일치하는 행이 빠질 수 있음해당 인덱스 재생성
길이 없는 bpchar 열에 B-tree 인덱스가 있을 때 (char(n)은 해당 없음)인덱스 전용 스캔이 틀린 결과를 낼 수 있음해당 인덱스 재생성
조회 중 missing chunk number 오류를 본 적이 있을 때TOAST(큰 값을 따로 저장하는 영역) 인덱스 갱신 누락테이블 단위 재생성
증분 백업을 쓸 때손상된 백업이 만들어질 수 있음업데이트 후 전체 백업을 새로 받고, 이후 증분은 그걸 기준으로
파티션 테이블에 NOT NULL NO INHERIT 제약이 있을 때파티션에 NULL이 들어갈 수 있었음공지의 확인 쿼리로 찾아 제거 또는 수정

재생성 명령은 공식 공지에 나온 형식 그대로입니다. 인덱스·테이블 이름만 바꿔 쓰세요.

REINDEX INDEX your_index_name;   -- 특정 인덱스
REINDEX TABLE your_table_name;   -- 테이블과 그 TOAST 인덱스까지

REINDEX는 작업 중 해당 테이블 쓰기를 막습니다. 운영 중인 큰 테이블이라면 사용량이 적은 시간에 하거나, 공식 문서의 REINDEX ... CONCURRENTLY 옵션 설명을 먼저 읽어 보세요.

이 밖에 대기 서버(standby)에서 병렬 pg_dump를 돌릴 때 덤프와 대기 서버 데이터가 함께 손상될 수 있던 문제, 크래시 뒤 데이터가 어긋날 수 있던 문제, 파티션 정리(pruning)·플래너가 행을 빠뜨리던 문제 등도 고쳐졌습니다. 마이너 업데이트는 덤프·복원 없이 실행 파일 교체와 재시작만으로 끝나니, 미룰 이유가 적습니다. 여러 번 건너뛴 경우에는 그사이 릴리스 노트의 후속 작업도 확인해야 합니다.

2단계: 14를 쓴다면 남은 기한 확인

커뮤니티 지원은 오늘 끝나지만, 관리형 클라우드 데이터베이스는 회사마다 자체 일정이 있습니다.

서비스표준 지원 종료그 이후
Amazon RDS for PostgreSQL2027-02-282027-03-01부터 유료 Extended Support, 2030-02-28 종료 (3년차부터 요금 단계 상승)
Google Cloud SQL for PostgreSQL2027-02-01유료 확장 지원 시작, 2030-02-01 지원 중단
Azure Database for PostgreSQL (Flexible Server)2027-01-31확장 지원 문서 별도 확인 필요

몇 달 여유가 있어 보이지만, 확장 지원은 공짜가 아니고 요금이 읽기 복제본과 대기 인스턴스에도 붙는 구조라 규모가 크면 부담이 커집니다. 직접 운영하는 서버(온프레미스, VM, 도커)라면 여유 기간이 없습니다. 오늘이 마지막 패치입니다.

3단계: 메이저 업그레이드 방법 고르기

방법중단 시간잘 맞는 경우주의할 점
덤프 후 복원 (pg_dump/pg_dumpall → 새 서버에 복원)데이터 크기에 비례작은 DB, 개발·테스트 환경, CI가장 단순하지만 큰 DB는 오래 걸림
pg_upgrade보통 몇 분직접 운영하는 서버링크 모드(-k)는 빠르지만, 새 클러스터를 한 번 띄우면 옛 클러스터로 돌아갈 수 없음
논리 복제로 이전전환 순간 몇 초 수준멈출 수 없는 큰 DB스키마·시퀀스·대용량 객체(large object)는 자동으로 넘어가지 않아 따로 챙겨야 함

관리형 서비스라면 콘솔의 “메이저 버전 업그레이드” 기능이나 블루/그린 배포 기능을 먼저 살펴보세요.

pg_upgrade는 “검사 모드"부터

pg_upgrade에는 실제로 데이터를 옮기지 않고 호환성만 점검하는 -c(--check) 옵션이 있습니다. 경로는 환경에 맞게 바꿔야 합니다.

pg_upgrade -c \
  -b /old/14/bin -B /new/18/bin \
  -d /old/14/data -D /new/18/data

-b/-B는 옛·새 실행 파일 폴더, -d/-D는 옛·새 데이터 폴더입니다. 검사에서 걸리는 확장 모듈이나 데이터 타입이 있으면 여기서 미리 드러납니다.

업그레이드 뒤 잊기 쉬운 것

  • 통계 다시 모으기: 18의 pg_upgrade는 플래너 통계 대부분을 옮겨 주지만, CREATE STATISTICS로 만든 확장 통계 등은 넘어가지 않습니다. 공식 문서는 업그레이드 뒤 아래 두 명령을 안내합니다. 첫 줄은 통계가 없는 테이블만 빠르게 채우고, 둘째 줄은 전체 통계를 갱신합니다.

    vacuumdb --all --analyze-in-stages --missing-stats-only
vacuumdb --all --analyze-only

  • 확장 모듈 버전: PostGIS, TimescaleDB 같은 확장은 새 메이저 버전용 패키지가 먼저 설치돼 있어야 합니다.

  • 애플리케이션·드라이버 테스트: 같은 쿼리라도 플래너가 바뀌어 실행 계획이 달라질 수 있습니다. 느린 쿼리 상위 몇 개는 꼭 비교해 보세요.

도커로 띄운 PostgreSQL이라면

공식 postgres 도커 이미지는 18부터 볼륨을 붙이는 경로가 바뀌었습니다. 예전처럼 /var/lib/postgresql/data에 볼륨을 붙이면 컨테이너가 뜨지 않는 사례가 보고됐고, 18에서는 상위 폴더인 /var/lib/postgresql에 붙이는 방식이 안내되고 있습니다. 또 이미지 태그만 postgres:14 → postgres:18로 바꾼다고 데이터가 변환되지는 않습니다. 덤프 후 복원이나 pg_upgrade 절차를 따로 밟아야 합니다. 정확한 설정은 Docker Hub의 postgres 이미지 설명을 기준으로 확인하세요.

어느 버전으로 갈까

  • 18로 가는 것이 무난합니다. 출시 1년이 넘어 마이너 업데이트가 7번 나왔고, 2030년 11월까지 지원됩니다.
  • 19는 11월 19일 정식 출시 예정입니다. 새 메이저의 첫 버전(x.0)은 운영 환경보다 테스트 환경에서 먼저 써 보고, 몇 번의 마이너 업데이트 뒤에 올리는 팀이 많습니다. 공지도 19로 올릴 때 전문 검색·pg_trgm·fuzzystrmatch 인덱스는 재생성이 필요할 수 있다고 안내합니다.
  • 15·16을 쓰는 곳도 남은 기간을 확인해 두세요. 15는 1년 뒤(2027년 11월) 같은 상황을 맞습니다.

지금 할 일 체크리스트

  1. 운영 중인 모든 DB의 버전을 확인합니다: SELECT version();
  2. 코드·인프라 설정에서 14 버전 고정을 찾습니다(도커 이미지 태그, Terraform의 engine_version, 헬름 차트 값 등).
  3. 사용 중인 메이저 버전의 **최신 마이너(이번 릴리스)**로 먼저 올리고, 위 표의 후속 작업이 해당되는지 확인합니다.
  4. 14를 쓴다면 업그레이드 대상 버전(권장 18)과 방법(덤프/pg_upgrade/논리 복제)을 정하고, 테스트 환경에서 리허설합니다.
  5. 관리형 서비스라면 확장 지원 요금이 시작되기 전으로 일정을 잡습니다.

정리

  • PostgreSQL 14는 2026-11-12 릴리스(14.25)가 마지막입니다. 이후 발견되는 취약점은 고쳐지지 않습니다.
  • 이번 정기 릴리스에는 인덱스 손상·잘못된 결과를 고치는 수정이 많아, 버전과 상관없이 업데이트 후 재생성·전체 백업 같은 후속 작업을 확인해야 합니다.
  • 관리형 클라우드는 2027년 초까지 표준 지원이 남았지만, 그 뒤는 유료 확장 지원입니다.
  • 메이저 업그레이드는 DB 크기와 허용 중단 시간에 따라 덤프·pg_upgrade·논리 복제 중 고르고, pg_upgrade -c로 미리 점검하세요.
