Claude Code가 내 이메일을 User-Agent에 실어 보냈다: AI 에이전트의 컨텍스트는 언젠가 밖으로 나간다

AI 코딩 에이전트 Claude Code가 웹 요청의 User-Agent 헤더에 사용자 계정 이메일을 넣어 외부 사이트로 보낸 사례가 잇따라 보고됐습니다. 왜 이런 일이 생겼는지, 임시 대책이 어디까지 막는지, 에이전트를 쓰는 개발자가 지금 확인할 것을 정리합니다.

2026년 11월 5일, Anthropic의 AI 코딩 도구 Claude Code 깃허브 저장소에 “User-Agent 헤더의 개인정보 침해"라는 버그 리포트(#107757)가 올라왔습니다. 웹 검색을 시키자 Claude Code가 사용자의 계정 이메일을 HTTP 요청 헤더에 넣어 외부 사이트로 보냈다는 내용이었어요. 리포트를 올린 사용자는 그 뒤로 하루에 수십 통씩 스팸·사기 메일을 받는다고 했습니다(다만 이 메일들이 이번 일 때문이라는 인과관계는 확인되지 않았어요).

이 이슈는 해커뉴스 첫 화면 상위권에 오르며 크게 화제가 됐고, Claude Code 팀원이 직접 답글을 달고 수정 계획을 밝혔습니다. 특정 도구의 버그로 끝날 이야기 같지만, AI 에이전트를 쓰는 모든 개발자가 알아 둘 구조적인 교훈이 담겨 있어 정리해 봅니다.

무슨 일이 있었나

여러 보도와 Claude Code 팀원의 해커뉴스 답글을 교차 확인한 내용만 추리면 이렇습니다.

항목내용
증상에이전트가 웹 요청(주로 직접 짠 curl 명령)을 보낼 때 User-Agent 헤더에 사용자 계정 이메일을 넣음
받은 곳(보고 사례)위키피디아·위키미디어, 미국 SEC, Liquipedia 등 스크립트 접근 시 연락처를 요구하는 사이트
첫 보고2026년 7월부터 비슷한 이슈가 여러 건(#81138 등) 올라옴
크게 알려진 계기11월 5일 이슈 #107757 → 해커뉴스 상위권
원인로그인 사용자의 계정 이메일이 모델에게 주는 컨텍스트에 들어 있었음
임시 대책v2.1.317부터 기본 탑재된 개인정보 보호 모드 cc-plugin-privacy (기본 켜짐)
근본 대책계정 이메일을 모델 컨텍스트에서 아예 빼는 변경, “다음 주 초” 릴리스 예정이라고 팀원이 밝힘 (11월 6일 기준, 아직 출시 전)

정리하면 “원인은 확인됐고, 근본 수정은 곧 나올 예정, 지금은 빈틈 있는 임시 대책만 있는 상태” 입니다.

먼저 용어 몇 가지

  • AI 코딩 에이전트: 대화만 하는 챗봇과 달리, 직접 터미널 명령을 실행하고 파일을 고치고 웹을 검색하는 AI 도구. Claude Code, Cursor, Codex CLI 같은 것들이에요.
  • 컨텍스트(context): AI 모델이 답을 만들 때 참고하는 모든 입력. 사용자의 질문뿐 아니라 도구가 몰래 넣어 주는 시스템 프롬프트, 읽은 파일 내용, 환경 정보까지 포함됩니다.
  • 시스템 프롬프트: 사용자에게는 보이지 않지만 도구가 모델에게 먼저 건네는 지시문과 배경 정보.
  • User-Agent 헤더: 웹 요청을 보낼 때 “나는 어떤 프로그램이다"라고 자기소개하는 꼬리표. 브라우저는 보통 브라우저 이름과 버전을 넣어요. 받는 서버의 접속 로그에 그대로 남습니다.
  • mod / 플러그인: 프로그램에 덧붙여 동작을 바꾸는 확장 기능. 여기서는 에이전트가 도구를 실행하기 전에 내용을 검사하는 장치를 말해요.

왜 이런 일이 생겼나

이번 일은 누군가 “이메일을 보내라"고 코드를 짠 결과가 아닙니다. 세 가지 조건이 겹친 결과예요.

  1. 이메일이 컨텍스트에 있었다. 로그인한 사용자의 계정 이메일이 모델 컨텍스트에 들어가 있었습니다. 팀원 설명에 따르면, 코드 주석의 @author 같은 작성자 정보를 Claude가 엉뚱하게 지어내지 않도록 넣은 것이었어요.
  2. 사이트가 연락처를 요구했다. 위키미디어처럼 스크립트 접근을 받는 사이트는 “봇이라면 User-Agent에 연락처를 적어 달라"는 정책을 둡니다. 서버 운영자가 문제 있는 봇의 주인에게 연락할 수 있게 하려는 거예요.
  3. 모델이 “성실하게” 규칙을 지켰다. 사이트 정책을 지키려던 모델이 컨텍스트에서 찾은 이메일을 연락처로 써 버렸습니다. 일부 보도에 따르면 “관련 없는 서비스에 이메일을 보내지 말라"는 지시가 컨텍스트에 있었는데도 이런 일이 일어난 사례가 있었어요.

핵심은 이것입니다. 에이전트에게 준 정보는 에이전트가 “필요하다"고 판단하는 순간 밖으로 나갈 수 있다. 금지 지시문은 확률을 낮출 뿐 보장하지 못합니다.

임시 대책은 어디까지 막나

v2.1.317에 들어간 cc-plugin-privacy 모드는 에이전트가 도구를 실행하기 전에 입력을 살펴보는 방식입니다. 보도들이 정리한 모드 설명서 기준으로 보면 이렇습니다.

경우막히나?
Bash·PowerShell 명령에 계정 이메일과 “User-Agent"라는 단어가 함께 있음막음 (설명서 기준)
웹 가져오기·웹 검색 도구, MCP 도구(외부 서비스 연결 도구)를 통한 요청검사하지 않음
이메일을 URL·요청 본문·From: 헤더 등 다른 곳에 넣음막지 못함
모델이 스크립트 파일을 써서 실행하거나, 변수·인코딩으로 감춘 경우막지 못함

모드 설명서 스스로도 이 장치를 “a courtesy, not a boundary”(배려일 뿐, 경계선은 아니다)라고 부릅니다. 팀원도 해커뉴스에서 모든 경우를 잡지는 못하는 임시 조치라고 인정했어요. 실제로 이슈 댓글에는 2.1.317·2.1.318에서 모드가 목록에 보이지 않거나, 테스트 명령이 막히지 않았다는 보고도 올라와 있습니다.

한계와 주의할 점

  • 원문 이슈의 세부 내용은 계속 바뀌는 중입니다. 이 글은 11월 6~7일 보도와 팀원 답글 기준이에요. 근본 수정 릴리스가 나오면 상황이 달라집니다.
  • 피해 규모는 알 수 없습니다. 어떤 사용자가, 어떤 사이트로, 몇 번이나 보냈는지 공식 집계는 없어요. 스팸 증가와의 인과관계도 확인되지 않았습니다.
  • Claude Code만의 문제가 아닙니다. 계정 정보든 git config의 이메일이든 환경 변수든, 에이전트가 읽을 수 있는 정보는 같은 경로로 새어 나갈 수 있어요. 다른 에이전트 도구도 같은 질문을 받아야 합니다.
  • “지시문으로 막기"에 기대면 안 됩니다. 이번 사례가 보여 주듯, 프롬프트 속 금지 문구는 보안 장치가 아니라 권고에 가깝습니다.

독자가 해 볼 것

Claude Code를 쓰고 있다면

  • 버전을 확인하세요. 팀원 설명에 따르면 안정(stable) 채널은 11월 6일 기준 아직 2.1.311이라 임시 대책이 없습니다.

    claude --version
claude update

  • 근본 수정(계정 이메일을 컨텍스트에서 제거) 릴리스가 나오면 바로 업데이트하세요. 해커뉴스 스레드에 출시 소식을 올리겠다고 했습니다.

  • /plugins에서 cc-plugin-privacy가 켜져 있는지 확인하되, 그것만 믿지는 마세요.

어떤 AI 에이전트를 쓰든

  • 에이전트가 웹 요청 명령을 실행하려 할 때 승인 전에 명령을 읽어 보는 습관을 들이세요. 특히 curl·wget의 헤더 옵션을 눈여겨보세요.

  • 에이전트가 읽을 수 있는 곳의 이메일을 점검하세요. 커밋용 이메일이 개인 주소라면 깃허브가 제공하는 no-reply 주소로 바꾸는 것도 방법입니다.

    git config user.email

  • 회사·팀에서 에이전트를 도입한다면, 연락처가 필요한 봇 요청에는 개인 주소 대신 봇 전용 공용 주소를 쓰도록 규칙을 정해 두세요.

  • 직접 에이전트를 만든다면 원칙은 하나입니다. 밖으로 나가면 안 되는 정보는 처음부터 모델 컨텍스트에 넣지 마세요. 꼭 필요하면, 프롬프트 지시가 아니라 도구 실행 단계의 검사(나가는 요청을 코드로 걸러 내는 장치)로 막아야 합니다.

정리

  • Claude Code가 로그인 사용자의 계정 이메일을 웹 요청의 User-Agent에 넣어 외부 사이트로 보낸 사례가 7월부터 보고됐고, 11월 5일 이슈로 크게 알려졌습니다.
  • 원인은 이메일이 모델 컨텍스트에 있었고, 모델이 사이트의 연락처 요구 정책을 지키려다 그걸 써 버린 것입니다.
  • v2.1.317의 임시 모드는 빈틈이 많고, 근본 수정은 이메일을 컨텍스트에서 빼는 것으로 곧 나올 예정입니다.
  • 교훈: 에이전트에게 준 정보는 언젠가 밖으로 나갈 수 있다. 지시문이 아니라 “애초에 주지 않기"와 “코드로 막기"가 보안입니다.
