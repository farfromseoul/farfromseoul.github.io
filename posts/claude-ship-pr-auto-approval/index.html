  • 무엇을 AI가 승인해도 되는지는 팀이 저장소에 정책 파일로 적어 정합니다. 민감한 변경은 사람 승인을 요구할 수 있습니다.
  • 비용은 토큰 사용량 기준 과금이고, 관리자가 지출 한도를 걸 수 있습니다.
  • Anthropic은 처음에는 관찰 전용(observe-only) 모드로 돌려 보라고 권합니다.
  • 공개된 성과 수치는 Anthropic 내부 팀 기준뿐이고, 독립 평가는 아직 없습니다(2026-11-24 확인 기준).

이 글은 9to5Mac, Trending Topics, StartupHub.ai 등 보도를 교차 확인해 썼습니다. 공식 소개 페이지(claude.com)는 이 글을 쓰는 환경에서 열리지 않았으니, 도입 전에는 아래 “참고 출처"의 공식 페이지를 꼭 직접 확인하세요.

먼저 용어 몇 가지

  • 풀 리퀘스트(PR, Pull Request): “내가 고친 코드를 본 코드에 합쳐 주세요"라고 올리는 요청입니다. 보통 동료가 리뷰하고 승인(approve)해야 합칠(merge) 수 있습니다.
  • CI(지속적 통합): PR이 올라오면 자동으로 빌드·테스트를 돌려 깨진 곳이 없는지 확인하는 과정입니다.
  • 머지 충돌(merge conflict): 두 사람이 같은 곳을 다르게 고쳐서 자동으로 합칠 수 없는 상태입니다.
  • CODEOWNERS: GitHub에서 “이 폴더를 바꾸면 이 사람이 리뷰해야 한다"고 적어 두는 파일입니다. Claude Ship의 정책 파일은 이것의 확장판에 가깝다고 소개됐습니다.
  • 브랜치 보호 규칙(branch protection): main 같은 중요한 브랜치에 “승인 몇 개 이상, 테스트 통과 필수” 같은 조건을 거는 GitHub 설정입니다.

세 에이전트가 각각 하는 일

에이전트하는 일할 수 없는 일상태
Code Review코드베이스 전체를 기준으로 PR을 검토하고, 찾은 문제를 스스로 한 번 더 확인한 뒤 PR에 남김—이미 정식 제공(GA)
PR Steward실패한 CI, 머지 충돌, 리뷰 의견에 대응해 코드를 고침. 변경마다 되돌리는 방법을 설명승인·머지 불가베타
Claude Approvals저장소의 정책을 읽고, 정책이 허용하는 일상적 변경은 스스로 승인. 민감한 변경은 사람 승인 요구 가능정책 밖 변경 승인베타

개발자 개인은 Claude Code의 새 /ship 명령으로 자기 PR에 써 볼 수 있다고 보도됐습니다. 다만 명령의 정확한 옵션과 정책 파일의 이름·형식은 보도에 나오지 않아 이 글에는 적지 않았습니다. 공식 문서에서 확인하세요.

두 수치 모두 Anthropic이 자기 팀에서 직접 잰 값입니다. 한 보도(Superpower Daily)에 따르면 Anthropic도 이 효과를 Claude Ship 하나만의 결과로 떼어 내 측정하지 않았고, 자동 리뷰가 버그를 놓칠 수 있다고 밝혔습니다. 다른 팀에서도 같은 효과가 날지는 아직 알 수 없습니다.

한계·주의할 점

  1. “AI가 승인한다"는 것 자체가 새로운 위험입니다. 정책을 느슨하게 쓰면 사람 눈을 거치지 않은 코드가 main에 들어갑니다. 정책 파일이 사실상 보안 설정이 됩니다.
  2. 정책 파일도 코드처럼 보호해야 합니다. 누군가 PR로 정책 파일 자체를 느슨하게 바꾸는 경우를 막도록, 정책 파일 변경은 반드시 사람 승인을 거치게 하는 편이 안전합니다(공식 권고가 아닌 일반적인 운영 원칙입니다).
  3. 브랜치 보호 규칙과의 관계를 먼저 정해야 합니다. Anthropic은 관찰 전용 모드로 먼저 써 본 뒤에 브랜치 보호의 필수 조건으로 넣으라고 권한 것으로 보도됐습니다. AI 승인을 필수 승인 하나로 셀지, 사람 승인과 함께 요구할지는 팀이 결정할 몫입니다.
  4. 비용이 예측하기 어렵습니다. 토큰 기준 과금이라 PR이 크거나 많을수록 비용이 늘어납니다. 지출 한도부터 거는 것이 좋습니다.
  5. GitHub 전용입니다. GitLab·Bitbucket을 쓰는 팀은 해당되지 않습니다.
  6. 비슷한 도구가 이미 있습니다. Trending Topics는 경쟁 도구로 GitHub Copilot 코드 리뷰, CodeRabbit, Cursor의 Bugbot 등을 꼽았습니다. Claude Ship의 차별점은 “승인"까지 맡긴다는 점인데, 바로 그 부분이 가장 신중해야 할 부분입니다.

나에게 맞는 선택

  • 입문자·학생: 개인 요금제에서는 쓸 수 없습니다. 대신 “AI 리뷰가 무엇을 잡고 무엇을 놓치는지"를 이해해 두면 좋습니다. 리뷰 의견을 그대로 받아들이지 말고, 왜 문제인지 직접 확인하는 습관이 더 중요해집니다.
  • 팀 개발자: 먼저 Code Review만 한 저장소에 붙여 보고, PR Steward는 수동으로 불러 써 보고, Claude Approvals는 관찰 전용 모드로 “AI라면 무엇을 승인했을지” 기록만 남겨 보는 순서가 보도된 권장 흐름과도 맞습니다.
  • 관리자·리드: 켜기 전에 ① 정책 파일 범위(문서·테스트만 허용 등 좁게 시작) ② 정책 파일 변경 시 사람 승인 필수 ③ 지출 한도 ④ 우리 조직이 제외 조건(ZDR·HIPAA·CMEK)에 해당하는지 ⑤ 브랜치 보호에서 AI 승인을 어떻게 셀지, 이 다섯 가지를 먼저 정하세요.

정리

Claude Ship은 “AI 코드 리뷰"에서 한 걸음 더 나가 수정과 승인까지 파이프라인으로 묶은 기능입니다. 반복적인 작은 변경이 많은 팀이라면 리뷰 대기 시간을 줄일 수 있지만, 공개된 효과 수치는 Anthropic 내부 측정뿐이고 승인 권한을 AI에 넘기는 만큼 정책 설계가 곧 보안입니다. 관찰 전용 모드로 충분히 지켜본 뒤 좁은 범위부터 여는 것이 현실적인 출발점입니다.
