비밀번호 관리자 1Password가 11월 25일(현지 시각) 보안 사고를 공개했습니다. 공격자가 직원 한 명의 회사 GitHub 계정을 손에 넣었고, 그 계정으로 비공개 저장소의 소스 코드를 복사한 뒤 CI/CD를 거쳐 백엔드 서비스에 악성 코드를 올려 일부 고객의 관리용 정보를 빼 갔습니다.

다행히 1Password는 고객의 금고(vault) 내용, 즉 저장된 비밀번호와 비밀 항목은 접근되지 않았다고 밝혔습니다. 그래도 이 사건은 “개발자 계정 하나가 어디까지 이어질 수 있는가"를 보여 주는 사례라, 1Password 사용자와 개발 조직 모두에게 볼 거리가 있습니다.

이 글은 1Password를 쓰는 분, 그리고 GitHub·CI/CD로 서비스를 배포하는 개발자·인프라 담당자, 공급망 보안을 공부하는 학생·취준생을 위한 정리입니다.

무슨 일이 있었나

아래 내용은 1Password 발표를 인용한 보도 3곳(The Hacker News, ITdaily, Android Central)에 공통으로 나온 내용을 중심으로 정리했습니다.

항목내용
침입 경로알 수 없는 공격자가 직원의 회사 GitHub 계정을 장악 (어떻게 탈취했는지는 공개되지 않음)
유출·악용비공개 저장소 소스 코드 복사, CI/CD 시스템 접근, 백엔드 서비스에 악성 코드 배포
빠져나간 고객 정보일부 고객의 이름·이메일, 계정·사용자 ID, 마지막 로그인 시각, 공개키, SRP 파라미터, 초대·계정 설정·복구 메일 링크에 담긴 토큰
안전하다고 밝힌 것금고 내용(비밀번호 등 저장 항목)
피해 규모“일부 고객"이라고만 밝힘, 정확한 수는 공개되지 않음
조사 시작11월 19일 수상한 활동을 조사하기 시작 (침입 시점 자체는 공개되지 않음)
공개11월 25일

핵심은 흐름입니다. 개발자 계정 → 소스 저장소 → 빌드·배포 파이프라인(CI/CD) → 운영 중인 백엔드 → 고객 데이터. 공격자는 서버를 직접 뚫지 않고, 서버에 코드를 내려 보내는 정상 통로를 탔습니다.

핵심 개념 먼저

  • CI/CD: 코드를 저장소에 올리면 자동으로 빌드·테스트(CI)하고 서버에 배포(CD)하는 파이프라인입니다. 편리한 만큼, 여기에 접근하면 운영 서버에 코드를 심을 수 있습니다.
  • 토큰(token): 비밀번호 대신 쓰는 접근 열쇠 문자열입니다. 보도에 따르면 1Password는 탈취된 토큰을 폐기했는데, 이 토큰이 어떻게 새어 나갔는지는 밝히지 않았습니다.
  • SRP(Secure Remote Password): 서버에 비밀번호 자체를 보내지 않고도 “비밀번호를 안다"는 것을 증명하는 로그인 방식입니다. 서버에는 검증용 값(파라미터)만 남습니다. 이번에 이 파라미터가 유출됐습니다.
  • 종단 간 암호화(E2EE): 데이터를 사용자 기기에서 암호화해 서버는 내용을 볼 수 없게 하는 방식입니다. 1Password 금고는 사용자만 가진 키로 암호화되므로, 서버 쪽이 뚫려도 금고 내용은 읽히지 않는다는 것이 1Password의 설명입니다.

유출된 정보, 얼마나 위험한가

유출된 정보의미1Password 설명 / 주의할 점
이름·이메일·계정 ID·로그인 시각누가 1Password를 쓰는지 알 수 있음맞춤형 피싱에 쓰일 수 있음
공개키원래 공개해도 되는 값단독으로는 금고를 열 수 없음
SRP 파라미터로그인 검증용 값금고를 여는 키는 사용자 기기에만 있음
메일 링크 속 토큰초대·설정·복구 링크의 일부토큰만으로는 못 쓰고, SSO 또는 등록 메일로 오는 6자리 코드가 추가로 필요

1Password는 예방 차원에서 초대·복구 메일의 코드를 6자리 숫자에서 10자리 문자로 늘렸습니다(두 매체는 영문·숫자 조합이라고 보도). 또 해당 GitHub 계정 비활성화, 내부 자격 증명 교체, GitHub·CI/CD·업무용 PC 통제 강화를 했다고 밝혔습니다. 노출된 토큰으로 계정이 탈취된 증거는 없다고 했습니다.

한계와 주의할 점

  • 공개되지 않은 것이 많습니다. 계정이 어떻게 탈취됐는지(피싱, 악성코드, 토큰 유출 등), 침입이 언제 시작됐는지, 영향받은 고객 수는 아직 나오지 않았습니다.
  • 알림 범위에 대한 보도가 엇갈립니다. 영향받은 사용자에게 개별 통지했다는 보도와, 모두에게 통지됐는지 불분명하다는 보도가 있습니다. 1Password 공식 발표를 직접 확인하세요.
  • “금고는 안전"은 설계에 근거한 주장입니다. 서버가 금고 키를 갖지 않는 구조라 설득력은 있지만, 백엔드에 악성 코드가 올라갔던 만큼 독립 조사 결과가 나오면 다시 확인할 필요가 있습니다. 보도에 따르면 외부 전문가가 조사에 참여하고 있습니다.

독자가 할 일

1Password 사용자라면

  1. 1Password 안내대로라면 마스터 비밀번호나 Secret Key를 바꿀 필요는 없습니다. 대신 피싱을 경계하세요. 이름·이메일이 유출된 만큼 “보안 사고로 계정 확인이 필요하다"는 식의 메일·문자·전화가 올 수 있습니다.
  2. 메일 속 링크로 로그인하지 마세요. 앱이나 직접 입력한 공식 주소로만 들어갑니다. 메일·전화로 계정 비밀번호나 Secret Key를 묻는다면 일단 의심하세요.
  3. 개별 통지 메일을 받았다면 그 안내를 따르되, 메일 속 링크 대신 앱에서 확인하세요.

GitHub·CI/CD를 운영하는 팀이라면 (이번 사건에서 꺼낼 수 있는 일반적인 점검 항목입니다)

  1. 개인 계정 하나로 운영 배포까지 가능한지 확인합니다. 배포 브랜치 보호 규칙, 필수 코드 리뷰, 배포 승인 단계가 있으면 한 계정만으로 운영에 코드를 올리기 어렵습니다.
  2. 토큰 수명과 권한을 줄입니다. 오래 쓰는 범용 토큰 대신, 저장소·권한을 좁힌 세분화된 토큰과 짧은 만료 기간을 씁니다.
  3. CI/CD에 저장된 비밀값(클라우드 키, 배포 키)을 점검합니다. 저장소 접근만으로 이 값들을 꺼낼 수 있는지 확인하세요.
  4. 감사 로그를 봅니다. 평소와 다른 위치·시간의 저장소 복제(clone), 토큰 생성, 워크플로 수정이 있었는지 알림을 걸어 둡니다.

정리

  • 1Password는 직원의 회사 GitHub 계정이 탈취돼 소스 코드와 일부 고객의 관리용 정보(이름·이메일·ID·공개키·SRP 파라미터·메일 링크 토큰)가 유출됐다고 밝혔습니다.
  • 금고 내용은 접근되지 않았다는 것이 회사 설명이고, 사용자에게는 피싱 주의 외에 별도 조치를 요구하지 않았습니다.
  • 개발 조직에게 남는 교훈은 “개발자 계정 = 운영 서버로 가는 열쇠” 라는 점입니다. 계정 하나, 토큰 하나로 배포까지 닿지 않도록 리뷰·승인·토큰 범위를 다시 보세요.
