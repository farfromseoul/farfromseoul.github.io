Red Hat Quay를 직접 운영한다면 지금 확인하세요 — 로그인 없이 레지스트리 서명 키를 바꿔치기하는 CVE-2026-123710

컨테이너 이미지 저장소 Red Hat Quay에서 익명 토큰만으로 신뢰 서명 키를 심어 모든 비공개 이미지를 읽고 덮어쓸 수 있는 결함(CVSS 9.8)이 고쳐졌습니다. 영향 범위, 고친 버전, 업데이트만으로 끝나지 않는 후속 점검을 정리합니다.

회사에서 Docker Hub 대신 사내 컨테이너 레지스트리를 쓴다면, 그 레지스트리는 빌드된 모든 이미지가 모이는 곳이자 배포 파이프라인이 매번 이미지를 받아 가는 곳입니다. 11월 11일(미국 기준) Red Hat이 공개한 Red Hat Quay 결함 CVE-2026-123710(CVSS 9.8)은 바로 이 레지스트리의 “열쇠"를 외부인이 바꿔 끼울 수 있게 하는 문제였습니다.

이 글은 Quay를 직접 설치해 운영하는 인프라·플랫폼 담당자, OpenShift를 쓰는 팀, 그리고 “컨테이너 레지스트리가 털리면 무슨 일이 생기나"가 궁금한 분을 위한 정리입니다.

이 글은 CVE 공식 기록(OpenCVE에 미러된 CVE/NVD 데이터), Red Hat 고객 포털의 공개 요약, SecurityWeek·The Hacker News 보도, Ostorlab 기술 분석을 교차 확인해 썼습니다. Red Hat의 상세 조치 문서는 구독자 전용이라 공개된 범위만 반영했습니다. (2026-11-14 확인 기준)

무슨 일이 있었나

  • 11월 11일: Quay 코드 저장소에 수정이 합쳐지고, CVE-2026-123710·CVE-2026-110697 두 건이 공개됐습니다. 두 건 모두 Red Hat 소속 연구자가 찾았습니다.
  • Red Hat은 Quay 3.9~3.18의 여덟 개 지원 브랜치에 고친 빌드와 보안 공지(RHSA) 8건을 냈습니다.
  • 11월 14일 확인 기준, 실제 공격에 쓰였다는 보고는 찾지 못했습니다. 다만 공격 방법이 이미 기술 분석으로 공개돼 있어 패치를 미룰 이유는 적습니다.

먼저 용어 몇 가지

  • 컨테이너 레지스트리: 컨테이너 이미지를 올리고(push) 내려받는(pull) 저장소입니다. Docker Hub가 대표적인 공개 레지스트리이고, Quay·Harbor 등은 회사가 직접 설치해 쓰는 레지스트리입니다.
  • Red Hat Quay / Project Quay: Red Hat이 만든 레지스트리입니다. 오픈소스판이 Project Quay, 상용 지원판이 Red Hat Quay, Red Hat이 직접 운영하는 클라우드 서비스가 quay.io입니다.
  • 서명 키(service key): Quay는 “이 사용자는 이 저장소를 받아 갈 수 있다” 같은 권한을 담은 토큰을 발급할 때 서버의 키로 서명합니다. 레지스트리는 신뢰 목록에 있는 키로 서명된 토큰이면 믿습니다.
  • 키 교체(key rotation): 오래된 서명 키를 새 키로 바꾸는 정상적인 운영 절차입니다. 이번 결함은 이 기능에서 나왔습니다.
  • 로봇 계정(robot account): CI/CD 파이프라인처럼 사람이 아닌 자동화 도구가 쓰는 계정입니다. 토큰 하나로 이미지를 올리고 받습니다.

무엇이 문제인가

CVE-2026-123710 — 서명 키 바꿔치기 (CVSS 9.8)

Quay의 키 관리 기능(/keys 경로)은 키를 교체하려는 요청에 “믿을 만한 키로 서명된 토큰"이 붙어 있는지 확인합니다. 그런데 그 토큰이 키 교체 용도로 발급된 것인지는 확인하지 않았습니다.

그 결과 공격 흐름이 이렇게 됩니다.

  1. 공격자가 레지스트리의 토큰 발급 경로(/v2/auth)에서 익명 토큰을 받습니다. 익명 접근은 Quay의 기본 설정에서 켜져 있습니다.
  2. 이 익명 토큰을 키 교체 요청에 붙여, 만료 기한이 없는 자기 공개키를 신뢰 목록에 올립니다. 이때 원래 서버 키는 지워집니다.
  3. 이제 공격자는 자기 키로 토큰을 직접 만들어, 모든 저장소의 비공개 이미지를 받고 덮어쓸 수 있습니다.

피해비공개 이미지와 그 안에 든 비밀값 유출, 이미지 바꿔치기(공급망 공격), 정상 키 삭제로 push·pull 마비
지속성심어진 키는 만료가 없고 재시작해도 남음
해당 배포 형태단독 설치(Podman·Docker), OpenShift의 Quay Operator, OpenShift용 mirror registry

특히 주의할 점은 비밀번호를 바꾸거나 로봇 토큰을 재발급해도 심어진 키는 사라지지 않는다는 것입니다(Red Hat 공개 요약). 키 자체를 찾아서 지워야 합니다.

CVE-2026-110697 — 다른 팀 로봇 토큰 엿보기 (CVSS 9.9)

같은 날 함께 공개된 두 번째 결함입니다. 로봇 계정 목록을 조회할 때, 네임스페이스(조직·사용자 이름) 문자열을 SQL LIKE 검색 패턴에 그대로 넣었습니다. LIKE에서 밑줄(_)은 “아무 글자 하나"를 뜻하기 때문에, 이름을 교묘하게 지은 네임스페이스로 조회하면 다른 팀의 로봇 계정과 복호화된 토큰까지 돌려받을 수 있었습니다.

  • 조건: 여러 팀(테넌트)이 한 Quay를 함께 쓰고, 공격자가 네임스페이스를 만들 수 있을 때
  • 피해: 빼낸 로봇 토큰으로 다른 팀 이미지를 읽고 덮어쓰기. OpenShift CI/CD에 악성 이미지를 끼워 넣는 데 쓰일 수 있음

  • Quay 5: Red Hat은 “영향 있음"으로 표시했지만, 11월 14일 확인 시점에 별도 수정 빌드 번호는 공개되지 않았습니다.
  • CVE-2026-110697의 수정 여부: Red Hat CVE 페이지는 같은 여덟 버전을 수정판으로 적었지만, 보안 공지 8건 본문에는 이 CVE가 빠져 있다는 보도가 있습니다. 같은 코드 수정에 함께 들어갔다는 보도도 있어, 업데이트 후 Red Hat 공지를 한 번 더 확인하는 것을 권합니다.
  • 오픈소스 태그: 기술 분석에 따르면 업스트림 최신 태그였던 v3.18.2에는 수정이 들어 있지 않습니다. 소스·커뮤니티 이미지로 운영한다면 태그 번호를 꼭 확인하세요.
  • quay.io: Red Hat 운영 클라우드는 이미 조치됐다고 알려졌습니다. quay.io만 쓰는 경우 직접 할 일은 없습니다.

업데이트 전 임시 조치와 업데이트 후 점검

업데이트만 하면 앞으로의 공격은 막히지만, 이미 심어진 키는 그대로 남습니다. 그래서 순서가 중요합니다.

  1. /keys 경로를 막는다: 프록시·로드밸런서에서 /keys를 내부 구성 요소 외에는 접근하지 못하게 차단합니다. (Red Hat 권고)
  2. 감사 로그를 확인한다: service_key_rotate, service_key_delete 이벤트 중 만료 기한(expiration_date)이 비어 있는 것, 그리고 모르는 키의 service_key_create 이벤트를 찾습니다.
  3. 모르는 키를 지운다: 관리자 화면·API에서 승인된 서비스 키 목록을 보고, 만료 없는 낯선 키를 삭제합니다. 1번 차단을 해 둔 상태에서 해야 합니다. 열려 있으면 다시 심을 수 있습니다.
  4. 수정 버전으로 올린다: 위 표의 버전 이상으로 업데이트합니다. 이것만이 근본 해결입니다.
  5. 로봇 토큰을 정리한다: 밑줄이 들어간 네임스페이스, 다른 이름과 겹칠 수 있는 네임스페이스의 로봇 토큰을 재발급하고, 평소와 다른 pull·push 기록이 있는지 봅니다.
  6. 불필요한 익명 접근은 끈다: 공개 이미지를 제공하지 않는다면 끄는 편이 좋습니다. 다만 이것만으로는 CVE-2026-123710을 막지 못합니다.

이 글에는 실행 명령어를 넣지 않았습니다. Red Hat의 상세 조치 절차가 구독자 전용 문서에 있어 공개 문서로 검증할 수 없었기 때문입니다. 실제 작업은 Red Hat 고객 포털의 해결 문서(7149923)와 사용 중인 버전의 공식 문서를 따르세요.

주의할 점

  • “내부망이니까 괜찮다"는 통하지 않습니다. Red Hat은 신뢰할 수 없는 사용자가 닿을 수 있는 모든 인스턴스, 즉 사내 레지스트리도 해당된다고 밝혔습니다. 사내 계정 하나만 탈취돼도 공격 조건이 됩니다.
  • 이미지 바꿔치기는 늦게 드러납니다. 레지스트리 이미지가 덮어써졌다면 그 이미지를 받아 간 서버·클러스터까지 영향을 받습니다. 중요한 이미지는 다이제스트(이미지 내용의 지문)로 고정해 배포하고 있는지, 서명 검증을 하는지 함께 점검할 기회로 삼으면 좋습니다.
  • 공식 상세 정보가 일부 비공개입니다. 이 글의 탐지 항목은 Red Hat 공개 요약과 언론·보안 업체 분석을 바탕으로 했습니다. 판단이 필요한 부분은 Red Hat 공식 문서를 우선하세요.

독자가 할 일

  • Quay를 운영한다: 오늘 /keys 차단 → 감사 로그·키 목록 점검 → 수정 버전 업데이트 → 로봇 토큰 정리 순서로 진행합니다.
  • OpenShift를 쓴다: Quay Operator나 mirror registry를 쓰는지부터 확인합니다. 클러스터 설치용 mirror registry도 해당됩니다.
  • quay.io만 쓴다: 조치는 필요 없습니다. 다만 쓰고 있는 로봇 토큰 권한이 지나치게 넓지 않은지 한 번 보는 것도 좋습니다.
  • 취준생·학생: “인증 토큰의 용도(audience·scope)를 확인하지 않으면 어떤 일이 생기는가"를 보여 주는 좋은 사례입니다. 서명이 맞는지만 보고 그 토큰이 무엇을 하라고 발급됐는지는 보지 않은 것이 핵심 원인입니다.

정리

  • Red Hat Quay에서 익명 토큰만으로 신뢰 서명 키를 심어 모든 비공개 이미지를 읽고 덮어쓸 수 있는 결함(CVE-2026-123710, 9.8)과, 다른 팀 로봇 토큰이 새는 결함(CVE-2026-110697, 9.9)이 공개됐습니다.
  • 수정 버전은 3.9.28 / 3.10.28 / 3.12.24 / 3.14.10 / 3.15.9 / 3.16.7 / 3.17.7 / 3.18.3입니다. Quay 5는 수정 빌드 번호가 아직 나오지 않았습니다.
  • 업데이트만으로는 끝나지 않습니다. 이미 심어진 키는 직접 찾아 지워야 하고, 그 작업은 /keys를 막아 둔 상태에서 해야 합니다.
