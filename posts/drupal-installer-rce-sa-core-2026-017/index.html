Drupal 보안팀이 2026년 11월 18일(UTC) 코어 보안 권고 두 건을 냈습니다. 그중 SA-CORE-2026-017(CVE-2026-132165)은 위험도 치명적(Critical), 25점 만점에 18점으로, 설치가 끝난 사이트에 남아 있는 설치 프로그램 install.php를 이용해 사이트를 다시 설치하려 시도할 수 있고, 그 결과 사이트 장악이나 원격 코드 실행까지 이어질 수 있다는 내용입니다.

수정 버전은 10.6.22 · 11.3.22 · 11.4.13 입니다. 업데이트와 함께, 이번 기회에 웹 서버에서 설치 경로 자체를 막아 두는 것이 Drupal 공식 문서의 권고입니다.

Drupal 공식 권고(SA-CORE-2026-017·018)와 공식 문서 「Securing the installer」를 직접 확인했고, 토론토대 정보보안팀 공지·TheDropTimes·Cyber Kendra 보도로 교차 확인했습니다. 한 곳에만 나온 내용은 넣지 않거나 그렇다고 표시했습니다. (2026-11-21 확인 기준)

무슨 일이 있었나

  • 11월 16일: Drupal 보안팀이 사전 공지(PSA-2026-11-16)로 “11월 18일에 치명적 등급 코어 릴리스가 나온다"고 예고했습니다. 공지에는 익명 사용자도 악용할 수 있는 문제가 있고, 공격 코드가 수 시간~수일 안에 나올 수 있다는 경고가 담겼습니다.
  • 11월 18일: 지원 중인 세 브랜치에 수정 버전이 나왔고, 권고 두 건이 공개됐습니다.
    • SA-CORE-2026-017 — 설치 프로그램 원격 코드 실행, 치명적 18/25, CVE-2026-132165
    • SA-CORE-2026-018 — 가젯 체인(gadget chain), 보통 이상(Moderately critical) 14/25, CVE-2026-132166
  • 017 취약점은 Drupal 보안팀 등과 함께 Anthropic의 오픈소스 스캐너가 찾은 것으로 권고문 제보자 명단에 적혀 있습니다.
  • 2026-11-21 확인 시점까지 실제 공격에 쓰였다는 보고는 없습니다. 다만 권고의 악용 단계 표기가 E:Proof(개념 증명 코드 존재)라서, 공개된 공격 코드가 나오는 건 시간문제로 보는 게 안전합니다.

핵심 개념 먼저

  • Drupal: PHP로 만든 오픈소스 CMS(콘텐츠 관리 시스템)입니다. 정부·대학·언론사 사이트에서 많이 씁니다.
  • install.php: 처음 사이트를 만들 때 브라우저로 여는 설치 마법사입니다. 설치가 끝난 뒤에도 코어 파일로 그대로 남아 있습니다. 이번 문제의 출발점이 바로 이것입니다.
  • settings.php: DB 접속 정보 같은 사이트 설정이 들어 있는 파일입니다. 웹 서버가 이 파일을 고쳐 쓸 수 있으면 공격 경로가 넓어집니다.
  • Drupal 위험도 점수: Drupal은 CVSS 대신 자체 기준(공격 난이도, 필요한 권한, 기밀성·무결성 영향, 악용 코드 여부, 영향받는 설정 비율)을 더해 25점 만점으로 매깁니다.
  • 가젯 체인: 그 자체로는 공격이 안 되지만, 다른 취약점으로 unserialize()(저장된 데이터를 PHP 객체로 되살리는 함수)에 위험한 입력을 넣을 수 있을 때 코드 실행으로 이어 주는 “부품 조합"입니다.

어떤 조건에서 위험한가

권고문은 공격 세부 내용을 밝히지 않고 “특정 조건에서” 설치 프로그램으로 재설치를 시도할 수 있다고만 적었습니다. 확인된 범위는 이렇습니다.

  • 설치가 끝난 사이트에서 /core/install.php가 외부에서 열리는 상태가 전제입니다.
  • 웹 서버 계정이 settings.php를 쓰거나 권한을 바꿀 수 없으면 일부 공격 경로는 막힌다고 권고문이 밝혔습니다. 반대로 말하면 설정 파일 권한이 느슨한 사이트일수록 위험합니다.
  • 토론토대 공지에 따르면 Drupal 기본 .htaccess는 설치 프로그램을 막지 않습니다(한 곳에서만 확인한 내용).

한계와 주의할 점

  • 공격 조건이 완전히 공개되지 않았습니다. “우리 사이트는 해당 없다"고 스스로 판단하기보다 업데이트와 경로 차단을 둘 다 하는 편이 낫습니다.
  • Drupal Steward(Drupal 보안팀과 연계된 웹 방화벽 서비스)를 쓰는 사이트는 알려진 공격 경로가 막힌다고 권고문이 밝혔지만, 업데이트는 여전히 필요하다고 덧붙였습니다.
  • nginx에서 정확히 일치(location =)로 막으면 안 됩니다. 일부 보안 공지 예시에 이 형태가 있는데, Drupal 공식 문서는 .php/ 뒤에 경로를 붙인 주소(/core/install.php/foo)가 빠져나갈 수 있다며 접두사 일치(^~)를 쓰라고 명시합니다.
  • 설치 경로를 막아도 update.php(DB 업데이트)는 막지 마세요. 공식 문서가 넓은 규칙으로 함께 막지 말라고 경고합니다.
  • 새 사이트를 브라우저 설치 마법사로 만들 수 없게 되므로, 이후 새 사이트는 Drush(drush site:install, install.php를 쓰지 않음)로 설치하라는 것이 공식 문서 안내입니다.

지금 할 일

1. 코어 업데이트

사이트 버전을 확인하고 10.6.22 · 11.3.22 · 11.4.13 중 맞는 버전으로 올립니다. 지원이 끝난 브랜치(11.2 이하, 10.5 이하)라면 이번 패치를 받을 수 없으니, 아래 2번으로 우선 막고 지원 버전 업그레이드 일정을 잡으세요.

2. 웹 서버에서 install.php 막기 (공식 권장 방법)

Drupal 공식 문서 「Securing the installer」의 1순위 방법입니다. 웹 서버 설정이라 코어를 업데이트해도 유지됩니다.

Apache — .htaccess가 아닌 서버(가상 호스트) 설정에 넣습니다. <Location>을 .htaccess에 넣으면 500 오류가 납니다. HTTPS 가상 호스트를 포함해 사이트를 서비스하는 모든 가상 호스트에 추가하세요.

<Location "/core/install.php">
  Require all denied
</Location>

바꾼 뒤에는 apachectl configtest로 문법을 확인하고 다시 불러옵니다.

nginx — HTTPS server 블록 안에 넣습니다. 접두사 일치(^~)를 쓰는 것이 핵심입니다.

location ^~ /core/install.php {
  return 404;
}

웹 서버 설정을 바꿀 수 없는 공유 호스팅(Apache)이라면 공식 문서의 2순위 방법인 웹 루트 .htaccess 추가를 쓸 수 있습니다. 다만 Composer로 관리하는 사이트는 composer install 때 .htaccess가 덮어써지므로, 공식 문서의 scaffold append 설정 안내를 함께 따라야 합니다.

<Files "install.php">
  Require all denied
</Files>

3. 막혔는지 확인

공식 문서에 나온 확인 명령입니다. example.com을 내 도메인으로 바꿔 실행하고, 셋 다 403 또는 404로 끝나야 합니다. 200이 나오면 차단이 안 된 것입니다.

curl -I https://example.com/core/install.php
curl -IL https://example.com/install.php
curl -I https://example.com/core/install.php/foo

확인 후 사이트가 정상 동작하는지, drush updatedb나 /update.php가 그대로 되는지도 봅니다.

4. settings.php 권한 점검

웹 서버 계정이 settings.php와 그 폴더(sites/default)를 쓸 수 없게 되어 있는지 확인합니다. 권고문이 이 조건에서 일부 공격 경로가 막힌다고 밝혔습니다.

5. 호스팅 업체 확인

공식 문서는 일부 호스팅 업체가 이미 설치 프로그램을 막아 두었을 수 있으니 확인해 보라고 안내합니다. 그래도 3번 확인 명령으로 직접 검증하는 것이 확실합니다.

정리

  • Drupal 코어의 설치 프로그램 install.php를 이용해 익명 공격자가 사이트를 다시 설치·장악할 수 있는 치명적(18/25) 취약점이 고쳐졌습니다.
  • 10.6.22 · 11.3.22 · 11.4.13으로 올리고, 지원 종료 브랜치는 업그레이드 계획을 세우세요.
  • 업데이트와 별개로 웹 서버에서 /core/install.php를 막고(nginx는 ^~ 접두사 일치), curl로 403/404가 나오는지 확인하세요.
  • 같은 날 나온 가젯 체인(018)은 단독으로는 위험하지 않지만, 같은 업데이트로 함께 해결됩니다.
