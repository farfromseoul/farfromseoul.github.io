AWS 공식 로컬 에뮬레이터 출시 — 계정 없이 내 PC·CI에서 S3·DynamoDB 테스트하기

AWS가 자기 서비스를 로컬에서 흉내 내는 무료 오픈소스 도구 'AWS Emulator'를 내놓았습니다. 설치·연결 방법, 기존 코드를 거의 그대로 쓰는 원리, 그리고 IAM 정책을 검사하지 않는 등 꼭 알아야 할 한계를 정리합니다.

AWS로 서비스를 만들어 본 사람이라면 한 번쯤 겪는 고민이 있습니다. “S3에 파일 올리는 코드 한 줄 고쳤는데, 확인하려면 진짜 AWS에 배포해야 하나?” 테스트용 계정을 따로 만들고, 요금이 나올까 걱정하고, CI(코드를 올릴 때마다 자동으로 빌드·테스트하는 파이프라인)에 접근 키를 넣는 일까지 따라옵니다.

AWS가 2026년 11월 11일, 이 문제를 직접 겨냥한 공식 도구 AWS Emulator를 공개했습니다. 내 컴퓨터나 CI 안에서 AWS 서비스를 흉내 내는 프로그램입니다. GeekNews에서도 “AWS가 마침내 자체 에뮬레이터를 만들었다"는 제목으로 화제가 됐습니다.

이 글은 AWS를 처음 배우는 학생·취준생과, 클라우드 연동 코드를 테스트하는 실무 개발자를 위한 정리입니다.

AWS 뉴스 블로그 발표 글, AWS What’s New 공지, SD Times 보도를 교차 확인해 썼습니다(2026-11-13 확인 기준). 본문 명령어는 모두 AWS 공식 블로그에 실린 그대로이며, 글쓴이가 직접 실행해 보지는 않았습니다.

무슨 일이 있었나

  • 무엇: AWS 서비스 API를 로컬에서 흉내 내는 에뮬레이터. Rust로 작성됐습니다.
  • 가격: 별도 요금 없음. 실제 AWS에 배포할 때만 그 자원 요금이 나옵니다.
  • 라이선스: 소스 코드는 CC0 1.0(저작권을 사실상 포기하는 퍼블릭 도메인 선언)으로 공개됐습니다.
  • 소스: GitHub aws/aws-emulator, 호환성 테스트는 aws/aws-emulator-evaluation-suite.
  • 눈에 띄는 점: AWS는 이 도구를 AI 에이전트들이 만들고 유지보수한다고 밝혔습니다(자세한 내용은 아래).

먼저 용어 몇 가지

  • 에뮬레이터(emulator): 진짜 시스템과 같은 방식으로 요청을 받고 응답하도록 흉내 내는 프로그램입니다. 진짜 AWS 대신 “가짜 AWS"를 띄운다고 생각하면 됩니다.
  • 엔드포인트(endpoint): 프로그램이 요청을 보내는 주소입니다. 평소에는 s3.amazonaws.com 같은 AWS 주소인데, 이것을 내 컴퓨터 주소로 바꾸면 요청이 에뮬레이터로 갑니다.
  • SDK·CLI: SDK는 코드에서 AWS를 부르는 라이브러리(boto3, AWS SDK for Java 등), CLI는 터미널에서 쓰는 aws 명령입니다.
  • SigV4: AWS 요청에 붙이는 서명 방식입니다. 누가 보낸 요청인지 증명하는 용도입니다.
  • API 모델(Smithy 모델): AWS가 각 서비스의 요청·응답 형식을 기계가 읽을 수 있게 적어 둔 명세서입니다. 에뮬레이터는 이 명세를 바탕으로 만들어졌습니다.

어떻게 동작하나

핵심은 코드를 고치지 않고 주소만 바꾼다는 점입니다. 이미 쓰고 있는 SDK·CLI 호출이 환경 변수 몇 개로 로컬 에뮬레이터를 향하게 됩니다.

항목내용
접속 주소https://127.0.0.1:9297 (HTTPS, 내 컴퓨터에서만 접근 가능)
자동 생성 파일첫 실행 시 ~/.aws/emulator/9297/에 자격 증명·설정 파일·인증서 생성
계정단일 계정 000000000000 고정
접근 키EMULATOR로 시작하는 키만 허용, 그 외 키로 서명한 요청은 거부
상태 저장메모리에 보관, 에뮬레이터를 끄면 사라짐
리전리전에 의존하지 않음
미구현 기능501 Not Implemented 응답

지원 범위에 대해 AWS는 “API 모델이 공개된 서비스의 API를 지원한다"고 설명합니다. 다만 서비스마다 얼마나 똑같이 동작하는지는 차이가 있어서, 릴리스마다 **충실도 보고서(fidelity report)**에 “서비스별 테스트 n개 중 k개 통과” 형태로 점수를 공개합니다. 쓰려는 서비스가 있다면 이 보고서부터 확인하는 것이 좋습니다.

시작하는 방법 (공식 블로그 기준)

1. 설치

리눅스(RPM 계열)에서는 패키지로 설치합니다. 아래는 AWS 블로그에 실린 명령 그대로입니다.

PKG=https://downloads.aws.com/aws-emulator/packages/aws-emulator/LTS/latest
sudo dnf install -y $PKG/aws-emulator-x86_64.rpm

aws-emulator -v
  • 데비안 계열용 패키지도 있습니다.
  • macOS·Windows는 아직 설치 패키지가 없습니다. 공식 문서의 Dockerfile로 이미지를 직접 빌드해 컨테이너로 띄우는 방식입니다(미리 만들어진 공식 이미지는 없음).
  • 소스에서 직접 빌드할 수도 있습니다.

2. 실행

aws-emulator

로그는 한 줄에 하나씩 JSON 형식으로 나옵니다.

3. CLI·SDK를 에뮬레이터로 연결

새 터미널에서 아래 환경 변수를 설정합니다. 마지막 줄은 실제 AWS 자격 증명이 섞여 들어가지 않도록 기존 값을 지우는 부분입니다.

export AWS_ENDPOINT_URL=https://127.0.0.1:9297
export AWS_SHARED_CREDENTIALS_FILE=~/.aws/emulator/9297/emulator_credentials
export AWS_CONFIG_FILE=~/.aws/emulator/9297/config
export AWS_EC2_METADATA_DISABLED=true
export AWS_DISABLE_HOST_PREFIX_INJECTION=true
export AWS_REGION=us-east-1
export AWS_DEFAULT_REGION=us-east-1
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN AWS_PROFILE

4. 연결 확인

curl --cacert ~/.aws/emulator/9297/ca.pem https://127.0.0.1:9297/__admin/health

aws sts get-caller-identity

두 번째 명령 결과에 계정 번호 000000000000이 보이면 에뮬레이터에 붙은 것입니다. 실제 계정 번호가 나오면 환경 변수가 적용되지 않은 것이니 다시 확인하세요.

AWS SDK for Java처럼 일부 SDK는 에뮬레이터가 만든 인증서를 신뢰하도록 트러스트 스토어(믿을 수 있는 인증서 목록)를 따로 설정해야 합니다.

테스트 코드 안에서 띄우기 (Rust)

Rust에서는 aws-emulator-embedded 크레이트를 개발 의존성으로 추가하면 테스트 프로세스 안에서 에뮬레이터를 띄울 수 있습니다. 인스턴스마다 상태가 따로라서 병렬 테스트끼리 버킷·테이블·큐가 섞이지 않습니다. 다른 언어용 내장 모드는 발표 글에 언급되지 않았습니다.

AI 에이전트가 만든 도구라는 점

AWS 블로그는 이 에뮬레이터를 AWS API 모델을 바탕으로 에이전트들이 만들고 유지보수한다고 설명합니다. 구조를 요약하면 이렇습니다.

역할하는 일
차이 찾기 에이전트에뮬레이터 동작을 실제 AWS·API 모델과 비교해 다른 점을 이슈로 등록
구현 에이전트이슈를 고치고 테스트 작성
보안 에이전트변경 사항을 공격자 관점에서 따로 검토
병합 관문컴파일·코딩 규칙·보안·충실도 하락 여부를 확인한 뒤에만 병합

SD Times는 여기서 더 나아가 사람이 코드를 작성하거나 리뷰하지 않았다고 보도했습니다. 코드는 AWS 내부 저장소에서 빌드·재시험을 거친 뒤 마지막 단계에서 GitHub에 공개된다고 합니다.

이 점은 양쪽으로 읽힙니다. 공식 API 명세와 실제 AWS 비교 테스트로 품질을 관리하는 방식은 흥미로운 사례이지만, 사람이 리뷰하지 않은 코드라는 점이 마음에 걸린다면 로컬·CI 테스트 용도로만 쓰고 운영 환경 근처에는 두지 않는 편이 안전합니다. 다행히 접속 주소가 기본으로 127.0.0.1이라 외부에서 붙을 수 없게 돼 있습니다.

한계와 주의할 점

공식 발표 글이 직접 밝힌 한계입니다.

  1. IAM 정책을 검사하지 않습니다. AWS에서는 권한 부족으로 거부될 요청이 로컬에서는 성공할 수 있습니다. “로컬에서 됐으니 배포해도 된다"가 권한 문제에서는 통하지 않습니다.
  2. 계정·리전이 하나뿐입니다. 교차 계정 접근, 리전 간 복제 같은 동작은 테스트할 수 없습니다.
  3. 보안 테스트 용도로는 맞지 않습니다. AWS가 직접 “애플리케이션 보안 테스트에는 적합하지 않다"고 적었습니다.
  4. 서비스마다 충실도가 다릅니다. 미구현 기능은 501을 돌려주므로, 테스트가 501로 실패하면 내 코드 문제가 아니라 에뮬레이터 미지원일 수 있습니다.
  5. 익명 사용 데이터를 기본으로 보냅니다. 끌 수 있으니, 회사 CI에 넣기 전에 공식 문서의 비활성화 방법을 확인하세요.
  6. SAM·CDK·Terraform 연동은 발표 글에 언급이 없습니다. 이런 도구와 함께 쓰려면 공식 문서와 GitHub 이슈를 먼저 확인하는 것이 좋습니다.

기존에도 LocalStack 같은 서드파티 로컬 AWS 도구가 있었습니다. 이번 발표는 AWS가 직접 만든 도구라는 점이 다르지만, 이미 다른 도구로 테스트 환경을 잘 갖춘 팀이라면 당장 갈아탈 이유는 크지 않습니다. 쓰는 서비스의 충실도 점수와 필요한 연동 기능을 비교해 보고 정하는 것을 권합니다.

이런 분이라면해 볼 일
AWS를 공부하는 학생·취준생계정·요금 걱정 없이 S3·DynamoDB API를 CLI로 연습. 단, IAM 권한 설계는 실제 AWS에서 따로 익혀야 함
사이드 프로젝트 개발자개발 중에는 AWS_ENDPOINT_URL만 바꿔 로컬에서 돌리고, 배포 전에 실제 AWS에서 한 번 더 확인
CI를 관리하는 실무 개발자통합 테스트 일부를 에뮬레이터로 옮겨 접근 키 없이 돌릴 수 있는지 검토. 텔레메트리 설정과 충실도 보고서 먼저 확인
보안·권한 테스트 담당이 도구로는 IAM·리소스 정책 검증이 안 되므로 기존 방식 유지

정리

  • AWS가 무료 오픈소스(CC0) 로컬 에뮬레이터 AWS Emulator를 11월 11일 공개했습니다.
  • 환경 변수로 엔드포인트만 바꾸면 기존 SDK·CLI 코드가 https://127.0.0.1:9297의 에뮬레이터로 향합니다.
  • 리눅스는 패키지로, macOS·Windows는 직접 빌드한 Docker 이미지로 씁니다.
  • IAM 정책 미검사, 단일 계정·리전, 서비스별 충실도 차이는 꼭 기억해야 합니다. 로컬 테스트는 빠른 확인용이고, 배포 전 실제 AWS 검증을 대신하지는 못합니다.
  • AI 에이전트가 만든 코드라는 점이 특징이자 고려할 점입니다.
