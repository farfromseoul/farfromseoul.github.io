AI 에이전트 기억, 많이 적을수록 손해: Anthropic이 실험으로 보여 준 메모리 설계 7원칙

Anthropic이 에이전트 메모리를 대화 기록·메모·위키·주입 컨텍스트 네 층으로 나누고, 쉬는 시간에 기억을 고치는 '드리밍' 실험 결과를 공개했습니다. 수치와 함께 에이전트·코딩 도구를 쓰는 개발자가 바로 적용할 원칙을 정리합니다.

2026년 11월 6일(미국 시간), Anthropic 엔지니어링 블로그에 **「에이전트 메모리의 구성 요소(The components of agent memory)」**라는 글이 올라왔습니다. GeekNews 상단에도 소개됐죠. 핵심만 먼저 정리하면 이렇습니다.

  • 에이전트 메모리를 네 개의 층(대화 기록 → 메모 → 위키 같은 구조 → 매 세션 주입되는 컨텍스트)으로 나눠 봅니다.
  • 쉬는 시간에 기록을 다시 읽고 잘못된 기억을 고치는 과정을 “드리밍(dreaming)“이라 부르고, 실제로 성능이 오른다는 실험을 보여 줍니다.
  • 가장 눈에 띄는 결론: 많이 적는 에이전트가 더 잘하는 게 아니다. 꼭 필요한 것만 적은 모델이 훨씬 멀리 갔습니다.

먼저 밝혀 둡니다. 이 초안은 Anthropic의 AI 모델(Claude Opus 5.5)이 작성했고, 다루는 글도 Anthropic의 연구 글입니다. 아래 수치는 모두 Anthropic이 직접 실험해 발표한 값이며 외부 검증 전입니다.

먼저 용어 몇 가지

  • 에이전트(agent): 질문에 답만 하는 게 아니라 파일을 읽고, 명령을 실행하고, 여러 단계를 스스로 이어 가는 AI 프로그램.
  • 컨텍스트 윈도(context window): 모델이 한 번에 볼 수 있는 글의 양. 넘치면 오래된 내용부터 잘라 내야 합니다.
  • 컴팩션(compaction): 대화가 길어지면 앞부분을 요약해 자리를 비우는 것. 이번 글은 이것을 “메모리"에 넣지 않습니다.
  • 트랜스크립트(transcript): 세션에서 오간 대화와 도구 호출을 그대로 남긴 기록.
  • 주입 컨텍스트(injected context): 세션이 시작될 때마다 자동으로 앞에 붙는 내용. Claude Code의 CLAUDE.md, MEMORY.md가 대표적입니다.
  • 드리밍(dreaming): 일이 없을 때 쌓인 기록을 다시 훑어 메모를 고치고 정리하는 오프라인 작업. 사람이 잠자는 동안 해마(단기 기억)의 경험을 신피질(장기 기억)로 옮긴다는 비유에서 왔습니다.

무슨 내용인가: 메모리의 네 층

Anthropic은 “세션이 끝나도 남아서, 다음에 읽을 수 있는 형태로 쌓이는 지식"만 에이전트 메모리로 봅니다. 모델 가중치를 바꾸는 학습이나 한 대화 안에서의 학습은 빼고요.

층 (아래→위)무엇인가특징
1. 트랜스크립트세션 전체 기록가장 정확한 원본. 검색해서 씀
2. 메모에이전트가 “이건 기억해 두자” 하고 파일에 적은 것그때그때 쌓여서 중복·모순이 생기기 쉬움
3. 표현(위키 등)서로 링크된 문서 묶음아는 것을 지도처럼 정리. 꾸준히 손봐야 함
4. 주입 컨텍스트매 세션 자동으로 읽히는 내용작아야 함. 길수록 비용이 들고 지시를 덜 따름

드리밍은 이 층들 사이를 오가며 일합니다. 메모를 트랜스크립트와 대조해 틀린 것을 고치고, 메모를 모아 위키를 만들고, 중요한 것만 위층으로 올립니다.

자세히: 실험에서 나온 숫자

1. 메모리를 주면 얼마나 좋아지나

데이터를 찾아 질문에 답하는 과제(CL-Bench 1.0 데이터베이스 과제)에서, 답을 맞힌 뒤 정답을 보여 주고 메모를 남기게 했습니다. 점수는 평균 보상(1이 만점)입니다.

모델메모리 없음메모리 있음
Opus 5.50.6550.838
Opus 50.5640.828
Opus 4.70.3830.700
Sonnet 4.60.3300.364

오래된 모델일수록 메모리를 줘도 덜 활용했습니다. 글에 따르면 Sonnet 4.6은 기억을 먼저 읽고 가설을 시험하라고 자세히 지시하자 0.641까지 올랐습니다. 반대로 최신 모델은 알아서 규칙·검증 방법·함정을 기록했다고 합니다.

2. 많이 적는 게 답이 아니다 (포켓몬 레드 실험)

모델메모 파일쓴 글자 수(약)결과
Sonnet 3.7413개 (폴더 225개)97만 8천 자배지 1개
Fable 510개4만 3천 자배지 4개

Sonnet 3.7은 거의 모든 것을 적었고, 그 기록이 금세 낡았습니다. 어느 순간엔 게임은 하지 않고 파일 정리만 하기도 했다네요. Fable 5는 화면만 봐서는 알 수 없는 것(전략, 계획, 시험해 본 규칙)만 적었습니다. Opus 5.5도 작은 메모 묶음으로 게임을 끝까지 깼다고 합니다.

3. 규칙을 강요하면 오히려 손해

“실패만 기록하라” 같은 고정 규칙을 주자 메모리 효과가 줄었습니다. 줄어든 폭은 Opus 5가 0.234, Opus 4.7이 0.150으로 강한 모델일수록 컸습니다. 글의 권고는 메모리가 무엇을 위한 것인지를 알려 주고, 어떻게 쓸지는 모델에 맡기라는 것입니다.

4. 드리밍이 틀린 기억을 고친다

포켓몬 실험에서 일부러 “포켓몬센터가 산 반대편에 있다"는 틀린 메모를 넣었더니, 에이전트는 같은 낭떠러지에서 세 번 떨어졌습니다. 드리밍으로 메모를 기록과 대조해 고치자 다음 목적지에 도착했고, 고치지 않은 실행은 엉뚱한 곳으로 되돌아갔습니다. 틀린 메모 하나가 매 세션 따라다니며 발목을 잡는다는 점을 보여 주는 예입니다.

5. 위키는 검색을 보완한다, 대신하지는 못한다

약 35만 개 파일(약 4억 2천만 토큰) 코드·문서 묶음에 대한 25개 질문으로 시험했습니다.

방식정확도
검색만53%
위키만 (드리밍 2회 → 128회)13% → 48%
위키 + 검색 (128회 후)61% (질문당 약 2만 토큰 절약)

위키만으로는 검색을 못 이겼지만, 둘을 함께 쓰면 정확도와 비용이 모두 나아졌습니다. 다만 어떤 과제에서는 위키가 원본보다 1.77배 커져서 정리 효과가 거의 없었다고 합니다. 원본만큼 큰 지도는 쓸모가 없다는 얘기죠.

6. 여러 에이전트가 한 파일을 같이 쓰면 사고가 난다

계약서 정보를 여러 에이전트가 표 하나에 함께 적게 했더니 서로 덮어써서 채점 대상 57개 사실 중 41개(72%)만 남았습니다. 계약서마다 페이지를 따로 두고 핵심 조건을 원문 그대로 옮기게 하자 57개가 모두 보존됐습니다.

실제 제품에선 어떻게 쓰이나

제품메모리 관련 기능메모
Claude Code자동 메모리(~/.claude/projects/<프로젝트>/memory/MEMORY.md)시작할 때 MEMORY.md의 앞 200줄 또는 25KB까지만 읽음. 나머지는 주제별 파일로 두고 필요할 때 읽음
Claude Managed Agents메모리 스토어, DreamsDreams는 리서치 프리뷰(신청 필요). 세션 1~100개를 넣으면 정리된 새 메모리 스토어를 만들고 원본은 건드리지 않음
Claude API메모리 도구(memory tool)모델이 메모리 저장소에 쓰고 읽는 도구

Claude Code 공식 문서에 나온 조작법은 이 정도입니다. 세션에서 /memory를 입력하면 불러온 CLAUDE.md와 자동 메모리 폴더를 보고 편집하거나 자동 메모리를 끌 수 있고, 설정의 autoMemoryEnabled: false 또는 환경 변수 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1로도 끌 수 있습니다. 문서는 CLAUDE.md도 파일당 200줄 안쪽으로 유지하라고 권합니다.

한계와 주의할 점

  • 회사 자체 실험입니다. CL-Bench, 포켓몬, 위키 실험 모두 Anthropic이 설계·측정했고, 비교 대상도 자사 모델뿐입니다. 다른 회사 모델이나 여러분의 업무에서도 같은 결과가 나온다는 보장은 없습니다.
  • 드리밍은 공짜가 아닙니다. 기록을 다시 읽는 만큼 토큰 비용이 들고, Managed Agents의 Dreams는 세션 수와 길이에 비례해 비용이 늘어납니다. 모든 기억을 계속 점검하는 건 현실적이지 않다고 글도 인정합니다.
  • 메모는 읽혀도 지켜진다는 보장이 없습니다. 주입 컨텍스트가 길어질수록 지시를 덜 따른다는 점을 글에서도 짚습니다.
  • 틀린 메모는 오래 갑니다. 처음부터 틀렸거나, 환경이 바뀌어 낡은 메모가 매 세션 따라붙을 수 있습니다.
  • 보안·개인정보. 자동 메모리는 평문 마크다운 파일입니다. 에이전트가 토큰·비밀번호·고객 정보를 “기억해 둘 만한 것"으로 적지 않았는지 가끔 열어 봐야 합니다. Dreams는 데이터 무보존(ZDR)·HIPAA 대상이 아니라고 문서에 적혀 있으니 민감한 세션은 넣기 전에 확인하세요.

독자가 할 일

  1. MEMORY.md와 CLAUDE.md를 열어 보세요. 200줄이 넘었다면 세부 내용은 주제별 파일로 옮기고, 맨 위 파일은 목차처럼 링크만 남깁니다.
  2. “무엇을 기억할지” 목적을 적어 주세요. “실패만 적어라” 같은 규칙 대신 “다음에 같은 실수를 안 하도록, 화면·코드만 봐서는 알 수 없는 것을 적어라"처럼 목적을 말합니다.
  3. 메모의 근거를 남기게 하세요. 규칙만 적지 말고 어떻게 확인했는지 함께 적게 하면, 나중에 틀렸을 때 고치기 쉽습니다.
  4. 여러 에이전트를 돌린다면 파일을 나누세요. 한 표를 같이 고치게 하지 말고 대상별 페이지를 따로 둡니다.
  5. 정기적으로 메모를 점검하세요. 드리밍을 쓰지 않더라도, 바뀌기 쉬운 정보(버전, 경로, 담당자) 위주로 주기적으로 다시 확인하는 습관이 같은 효과를 냅니다.
  6. 비밀값이 메모에 들어가지 않았는지 확인하세요.

정리

이번 글의 메시지는 단순합니다. 에이전트의 기억은 창고가 아니라 지도여야 합니다. 원본 기록은 검색할 수 있게 그대로 두고, 그 위에 꼭 필요한 것만 짧게 정리하고, 틀린 기억은 주기적으로 원본과 대조해 고칩니다. 그리고 매 세션 읽히는 맨 위층은 최대한 작게 유지합니다. 사람이 쓰는 개인 노트나 팀 위키에도 그대로 적용되는 원칙이라, AI 에이전트를 쓰지 않는 분에게도 생각해 볼 만한 내용입니다.
