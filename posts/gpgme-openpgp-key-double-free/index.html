요점은 간단합니다. 아주 긴 사용자 ID를 넣어 조작한 OpenPGP 키 하나를 앱이 읽기만 해도 메모리 이중 해제가 일어날 수 있고, 공지는 이를 이용해 앱의 데이터를 빼낼 수 있으며 원격 코드 실행(RCE)도 배제할 수 없다고 밝혔습니다. GPGME는 메일 클라이언트, XMPP 메신저, Samba, Flatpak처럼 우리가 매일 쓰는 소프트웨어 안에 들어 있습니다.

무슨 일이 있었나

항목내용 (공식 공지 기준)
식별자CVE-2026-129975, GnuPG 이슈 T8557
공개일2026-11-20
영향GPGME 2.3.0 이전 모든 버전 (공유 라이브러리·DLL·정적 링크 모두)
수정 버전GPGME 2.3.1 (2.3.0은 공개 배포된 적 없음)
원인상태 줄·키 목록을 읽는 내부 함수 2곳의 이중 해제
영향데이터 유출 가능, 원격 코드 실행 배제 못 함
CVSS 점수공지에 없음
실제 악용 여부공지에 언급 없음
발견자Johan Carlsson (GitLab을 통해 11월 12일 전달)

원래 공개 예정일은 11월 25일이었는데, GitLab이 별개의 “Ruby2Shell” 버그 때문에 일정을 앞당겨 업데이트해야 했고, 그래서 GnuPG도 11월 20일에 공지를 앞당겨 냈다고 설명합니다. 수정 커밋 메시지에는 24년 묵은 버그라는 표현이 들어 있습니다.

핵심 개념 먼저

  • GnuPG(gpg): 메일·파일을 암호화하고 전자서명하는 오픈소스 도구입니다. OpenPGP라는 표준을 구현합니다.
  • GPGME: “GnuPG Made Easy”. 앱이 gpg를 직접 다루지 않고 함수 호출로 암호화·서명·키 조회를 할 수 있게 해 주는 중간 라이브러리입니다. 메일 앱의 “서명 확인” 버튼 뒤에서 주로 이 라이브러리가 일합니다.
  • OpenPGP 키와 사용자 ID: 공개키에는 “이름 <메일 주소>” 같은 사용자 ID가 붙어 있습니다. 이번 버그는 이 사용자 ID를 비정상적으로 길게 만든 키에서 시작합니다.
  • 이중 해제(double free): 이미 돌려준(free) 메모리를 한 번 더 돌려주는 실수입니다. 메모리 관리 구조가 꼬이면서 공격자가 프로그램 흐름을 비틀 여지가 생기는, 대표적인 메모리 안전성 버그입니다.
  • 정적 링크(static linking): 라이브러리를 실행 파일 안에 통째로 넣어 빌드하는 방식입니다. 이 경우 시스템 라이브러리만 업데이트해서는 고쳐지지 않고 앱을 다시 빌드해야 합니다.

자세한 내용

버그가 생기는 과정

공지에 따르면 문제는 GPGME가 gpg의 출력(상태 줄, 키 목록)을 읽는 두 함수 read_status와 read_colon_line에 있습니다.

  1. 두 함수는 1024바이트짜리 버퍼로 시작하고, 줄이 길면 버퍼를 늘려(realloc) 다시 잡습니다.
  2. 그런데 새로 잡은 버퍼 주소를 함수가 끝날 때가 돼서야 작업 정보에 기록했습니다.
  3. 그 사이에 읽기 오류 같은 이유로 함수가 일찍 빠져나가면, 작업 정보에는 이미 해제된 옛 주소가 남습니다.
  4. 나중에 정리 단계에서 이 옛 주소를 또 해제하면서 이중 해제가 일어납니다.

아주 긴 사용자 ID는 버퍼를 늘리게 만드는 방아쇠입니다. 수정 패치는 늘린 버퍼 주소를 realloc 직후 바로 기록하도록 바꾼, 열 줄 남짓의 작은 변경입니다.

어디까지 영향을 받나

공지가 GPGME를 쓰는 예로 직접 든 소프트웨어는 다음과 같습니다.

분류공지에 나온 예
GnuPG 배포판Gpg4win, GnuPG Desktop, GnuPG VS-Desktop
메일대부분의 메일 클라이언트
메신저많은 XMPP 클라이언트
서버·인프라Samba
앱 배포Flatpak

Flatpak은 리눅스 데스크톱 앱 설치 도구로, 원격 저장소 서명을 확인하는 데 GPG를 씁니다. Samba는 리눅스에서 윈도 파일 공유·도메인 기능을 제공하는 서버입니다. 즉 개인 PC뿐 아니라 서버와 앱 배포 경로도 함께 봐야 합니다.

무엇을 업데이트하나 (공식 권고)

상황할 일
리눅스 등에서 공유 라이브러리로 쓰는 경우GPGME를 2.3.1로 올림 (보통 배포판 보안 업데이트로 들어옴)
윈도 앱이 GPGME DLL을 쓰는 경우Gpg4win(공지에서 5.1.2 언급)에 들어 있는 DLL 사용
GPGME를 정적 링크해 빌드한 앱2.3.1로 다시 빌드
당장 버전을 못 올리는 경우공지에 첨부된 패치 적용 (오래된 버전에도 대부분 깔끔히 적용될 것이라고 함)
C++/Qt 바인딩(GPGMEPP, GPGMEQT)별도 업데이트 필요 없음

설정으로 막는 임시 우회책은 공지에 없습니다. 결국 업데이트 또는 패치가 유일한 해결책입니다.

한계·주의할 점

  • 악용 여부와 위험 점수는 아직 공식 정보가 없습니다. 공지는 실제 공격이 있었는지, CVSS가 몇 점인지 밝히지 않았습니다. “RCE 확정"처럼 쓴 기사도 있지만, 공식 표현은 “배제할 수 없다"입니다.
  • 2.x 이전(1.x) 구버전의 별도 수정판, 배포판별 보안 공지 번호 같은 정보는 일부 보안 블로그에만 나오고 공식 공지에서는 확인되지 않아 이 글에서는 다루지 않았습니다. 쓰는 배포판의 보안 공지를 직접 확인하세요.
  • 시스템 GPGME를 올려도 앱 안에 GPGME를 따로 넣어 둔 경우(정적 링크, 번들 DLL, 일부 Flatpak 런타임)는 그 앱·런타임이 업데이트돼야 고쳐집니다.
  • 공지는 서명된 데이터를 보내는 방식으로 데이터를 빼낼 수 있다고 예를 들었습니다. 즉 사용자가 키를 직접 가져오지 않아도 메일·메시지 처리 과정에서 위험할 수 있으니, “낯선 키만 안 받으면 된다"고 안심하지 않는 편이 좋습니다.

독자가 할 일

개인 사용자(취준생·대학생 포함)

  1. 리눅스라면 배포판 업데이트를 적용하고, 업데이트 목록에 gpgme가 있는지 확인합니다.
  2. 윈도에서 Gpg4win이나 이를 쓰는 메일 앱을 쓴다면 최신 버전으로 올립니다.
  3. 메일 앱, XMPP 메신저 등 PGP 기능이 있는 앱은 앱 업데이트를 확인합니다.
  4. 업데이트 전까지는 출처를 모르는 공개키를 가져오거나, 낯선 서명 메일을 열어 서명 확인하는 일을 미룹니다.

개발자·운영자

  1. 서버(특히 Samba)와 CI 이미지, 컨테이너 베이스 이미지에서 GPGME 버전을 확인하고 2.3.1 또는 배포판 수정판으로 올립니다.
  2. 자사 제품이 GPGME를 정적 링크하거나 DLL로 번들하고 있다면 2.3.1로 다시 빌드해 배포합니다.
  3. SBOM(소프트웨어 구성 목록)이 있다면 gpgme를 검색해 영향받는 제품을 빠르게 추립니다.
  4. 사용자가 올린 키를 서버에서 GPGME로 처리하는 서비스(키 서버, 메일 게이트웨이, 서명 검증 API 등)는 우선순위를 가장 높게 둡니다.

정리

  • 조작한 OpenPGP 키 하나로 GPGME를 쓰는 앱에서 이중 해제가 일어나는 버그가 2026-11-20 공개됐습니다(CVE-2026-129975).
  • 2.3.0 이전 모든 버전이 영향을 받고, 2.3.1이 수정 버전입니다. 정적 링크·번들 DLL은 다시 빌드해야 합니다.
  • 메일·XMPP 클라이언트, Samba, Flatpak 등 범위가 넓으니, 배포판·앱 업데이트를 이번 주 안에 확인하세요.
  • 악용 여부와 CVSS는 아직 공식 발표가 없으니, 추가 공지를 지켜볼 필요가 있습니다.
