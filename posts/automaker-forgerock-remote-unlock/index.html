보안 연구자들이 자동차 회사 2곳의 로그인 시스템에서 남은 기본 비밀번호, JS 파일에 들어간 관리자 계정, 건너뛸 수 있는 MFA를 엮어 차 문을 원격으로 열고 시동까지 걸었습니다. 새로운 취약점이 아니라 흔한 설정 실수의 연쇄였다는 점에서, 우리 서비스도 바로 점검할 거리를 정리합니다.

차 키 대신 스마트폰 앱으로 문을 열고 시동을 거는 커넥티드 카, 이제 흔하죠. 11월 7일, 보안 연구자 샘 커리(Sam Curry) 와 슈밤 샤(Shubham Shah) 가 자동차 회사 두 곳의 계정 시스템을 뚫어 다른 사람의 차 문을 열고 시동을 걸 수 있었다는 분석 글을 각자 블로그에 올렸습니다. 두 회사는 이름을 밝히지 말아 달라고 요청했고, 신고를 받고 약 두 시간 만에 막았다고 합니다.

눈여겨볼 점은 따로 있습니다. 이번 공격에는 새로 발견된 제로데이(아직 알려지지 않은 취약점)가 하나도 없었습니다. 공장 출하 그대로인 비밀번호, 웹에 그대로 배포된 관리자 계정, 건너뛸 수 있는 MFA 같은 흔한 실수가 줄줄이 이어졌을 뿐이에요. 그래서 자동차와 상관없는 웹 서비스를 만드는 분에게도 그대로 쓸모 있는 사례입니다.

이 글은 연구자들의 공개 글과 여러 보도를 교차 확인해 정리했습니다. 자동차 회사 이름은 공식 확인되지 않아 쓰지 않습니다.

가능했던 일계정 탈취, 차량 위치·상태 조회, 문 잠금·해제, 원격 시동·정지

조치신고 후 약 2시간 만에 수정, 노출된 자격 증명 교체

여러 보도가 한목소리로 짚은 부분은 ForgeRock 제품 자체의 결함이 아니라, 각 회사의 배포·설정 실수라는 점입니다. 같은 제품을 쓰는 회사라도 설정을 제대로 했다면 이번 경로는 통하지 않았다는 뜻이에요.

먼저 용어 몇 가지

  • 아이덴티티 플랫폼(IAM): 회원 가입, 로그인, 비밀번호 재설정, 권한 같은 “누가 누구인가"를 관리하는 시스템입니다. ForgeRock의 OpenAM(로그인 담당), OpenIDM(사용자 정보 관리 담당)이 여기에 속해요.
  • WAF(웹 애플리케이션 방화벽): 서버 앞에서 요청 주소·내용을 보고 위험해 보이는 요청을 막는 필터입니다.
  • 경로 혼동(path confusion): 같은 URL을 앞단 필터와 뒷단 서버가 서로 다르게 해석하는 문제입니다. 필터는 “안전한 주소"로 보고 통과시켰는데, 서버는 그걸 “관리자 주소"로 받아들이는 식이죠.
  • 기본 자격 증명(default credentials): 제품을 설치하면 처음부터 들어 있는 아이디·비밀번호입니다. 이번에는 admin:admin이 그대로 남아 있었다고 보도됐습니다.
  • ROPC(Resource Owner Password Credentials): 앱이 사용자 아이디·비밀번호를 직접 받아 바로 토큰으로 바꾸는 오래된 OAuth 방식입니다. 리디렉션·추가 인증 단계를 건너뛰기 쉬워요.
  • 토큰 교환: 한 종류의 로그인 토큰을 다른 서비스용 토큰으로 바꿔 받는 과정입니다. 여기서는 최종적으로 차량 앱용 토큰을 얻는 데 쓰였습니다.

자세한 내용: 두 갈래의 공격 경로

두 연구자의 글은 서로 다른 지역·시스템을 다룹니다. 큰 흐름만 표로 정리하면 이렇습니다.

1. 호주 쪽 경로 (Shah의 글)

단계한 일무엇이 문제였나
① 번호판 → 차대번호호주 차량 등록 조회로 차대번호(VIN)를 얻음원래 공개된 기능(취약점 아님)
② 관리 도구 발견앱을 분석하다 공개 서브도메인의 관리자 도구를 찾음사내 관리 화면이 인터넷에 노출
③ JS 번들 속 비밀로그인 페이지가 내려받는 큰 JavaScript 파일에 API 키·관리 기능이 들어 있었음클라이언트 코드에 비밀값
④ 차대번호 → 계정관리 API로 차대번호를 가입자 정보, 이메일까지 연결관리 API 접근 통제 부족
⑤ 스테이징 계정이 운영에서 작동벤더 JS 파일 속 OpenIDM 관리자 계정이 운영 서버에서도 통함테스트용 비밀이 운영과 같음
⑥ WAF 우회인코딩을 섞은 경로로 차단 규칙을 피해 관리 API에 도달경로 해석 차이
⑦ MFA 건너뛰기비밀번호를 재설정한 뒤 ROPC 방식으로 MFA 없이 토큰 발급MFA가 모든 로그인 경로에 걸려 있지 않음
⑧ 원격 명령차량 앱 토큰으로 문 열림 명령 전송위 단계가 다 뚫린 결과

2. 미국·캐나다 쪽 경로 (Curry의 글)

단계한 일무엇이 문제였나
① 경로 혼동앞단 필터와 뒷단 서비스의 URL 해석 차이로 숨겨진 관리 콘솔에 접근경로 해석 차이
② 관리 콘솔Apache Felix 관리 콘솔이 기본 비밀번호(admin:admin)로 열림기본 자격 증명 미변경
③ 서버에서 코드 실행OpenIDM의 예약 작업 기능으로 운영 서버에서 스크립트 실행관리 기능이 곧 코드 실행 권한
④ 세션 만들기고객 계정의 정상 세션을 만들어 앱 토큰으로 교환아이덴티티 서버가 “모든 열쇠"를 가짐
⑤ 차량 제어위치·상태 조회, 문 잠금·해제, 시동정상 앱과 똑같은 API 경로 사용

두 경로 모두 하나하나는 “설마 이게 문제일까” 싶은 실수입니다. 그런데 그 작은 실수들이 순서대로 이어지자 “번호판만 알면 남의 차를 연다"는 결과가 나왔어요.

한계와 주의할 점

  • 회사 이름은 확인되지 않았습니다. 일부 보도가 특정 브랜드를 추측했지만, 연구자와 회사 모두 공식 확인하지 않았습니다.
  • 실제 악용 여부는 모릅니다. 지금까지 범죄에 쓰였다는 공개 증거는 없지만, 수정 전에 누가 같은 길을 썼는지는 알려지지 않았습니다. 영향받은 차량 수, 노출 기간도 공개되지 않았어요.
  • 시험 시점은 보도마다 다릅니다. 그래서 이 글에서는 구체적인 시험 날짜를 쓰지 않았습니다.
  • “2시간 만에 수정"이 끝은 아닙니다. 자격 증명을 바꾸고 노출 파일을 지운 것은 빠른 대응이지만, 같은 유형의 설정이 다른 곳에 남아 있는지는 별개의 문제입니다.
  • WAF가 나빴다는 이야기가 아닙니다. WAF는 보조 수단일 뿐, 뒷단 서비스가 스스로 인증·권한을 확인하지 않으면 필터 하나가 뚫리는 순간 전부 열린다는 점이 핵심이에요.

독자가 할 일: 우리 서비스 점검 6가지

자동차 회사가 아니어도 로그인·관리자 화면이 있는 서비스라면 그대로 적용됩니다. 학생 프로젝트라면 1·2번만 해도 충분히 의미가 있어요.

1배포된 프런트엔드 파일에 비밀값이 없는가빌드 결과물(JS 번들)에서 key, secret, password, token 같은 단어를 검색해 봅니다. 브라우저로 내려가는 코드에는 공개해도 되는 값만 있어야 합니다.
2설치 기본 계정을 모두 바꿨는가DB, 관리 콘솔, 모니터링 도구, 미들웨어의 초기 계정 목록을 만들어 하나씩 확인합니다. 쓰지 않는 콘솔은 아예 끕니다.
3스테이징과 운영의 비밀이 다른가테스트 환경의 키로 운영 API를 호출할 수 없어야 합니다. 환경마다 별도 비밀을 발급합니다.
4관리자 화면이 인터넷에 열려 있지 않은가사내망·VPN·IP 허용 목록 뒤로 옮기고, 공개 서브도메인 목록을 주기적으로 훑어봅니다.
5MFA가 모든 로그인 경로에 걸리는가웹 로그인뿐 아니라 모바일 앱, 오래된 API, ROPC 같은 레거시 OAuth 흐름까지 확인합니다. OAuth 보안 모범 사례 문서(RFC 9700)는 ROPC를 쓰지 말라고 권고합니다.
6뒷단 서비스가 직접 권한을 확인하는가“WAF가 막아 주니까"가 아니라, 관리 API마다 서비스 안에서 인증·권한 검사를 합니다. 경로 정규화(인코딩 해석)를 앞단과 뒷단이 같게 맞추는 것도 함께 봅니다.

실무 팀이라면 여기에 하나를 더하면 좋습니다. “관리 권한 = 서버 코드 실행 권한"인 기능(예약 스크립트, 플러그인 업로드, 스크립트 콘솔)이 어디 있는지 목록으로 만들어 두세요. 이번 미국 쪽 경로처럼, 관리 콘솔 하나가 뚫리면 곧바로 서버 장악으로 이어지는 지점입니다.

정리

  • 연구자 2명이 자동차 회사 2곳의 계정 시스템을 통해 남의 차를 원격으로 열고 시동을 걸 수 있음을 보였고, 회사들은 약 2시간 만에 막았습니다.
  • 원인은 새로운 취약점이 아니라 기본 비밀번호, JS 속 관리자 계정, 운영과 같은 테스트 비밀, 경로 해석 차이, 일부 경로의 MFA 누락이 이어진 결과였습니다.
  • 우리 서비스에서도 번들 속 비밀값, 기본 계정, 관리자 화면 노출, 모든 경로의 MFA부터 오늘 확인해 볼 수 있습니다.
