구글의 보안 연구팀 Project Zero가 2026년 11월 13일 취약점 공개 정책을 바꿨습니다. 지금까지는 “고치는 데 90일, 사용자에게 퍼지는 데 30일"을 기다렸다면, 이제는 신고한 날로부터 정해진 날수가 지나면 고쳤는지와 상관없이 공개합니다. 그 날수도 90일에서 60일, 30일로 단계적으로 줄어듭니다.

이 글은 소프트웨어를 만들어 배포하는 개발자, 서버·사내 시스템 패치를 맡은 운영자, 그리고 “취약점은 어떤 순서로 세상에 알려지나"가 궁금한 학생·취준생을 위한 정리입니다.

Project Zero 공식 블로그 글(2026-11-13)을 기준으로 썼고, Cloud Security Alliance 요약과 대조했습니다. (2026-11-15 확인 기준)

무슨 일이 있었나

  • 11월 13일: Project Zero의 Natalie Silvanovich가 “Policy and Disclosure: 2026 Edition"을 발표했습니다.
  • 바로 적용: 같은 날부터 새 정책 **“Full 90”**이 시행됩니다.
  • 단계적 단축: 2027년 2월 2일부터 Full 60, 2028년 1월 3일부터 Full 30.
  • 사라지는 것: 패치 후 배포 기간(30일 soak time), 기한 연장(grace period), 변종 취약점(variant) 특례.

먼저 용어 몇 가지

  • Project Zero: 구글 안에서 남의 제품(구글 제품 포함)의 취약점을 찾아 업체에 알리는 연구팀입니다. 운영체제·브라우저·하드웨어까지 폭넓게 다룹니다.
  • 조율된 공개(coordinated disclosure): 취약점을 찾은 사람이 먼저 업체에 비공개로 알리고, 정해진 기간이 지나면 세상에 공개하는 관행입니다. 업체에는 고칠 시간을, 사용자에게는 결국 정보를 주려는 절충입니다.
  • 패치 갭(patch gap): 수정판이 나온 날과 사용자가 실제로 설치한 날 사이의 틈입니다. 이 기간에 공격자는 공개된 패치를 분석해 공격 방법을 만들 수 있습니다.
  • 패치 디핑(patch diffing): 수정 전후 코드를 비교해 어디가 고쳐졌는지 알아내는 기법입니다. 공격자도 이 방법으로 취약점 위치를 거꾸로 찾아냅니다.
  • 실제 악용(in the wild): 연구실이 아니라 실제 공격에 이미 쓰이고 있는 상태를 말합니다.

무엇이 달라졌나

항목이전 “90+30” (2021~)새 “Full X” (2026-11-13~)
공개 기준업체가 고쳤는지, 언제 고쳤는지에 따라 달라짐신고일 + X일, 고친 여부는 판단 기준이 아님
기한수정 90일 + 배포 30일90일 → 60일(2027-02-02) → 30일(2028-01-03)
기한 연장조건부 grace period 있음없음
변종 취약점별도 규칙 있음없음
남은 예외—실제 악용 중(구글 별도 정책 적용), 이미 공개됨, 업체가 먼저 공개 요청
업체와 협상수정 확인·연장 등 건별 논의자동화할 수 있게 단순화

Project Zero는 고쳤는지 여부를 계속 추적하고, 고쳐지지 않았으면 그 사실도 알리겠다고 했습니다. 다만 그것이 공개 날짜를 바꾸지는 않습니다. 스펙터·멜트다운처럼 아주 드문 경우의 예외는 앞으로도 있을 수 있다고 덧붙였습니다.

왜 바꿨나

Project Zero가 든 이유는 크게 네 가지입니다.

  1. 찾는 속도가 빨라졌습니다. LLM(대규모 언어 모델) 덕분에 취약점을 찾고 공격 코드를 만드는 일이 빨라졌고, 같은 버그를 여러 사람, 그중 악의적인 쪽도 함께 찾을 가능성이 커졌다고 봤습니다.
  2. 패치 뒤 30일이 더는 비밀 기간이 아닙니다. 패치가 나오면 LLM으로 패치 디핑과 공격 코드 작성이 빨라져, 30일 배포 기간은 “아직 아무도 모른다"는 착각만 준다고 설명합니다.
  3. 신고 건수가 늘었습니다. 예전에는 1년에 몇 건 나오던 대상에서 이제는 일주일에 여러 건을 찾는다고 합니다. 건마다 수정 확인·연장을 협상하는 방식은 감당이 안 된다는 것입니다.
  4. 중요도는 공개 시점의 기준이 아니라고 봤습니다. 심각한 버그든 아니든 공격자가 찾아낼 확률은 같기 때문입니다.

한 번에 30일로 줄이지 않고 단계를 둔 이유도 밝혔습니다. 업체 쪽에서 “갑자기 줄이면 절차를 고치는 동안 사용자가 위험해진다”, “중요도 대신 마감 순으로 고치게 된다”, “기한 넘기기를 당연하게 여기게 된다"는 의견이 나왔다고 합니다.

주의할 점과 한계

  • Project Zero 신고에만 해당합니다. 다른 보안 회사·연구자·버그 바운티의 공개 기한은 그대로입니다. 다른 팀이 따라갈지는 아직 알 수 없습니다.
  • 공개되는 내용의 범위는 글에 자세히 나오지 않습니다. 공격 코드(PoC)까지 함께 나오는지는 공식 글에서 확인하지 못했습니다.
  • 이미 진행 중인 신고에 어떻게 적용되는지도 명시돼 있지 않습니다. 업체라면 Project Zero에 직접 확인하는 편이 안전합니다.
  • 반론도 예상됩니다. “고치기 전에 공개하면 공격자에게 지도를 주는 것"이라는 오래된 비판이 있습니다. Project Zero의 입장은 공격자가 이미 빠르게 찾고 있으니 사용자가 위험을 아는 편이 낫다는 쪽입니다. 어느 쪽이 맞는지는 실제 사례가 쌓여야 판단할 수 있습니다.

독자가 할 일

  • 소프트웨어를 만들어 배포한다: 보안 신고를 받으면 “고치는 시간"뿐 아니라 사용자에게 퍼지는 시간까지 기한 안에 끝내야 한다고 보고 절차를 점검하세요. 자동 업데이트, 빠른 핫픽스 배포, 설정 변경으로 막는 임시 조치(완화책)를 미리 준비해 두면 기한이 짧아져도 버틸 수 있습니다.
  • 서버·사내 시스템을 운영한다: 패치 갭을 줄이는 것이 핵심입니다. 운영체제·브라우저·주요 라이브러리 업데이트를 “다음 정기 점검 때"가 아니라 며칠 안에 적용할 수 있는 흐름을 만들어 두세요. 수정판보다 공개 글이 먼저 나올 수도 있으니, 업체 보안 공지와 함께 임시 조치 안내도 챙겨 봐야 합니다.
  • 오픈소스를 관리한다: 보안 신고 창구(보안 정책 문서, 비공개 신고 경로)가 있는지 확인하고, 릴리스를 빠르게 낼 수 있는지 점검해 두세요.
  • 취준생·학생: 취약점이 “발견 → 비공개 신고 → 수정 → 공개” 순서로 흐른다는 것, 그리고 AI가 이 시간표 자체를 바꾸고 있다는 점을 보여 주는 사례입니다. 보안 직무 면접에서 “책임 있는 공개"를 묻는다면 좋은 이야깃거리가 됩니다.

정리

  • Project Zero가 2026년 11월 13일부터 **“Full 90”**을 시행합니다. 신고 후 90일이 지나면 고쳤든 못 고쳤든 공개합니다.
  • 기한은 2027년 2월 2일 60일, 2028년 1월 3일 30일로 줄어듭니다. 기한 연장과 30일 배포 기간은 없어졌습니다.
  • 이유는 AI로 빨라진 취약점 발견·공격과 늘어난 신고 건수입니다. 만드는 쪽은 배포까지 포함한 대응 속도를, 쓰는 쪽은 빠른 업데이트 습관을 갖춰야 할 때입니다.
