PostgreSQL 19 출시 — 서비스를 멈추지 않고 부푼 테이블을 줄이는 REPACK (CONCURRENTLY)

11월 19일 나온 PostgreSQL 19의 핵심은 테이블을 잠그지 않고 빈 공간을 돌려받는 REPACK (CONCURRENTLY)입니다. 쓸 수 없는 조건과 주의점, 함께 바뀐 autovacuum·복제·보안 기본값까지 정리합니다.

2026-11-23 · #postgresql #postgresql-19 #repack #vacuum #table-bloat #logical-replication #database-upgrade

목차
  • 무슨 일이 있었나
  • 먼저 용어 몇 가지
  • REPACK은 무엇이 다른가
  • CONCURRENTLY를 쓸 수 없는 경우
  • 주의할 점
  • 함께 바뀐 것 중 챙길 것
  • 지금 할 일
  • 정리
  • 참고 출처

PostgreSQL을 오래 운영하면 “데이터는 별로 안 늘었는데 디스크는 계속 찬다"는 상황을 한 번쯤 만납니다. 지금까지 이걸 근본적으로 푸는 기본 명령(VACUUM FULL)은 작업 내내 테이블을 잠갔기 때문에, 많은 팀이 점검 시간을 따로 잡거나 외부 확장 도구를 썼습니다.

2026년 11월 19일 나온 PostgreSQL 19는 이 문제를 본체에서 직접 다룹니다. 새 명령 REPACK과, 읽기·쓰기를 막지 않는 REPACK (CONCURRENTLY)가 들어왔습니다.

이 글은 서비스나 사이드 프로젝트에서 PostgreSQL을 쓰는 개발자, 그리고 데이터베이스를 처음 맡게 된 분을 위한 정리입니다.

무슨 일이 있었나

PostgreSQL 개발 그룹이 메이저 버전 19를 정식 출시했습니다. 공식 발표가 앞세운 변화는 크게 네 가지입니다.

영역주요 변화
테이블 정리REPACK, REPACK (CONCURRENTLY) 추가. VACUUM FULL·CLUSTER를 대체하는 명령으로 소개(두 명령은 호환을 위해 남음)
실행 계획pg_plan_advice로 쿼리 실행 계획 선택을 고정·유도, pg_stash_advice로 쿼리별 저장
autovacuum인덱스 정리 병렬화(autovacuum_max_parallel_workers), 테이블 우선순위 점수제
복제·보안논리 복제가 시퀀스까지 지원, 재시작 없이 논리 복제 시작, md5 인증 시 경고, RADIUS 인증 제거

먼저 용어 몇 가지

  • 테이블 팽창(bloat): PostgreSQL은 행을 수정·삭제해도 옛 버전을 바로 지우지 않습니다. 이 “죽은 행"이 쌓여 실제 데이터보다 파일이 커지는 현상입니다.
  • VACUUM: 죽은 행 자리를 재사용할 수 있게 표시하는 정리 작업입니다. 파일 크기 자체는 대개 줄지 않습니다.
  • VACUUM FULL / CLUSTER: 테이블을 새 파일로 통째로 다시 써서 운영체제에 공간을 돌려줍니다. 대신 작업 내내 테이블을 잠급니다.
  • ACCESS EXCLUSIVE 잠금: 가장 강한 잠금입니다. 걸려 있는 동안 그 테이블은 조회도 못 합니다.
  • 논리 디코딩(logical decoding): WAL(변경 기록)을 읽어 “어떤 행이 어떻게 바뀌었는지"로 풀어내는 기능입니다. 논리 복제의 바탕입니다.
  • 복제 식별자(replica identity): 논리 디코딩이 행을 구분하는 기준입니다. 보통 기본 키가 그 역할을 합니다.

REPACK은 무엇이 다른가

REPACK은 테이블 전체를 새 파일로 다시 써서 빈 공간을 운영체제에 돌려줍니다. USING INDEX를 붙이면 인덱스 순서로 행을 재배치합니다(기존 CLUSTER 역할). 실행하려면 테이블에 대한 MAINTAIN 권한이 필요합니다.

차이는 잠금에 있습니다.

방식작업 중 잠금작업 중 읽기·쓰기
VACUUM FULL, CLUSTER, REPACK처음부터 끝까지 ACCESS EXCLUSIVE막힘
REPACK (CONCURRENTLY)대부분은 SHARE UPDATE EXCLUSIVE, 마지막 파일 교체 순간에만 ACCESS EXCLUSIVE가능

CONCURRENTLY 모드는 복사하는 동안 들어온 변경을 논리 디코딩으로 따로 모았다가, 마지막에 짧게 잠그기 직전에 반영합니다. 그래서 그동안 pg_repack 같은 외부 확장으로 하던 일을 본체 기능으로 할 수 있게 됐습니다.

공식 문서에 나온 문법 형태는 다음과 같습니다(일부만 옮김). 아래는 문서 문법을 그대로 따른 예이며, 이 글에서 직접 실행해 본 것은 아닙니다.

-- 문법 요약 (PostgreSQL 19 문서)
-- REPACK [ ( option [, ...] ) ] [ table_and_columns [ USING INDEX [ index_name ] ] ]
-- option: VERBOSE | ANALYZE | CONCURRENTLY

REPACK (CONCURRENTLY, VERBOSE) orders;

진행 상황은 pg_stat_progress_repack 뷰에서 볼 수 있습니다.

CONCURRENTLY를 쓸 수 없는 경우

문서가 밝힌 제한이 꽤 많습니다. 운영에 쓰기 전에 대상 테이블이 걸리는지 먼저 확인하세요.

조건설명
일반 테이블이 아님구체화된 뷰(materialized view) 등은 불가
UNLOGGED 테이블불가
파티션 테이블(부모)불가
기본 키도, 인덱스 기반 복제 식별자도 없음불가 — 논리 디코딩으로 행을 구분해야 하기 때문
시스템 카탈로그·TOAST 테이블, heap이 아닌 접근 방식불가
트랜잭션 블록 안에서 실행불가
max_repack_replication_slots 여유 없음불가 — 내부적으로 복제 슬롯을 하나 씀
테이블 이름 없이 전체 실행CONCURRENTLY와 함께 쓸 수 없음

주의할 점

  • 디스크 여유가 필요합니다. 새 파일을 만든 뒤 바꾸는 방식이라, 최소한 “테이블 크기 + 인덱스 크기"만큼 빈 공간이 있어야 합니다. 디스크가 거의 찬 상태에서 공간을 확보하려고 쓰기에는 맞지 않을 수 있습니다.
  • MVCC 안전하지 않습니다. 작업이 끝난 뒤, 작업 전에 시작된 트랜잭션에는 테이블이 비어 보일 수 있다고 문서가 경고합니다. 오래 열려 있는 리포트성 트랜잭션이 있는 시간대는 피하는 편이 좋습니다.
  • 변경량 한도가 있습니다. 작업 중 동시에 수정·삭제된 행이 약 1억 400만 개를 넘으면 명령이 실패합니다.
  • 도중의 DDL에 약합니다. 다른 세션이 같은 테이블 구조를 바꾸면 실패할 수 있습니다.
  • VACUUM을 대신하지 않습니다. 트랜잭션 ID 겹침(wraparound) 예방에는 여전히 VACUUM이 맞고, 오래 걸리는 REPACK은 다른 테이블의 정리를 늦출 수 있습니다.
  • 아직 첫 릴리스입니다. 19.0은 메이저 버전의 첫 릴리스입니다. 중요한 운영 DB는 첫 마이너 업데이트를 기다리자는 의견도 커뮤니티에 있습니다.

함께 바뀐 것 중 챙길 것

기본값이 바뀐 항목

  • JIT 기본 꺼짐: 비용 추정이 믿기 어려웠다는 이유로 JIT 컴파일이 기본 비활성화됐습니다. 분석 쿼리에서 JIT 효과를 보던 곳은 업그레이드 후 성능을 비교해 보세요.
  • TOAST 기본 압축 lz4: LZ4를 포함해 빌드한 경우 큰 값 압축 기본 방식이 lz4로 바뀝니다.
  • md5 인증 경고: md5로 로그인에 성공하면 경고가 나옵니다(md5_password_warnings로 끌 수 있음). md5는 18에서 지원 중단 예고됐고 앞으로 제거될 예정이니 SCRAM으로 옮길 때입니다.
  • RADIUS 인증 제거: 이 방식을 쓰는 곳은 업그레이드 전에 다른 인증으로 바꿔야 합니다.

운영에 도움이 되는 추가 기능

  • 논리 복제 슬롯을 처음 만들 때 WAL 수준이 자동으로 logical로 올라갑니다(재시작 불필요, effective_wal_level로 확인).
  • FOR ALL SEQUENCES로 시퀀스까지 논리 복제할 수 있어, 복제 기반 업그레이드나 이전 때 시퀀스 값을 따로 맞추던 수고가 줄어듭니다.
  • 대기 서버에서 WAIT FOR LSN으로 “방금 쓴 데이터가 복제될 때까지 기다렸다 읽기"를 할 수 있습니다.
  • 새 모니터링 뷰 pg_stat_lock, pg_stat_recovery, pg_stat_autovacuum_scores와 EXPLAIN ANALYZE의 IO 옵션이 생겼습니다.
  • 외래 키 검사 개선으로 대량 INSERT가 시험에서 2배 가까이 빨라졌다고 공식 발표에 나와 있습니다(PostgreSQL 측 테스트 결과, 환경에 따라 다름).
  • 개발자용으로 INSERT ... ON CONFLICT DO SELECT, COPY의 JSON 출력, 윈도 함수 IGNORE NULLS 등이 추가됐습니다.

지금 할 일

  1. 팽창이 심한 테이블 목록부터 만들어 두세요. 그 테이블에 기본 키가 있는지, 파티션·UNLOGGED가 아닌지 확인하면 CONCURRENTLY 대상인지 바로 갈립니다.
  2. 디스크 여유를 계산하세요. 대상 테이블과 인덱스 크기를 합친 만큼 빈 공간이 있어야 합니다.
  3. 외부 확장(pg_repack)을 쓰는 곳은 19로 올린 뒤 본체 REPACK으로 바꿀지 스테이징에서 비교해 보세요.
  4. 업그레이드 전 점검: RADIUS·md5 인증을 쓰는지, JIT 의존 쿼리가 있는지 확인합니다. 전체 변경 사항은 공식 릴리스 노트에서 확인하세요.
  5. 운영 DB는 서두르지 않기: 개발·스테이징에서 먼저 써 보고, 클라우드 관리형 DB라면 제공사의 19 지원 일정을 확인하세요.

정리

PostgreSQL 19의 REPACK (CONCURRENTLY)는 “부푼 테이블 줄이기"를 점검 시간 없이 본체 기능으로 할 수 있게 해 준다는 점에서 운영자에게 반가운 변화입니다. 다만 기본 키 필요, 디스크 여유, MVCC 비안전 같은 제약이 분명하니, 대상 테이블이 조건에 맞는지 먼저 확인하고 스테이징에서 시험해 보는 것이 순서입니다. JIT 기본값 변경과 RADIUS 제거처럼 업그레이드 때 놓치기 쉬운 기본값 변화도 함께 챙기세요.
