웹사이트는 우리 팀이 짠 코드만으로 돌아가지 않습니다. 분석 도구, 광고 태그, 채팅 위젯, A/B 테스트 도구처럼 다른 회사 서버에서 불러오는 자바스크립트가 페이지마다 여러 개 붙어 있습니다. 이 스크립트는 내 사이트 안에서 내 코드와 똑같은 권한으로 실행됩니다.

2026년 11월 16일(UTC), 바로 이 구조가 뚫렸습니다. A/B 테스트 플랫폼 Optimizely를 거쳐 BBC, Zoom, CNN, Salesforce, GitLab, HSBC 등 178개 조직의 사이트 방문자에게 악성 자바스크립트가 배포됐습니다. 피해 기업들의 소스 코드는 한 줄도 바뀌지 않았습니다.

Optimizely의 확인 발언(Help Net Security·The Next Web 보도), 최초 발견자 Scott Helme(Report URI)의 분석을 인용한 여러 보도, StepSecurity의 기술 분석, GeekNews 요약을 교차 확인해 썼습니다. (2026-11-18 확인 기준)

무슨 일이 있었나

시각(UTC, 2026년)내용
11월 16일 04:21경첫 악성 코드 주입이 관측됨
11월 16일 하루 동안공격자가 페이로드(실제 악성 동작 코드)를 여러 차례 고쳐 가며 기능을 추가
11월 16일 밤감염된 스크립트 대부분이 정리됨 (일부는 늦게까지 남음)
11월 17일Optimizely가 사고를 공식 확인
  • 피해 규모: Scott Helme 팀이 Optimizely 스크립트 1,611개를 점검해 188개에서 악성 코드를 찾았고, 이는 178개 조직에 해당합니다. 점검하지 못한 스크립트도 있어 실제 규모는 더 클 수 있다고 봅니다.
  • 노출 시간: 대부분 사이트에서 하루가 채 안 됐습니다.
  • 원인: Optimizely는 “Experimentation(실험) 제품의 취약점"이 악용됐다고 밝혔고, 일부 보도는 그 위치를 계정 가입 절차로 전합니다. 이 결함으로 어떻게 남의 프로젝트에 코드를 쓸 수 있었는지는 아직 공개되지 않았습니다.
  • Optimizely 조치: 취약 경로 차단·수정, 주입된 코드 제거, 세션 종료와 토큰 폐기, 영향받은 고객 통보.

먼저 용어 몇 가지

  • A/B 테스트 도구: 방문자를 두 그룹으로 나눠 다른 화면을 보여 주고 어느 쪽 반응이 좋은지 재는 도구입니다. 화면을 바꾸려고 페이지 안에서 자바스크립트를 실행합니다.
  • 서드파티 스크립트: 내 서버가 아닌 외부 회사 서버(CDN)에서 불러오는 스크립트입니다. <script src="https://외부회사/..."> 형태로 붙습니다.
  • 공급망 공격: 목표 회사를 직접 뚫는 대신, 그 회사가 믿고 쓰는 도구·라이브러리·업체를 뚫어 거쳐 들어가는 공격입니다.
  • 스키머(skimmer): 결제 폼에 입력되는 카드 번호를 몰래 빼돌리는 코드입니다.
  • CSP(콘텐츠 보안 정책): “이 페이지는 어느 도메인의 스크립트만 실행하고, 어디로만 데이터를 보낼 수 있다"를 브라우저에 알려 주는 HTTP 응답 헤더입니다.
  • SRI(하위 리소스 무결성): 외부 스크립트의 해시값을 미리 적어 두고, 내용이 바뀌면 브라우저가 실행을 거부하게 하는 기능입니다.

어떻게 동작했나

Optimizely Web을 쓰는 사이트는 프로젝트마다 하나씩 있는 스크립트(cdn.optimizely.com/js/<프로젝트 ID>.js 형태)를 페이지에 넣습니다. 이 스크립트에는 고객이 직접 적어 넣는 “Project JavaScript” 칸이 포함돼, 모든 페이지에서 함께 실행됩니다.

공격자는 이 칸에 악성 코드를 써 넣었습니다. 그러면:

  1. 피해 기업의 HTML은 그대로입니다. 늘 불러오던 Optimizely 스크립트를 늘 쓰던 주소에서 불러올 뿐입니다.
  2. 그런데 그 스크립트 안에 공격자 코드가 들어 있어, 방문자 브라우저에서 피해 기업 사이트의 권한으로 실행됩니다.

StepSecurity 분석에 따르면 악성 코드를 불러오는 방식도 세 가지로 나뉘었습니다. 외부 서버 주소를 그대로 쓰는 방식, 주소를 base64로 감춰 단순 검색을 피하는 방식, 그리고 페이로드 전체를 스크립트 안에 넣고 eval로 실행하는 방식입니다. 마지막 방식은 공격자 서버 도메인을 막아도 실행됩니다.

페이로드가 한 일

기능내용한계
암호화폐 주소 바꿔치기화면·입력칸·클립보드의 지갑 주소를 공격자 주소로 교체결제 관련 문맥에서만 동작
쿠키·화면 탈취주소를 바꾼 뒤 화면 캡처와 쿠키를 공격자 서버로 전송HttpOnly 쿠키는 읽지 못함
카드 스키밍사이트 자체 결제 폼의 카드 번호·유효기간·CVV 수집Stripe 같은 결제사 호스팅 폼(별도 iframe)은 접근 불가
iOS 공격 단계아이폰·아이패드 방문자에게 iOS 공격 도구 모음(Coruna, DarkSword로 지목) 로드실제 기기 감염은 보고되지 않음

암호화폐 피해는 Helme 추정 약 7,000달러로, 다른 분석 업체도 비슷한 규모로 봤습니다. 카드·쿠키가 얼마나 새어 나갔는지는 아무도 셀 수 없습니다. 블록체인처럼 흔적이 남지 않기 때문입니다.

기존 방어가 놓친 이유

이번 사건이 실무자에게 불편한 이유는, 흔히 쓰는 방어 수단 대부분이 구조적으로 볼 수 없는 곳에서 일이 벌어졌다는 점입니다.

방어 수단이번 공격에서이유
코드 리뷰·저장소 스캔❌ 못 잡음피해 기업 저장소의 코드는 바뀌지 않음
신뢰 도메인 허용(cdn.optimizely.com만 허용)❌ 못 막음악성 코드가 바로 그 허용된 도메인에서 옴
SRI⚠️ 적용 어려움실험을 바꿀 때마다 스크립트 내용이 달라져 해시를 고정할 수 없음
CSP script-src 호스트 허용 목록⭕ 일부 차단외부 서버에서 페이로드를 받는 방식은 막지만, 스크립트 안에 통째로 넣고 eval로 돌리는 방식은 unsafe-eval이 허용돼 있으면 통과
CSP connect-src 허용 목록⭕ 일부 차단탈취한 데이터를 외부로 보내는 요청을 막음. 단, 화면의 주소 바꿔치기 자체는 전송이 필요 없어 막지 못함
결제사 호스팅 결제 폼⭕ 카드 보호다른 출처(origin)의 iframe 안은 스크립트가 읽을 수 없음

또 하나 짚을 지점은 eval 허용입니다. A/B 테스트 도구는 화면을 동적으로 바꾸는 특성상 eval류 실행을 허용하는 CSP 설정이 필요해지는 경우가 있는데, Help Net Security 보도는 이 설정 때문에 스크립트에 통째로 들어 있던 예비 페이로드가 일부 사이트에서 실행됐다고 전합니다.

한계와 주의할 점

  • 진입 경로가 아직 불분명합니다. “가입 절차 취약점"으로 어떻게 다른 고객 프로젝트에 쓰기 권한을 얻었는지 Optimizely가 설명하지 않았습니다. 후속 발표에 따라 해석이 바뀔 수 있습니다.
  • 수치는 분석 주체마다 조금씩 다릅니다. 감염 스크립트 수, 마지막 정리 시각, 피해 금액은 각 업체가 본 범위 안의 값입니다.
  • 분석 업체의 이해관계. 최초 발견자인 Report URI와 StepSecurity 모두 스크립트 감시 제품을 팝니다. 사실 관계는 여러 보도로 교차 확인했지만, “우리 제품이면 막았다"는 식의 결론은 걸러서 보는 게 좋습니다.
  • iOS 단계는 확인되지 않은 부분이 많습니다. 공격 도구가 로드된 것과 실제 기기가 감염된 것은 다른 이야기이며, 후자는 보고되지 않았습니다.
  • 비슷한 사례가 이어지고 있습니다. 2024년 polyfill.io 사건처럼, “믿고 붙여 둔 외부 스크립트"가 공격 통로가 되는 일은 이번이 처음이 아닙니다.

독자가 할 일

웹사이트를 운영·개발한다면

  1. 우리 사이트에 붙은 서드파티 스크립트 목록부터 만듭니다. 태그 매니저 안에 숨어 있는 것까지 포함합니다. 모르는 스크립트는 지킬 수도 없습니다.
  2. Optimizely Web을 쓴다면 모든 프로젝트의 Project JavaScript 칸을 직접 열어 보고, 사용자 계정·API 토큰을 점검합니다. 필요하면 Optimizely에 우리 프로젝트가 수정됐는지, 언제였는지 문의합니다.
  3. 결제·로그인 페이지에서는 서드파티 스크립트를 빼거나 최소화합니다. 카드 입력은 결제사가 호스팅하는 폼(iframe)으로 옮기는 것이 이번에 실제로 효과가 있었던 방어입니다.
  4. CSP를 “있다"에서 “제대로 있다"로 올립니다. script-src와 connect-src를 허용 목록 방식으로 좁히고, unsafe-eval이 정말 필요한지 따져 봅니다. 처음에는 Content-Security-Policy-Report-Only 헤더로 위반 보고만 받아 보면서 조이면 서비스를 깨뜨리지 않고 적용할 수 있습니다.
  5. CSP 위반 보고(report)를 실제로 받아서 봅니다. StepSecurity는 이번 사건에서도 위반 보고에 찍힌 차단 기록으로 악성 로더가 실행된 페이지를 찾으라고 권고합니다.

그냥 방문자라면

  • 11월 16일 언급된 사이트에서 암호화폐를 보냈다면 받는 주소가 맞았는지 확인합니다. 앞으로는 복사·붙여넣기한 주소를 하드웨어 지갑 화면 등에서 한 번 더 대조하는 습관을 들입니다.
  • 그날 해당 사이트 자체 결제창에 카드를 입력했다면 카드 내역을 확인하고, 걱정되면 카드 재발급을 요청합니다.
  • 아이폰·아이패드는 최신 iOS로 업데이트합니다. 보도에 따르면 이번에 로드된 공격 도구는 iOS 18.7.3, 26.3 이후 버전에서 이미 막힌 취약점을 노립니다.

정리

  • Optimizely의 취약점으로 178개 조직의 A/B 테스트 스크립트에 악성 코드가 들어가, 하루 동안 방문자에게 배포됐습니다.
  • 피해 기업의 코드는 바뀌지 않았고, 악성 코드는 허용 목록에 올려 둔 신뢰 도메인에서 왔습니다. 그래서 코드 리뷰·도메인 허용·SRI 같은 익숙한 방어가 대부분 통하지 않았습니다.
  • 실제로 피해를 줄인 것은 **좁게 짠 CSP(connect-src 포함)**와 결제사 호스팅 결제 폼이었습니다.
  • 서드파티 스크립트는 “우리 코드"와 같은 권한으로 돌아갑니다. 붙일 때 한 번이 아니라, 붙어 있는 동안 계속 의심하고 지켜봐야 하는 대상입니다.
