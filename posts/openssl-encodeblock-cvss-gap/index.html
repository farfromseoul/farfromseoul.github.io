OpenSSL 취약점 CVE-2026-121481, '9.8 치명적'이 아니라 OpenSSL 기준 '낮음' — 점수가 서로 다를 때 읽는 법

OpenSSL 4.0·4.1의 Base64 인코딩 함수 EVP_EncodeBlock() 정수 오버플로(CVE-2026-121481)가 한때 CVSS 9.8로 표시돼 화제가 됐지만, OpenSSL은 '낮음'으로 매겼고 현재 CISA 점수는 5.9입니다. 영향 버전, 실제 위험 조건, 점수가 갈린 이유와 점수 읽는 법을 정리합니다.

11월 20일 Hacker News 첫 화면에 “OpenSSL 버퍼 오버플로, CVSS 9.8"이라는 글이 올라왔습니다. OpenSSL은 거의 모든 서버·언어 런타임이 쓰는 암호 라이브러리라서 9.8(치명적)이라는 숫자만 보면 당장 비상 패치를 해야 할 것처럼 보입니다.

그런데 이 취약점을 직접 관리하는 OpenSSL 프로젝트는 위험도를 ‘낮음(Low)‘으로 매겼고, 미국 CISA가 CVE 기록에 붙인 현재 점수는 5.9, Red Hat은 3.7입니다. 같은 버그에 9.8부터 ‘낮음’까지 숫자가 갈린 셈입니다.

이 글은 ① 무슨 버그인지 ② 내 시스템이 해당되는지 ③ 점수가 왜 이렇게 갈렸고, 앞으로 비슷한 일이 생기면 무엇을 보고 판단하면 되는지를 정리합니다.

CVE 기록(OpenSSL이 발급 기관)을 OpenCVE·CIRCL Vulnerability-Lookup 두 곳의 미러로 확인했고, 수정 PR(openssl/openssl #33652) 토론, OpenSSL 공식 다운로드 페이지와 11월 17일 보안 권고를 직접 읽었습니다. 한 곳에만 나온 내용은 넣지 않거나 그렇다고 표시했습니다. (2026-11-21 확인 기준)

무슨 일이 있었나

  • 11월 10일: 연구자가 EVP_EncodeBlock()의 길이 계산 문제를 고치는 PR(#33652)을 OpenSSL 저장소에 올렸습니다. 제보자이자 수정 작성자로 CVE 기록에 이름이 올라 있습니다.
  • 11월 18일: CVE-2026-121481이 공개됐습니다. 같은 날 GitHub 보안 권고(GHSA, 아직 GitHub 검토 전)에는 CVSS 9.8이 표시됐습니다.
  • 11월 19~20일: CVE 기록의 점수가 여러 번 바뀌었습니다. OpenCVE의 변경 이력에는 9.8 → 8.4 → 5.9 순으로 남아 있고, 현재 값은 CISA-ADP(CISA가 CVE 기록에 보강 정보를 붙이는 프로그램)의 5.9입니다. NVD는 아직 자체 분석 전(Awaiting Analysis) 상태입니다.
  • 실제 공격 보고 없음: CISA KEV(실제 악용된 취약점 목록)에 없고, CISA의 SSVC 평가도 “악용 없음, 자동화 불가"입니다. 30일 내 악용 확률을 추정하는 EPSS도 1% 미만입니다.

핵심 개념 먼저

  • Base64: 바이너리 데이터를 글자(A–Z, a–z, 0–9, +, /)로 바꾸는 인코딩입니다. 인증서 PEM 파일, HTTP Basic 인증 헤더 등에 쓰입니다.
  • EVP_EncodeBlock(): OpenSSL이 제공하는 Base64 인코딩 함수입니다. 호출하는 쪽이 결과를 담을 버퍼를 미리 준비해야 합니다.
  • 정수 오버플로: 계산 결과가 변수에 담을 수 있는 최댓값을 넘어 엉뚱하게 작은 값(또는 음수)으로 바뀌는 현상입니다. 길이 계산에서 생기면 “버퍼가 충분하다"고 잘못 판단해 메모리를 넘쳐 쓰게 됩니다.
  • CVSS: 취약점의 심각도를 0~10점으로 매기는 공통 기준입니다. 다만 점수는 ‘최악의 사용 방식’을 가정해 매길 수도, ‘실제로 노출되는 방식’을 따져 매길 수도 있어서 누가 매기느냐에 따라 달라질 수 있습니다.
  • CNA: CVE 번호를 발급하고 기록을 관리하는 기관입니다. OpenSSL 취약점은 OpenSSL 프로젝트가 직접 CNA입니다.

자세한 내용

어떤 버그인가

EVP_EncodeBlock()은 입력 길이를 받아 결과 길이(입력의 약 4/3배)를 계산합니다. 입력이 약 1.6GB 이상, 즉 int 최댓값(약 21억)에 가까워지면 이 계산이 넘쳐서, 함수가 호출자가 준비한 버퍼 바깥(힙 메모리)에 써 버릴 수 있습니다. CVE 기록은 이를 정수 오버플로(CWE-190)로 분류합니다.

정리하면 “아주 큰 데이터를 한 번에 Base64로 인코딩할 때만” 생기는 문제입니다.

  • OpenSSL 공식 다운로드 페이지의 최신 버전은 4.1.0(10월 23일), 4.0.3(9월 29일), 3.5.9(9월 29일) 입니다.
  • 11월 17일 OpenSSL 보안 권고(별도 CVE 3건, 모두 ‘낮음’)는 4.1.1·4.0.4 등이 12월 1일 출시 예정이라고 밝혔습니다. 이 CVE의 수정도 그 버전에 들어갈 것으로 CVE 기록이 표시하지만, 수정 PR 자체는 확인 시점에 아직 리뷰 토론 중이었습니다.
  • 배포판 쪽 표기는 다를 수 있습니다. Ubuntu는 여러 릴리스의 openssl·Node.js 패키지를 목록에 올렸는데, 이는 업스트림의 “3.x·1.1.1 영향 없음"과 맞지 않는 부분이 있어 각 배포판 보안 추적 페이지에서 내 패키지를 직접 확인하는 게 안전합니다.

실제로 위험해지는 조건

OpenSSL이 ‘낮음’으로 매긴 이유(CVE 기록 설명 요약)는 다음과 같습니다.

  • 공격자가 이 함수에 그 정도 길이를 넣을 경로가 알려져 있지 않다. 호출자가 약 2GB 버퍼를 직접 다뤄야 한다.
  • TLS·QUIC·CMS 같은 OpenSSL 내부 기능은 그렇게 큰 데이터를 인코딩하지 않는다. 즉, 웹 서버가 HTTPS 연결을 받는다고 해서 원격에서 건드릴 수 있는 버그가 아니다.
  • openssl s_client의 프록시 비밀번호 처리처럼 명령줄 도구 경로도 현실적으로 닿기 어렵다.

반면 제보자는 PR에서 환경 변수로 아주 긴 프록시 비밀번호를 넘기면 이론상 닿을 수 있다고 반박했습니다. 이 경우에도 공격자가 해당 명령의 실행 환경을 이미 조작할 수 있어야 하므로, 원격 공격과는 거리가 멉니다.

내 코드가 위험한 경우는 이렇게 좁혀집니다.

  • 직접 만든 C/C++ 프로그램(또는 OpenSSL을 바로 부르는 바인딩)이 외부에서 받은 큰 데이터를 길이 제한 없이 통째로 EVP_EncodeBlock()에 넘긴다.
  • 그 데이터 크기를 공격자가 정할 수 있다(예: 업로드 파일을 한 번에 Base64로 변환).

점수는 왜 이렇게 갈렸나

평가 주체점수·등급가정
GitHub 보안 권고(검토 전)9.8 치명적네트워크에서 인증 없이, 쉽게 공격 가능하다고 가정
CISA-ADP (현재 CVE 기록)5.9 보통네트워크 경로지만 공격 조건이 까다롭고(AC:H), 영향은 서비스 중단(가용성)만
Red Hat3.7 낮음공격 조건 까다로움, 가용성 영향도 제한적
OpenSSL (CNA)낮음(Low)알려진 공격자 제어 경로 없음

9.8은 “라이브러리 함수에 넘치는 길이를 넣으면 메모리가 깨진다 → 최악이면 원격 코드 실행"이라는 최악의 가정을 그대로 점수로 옮긴 결과에 가깝습니다. 반면 OpenSSL과 CISA의 현재 값은 “실제로 그 길이를 넣을 수 있는가” 를 따진 결과입니다. 처음 알려진 숫자가 9.8이라 제목과 알림에 그 숫자가 퍼졌고, 이후 기록이 고쳐졌지만 첫인상이 남은 경우입니다.

PR 토론에서도 OpenSSL 리뷰어 중 한 명은 재현 코드가 인위적이라며 “실제로 일어난다는 근거 없이는 CVE가 아닐 수도 있다"는 의견을 냈고, 반환값을 어떻게 바꿀지(-1, 0, 강제 중단)를 두고도 논의가 이어지고 있습니다.

한계·주의할 점

  • ‘낮음’이 ‘무시해도 됨’은 아닙니다. 큰 데이터를 다루는 자체 프로그램이라면 실제로 메모리가 깨질 수 있습니다. 수정 버전이 나오면 평소 업데이트 주기에 맞춰 올리세요.
  • 점수는 아직 확정되지 않았습니다. NVD 분석 전이고, CVE 기록도 며칠 사이 여러 번 바뀌었습니다. 이 글의 수치는 2026-11-21 확인 기준입니다.
  • 수정 방식이 아직 확정 전입니다. 수정 PR이 리뷰 중이라 최종 동작(오류 반환인지, 강제 중단인지)이 바뀔 수 있습니다. 반환값을 검사하지 않는 코드는 수정 후 동작을 다시 확인할 필요가 있습니다.

독자가 할 일

  1. 버전 확인: 서버에서 openssl version으로 쓰고 있는 OpenSSL 버전을 봅니다. 4.0.x·4.1.x가 아니면 업스트림 기준으로는 해당되지 않습니다. 다만 언어 런타임(Node.js, Python 등)이나 컨테이너 이미지에 별도로 묶인 OpenSSL이 있을 수 있으니 함께 확인하세요.
  2. 배포판 공지 확인: 배포판 패키지를 쓴다면 Ubuntu·Debian·Red Hat·SUSE 등 보안 추적 페이지에서 CVE-2026-121481을 검색해 내 패키지 상태를 봅니다.
  3. 직접 쓴 코드 점검: EVP_EncodeBlock()을 직접 호출하는 코드가 있다면, 입력 길이에 상한을 두고 반환값을 검사하는지 확인합니다. 큰 데이터는 스트리밍 방식(조금씩 나눠 인코딩)으로 처리하는 것이 안전합니다.
  4. 12월 1일 전후로 업데이트 계획: 4.0.4·4.1.1 출시 예정일에 맞춰 정기 패치에 포함합니다. 비상 패치 수준으로 서두를 근거는 현재로서는 약합니다.

정리

  • CVE-2026-121481은 OpenSSL 4.0.0~4.0.3, 4.1.0의 Base64 인코딩 함수에서 약 1.6GB 이상의 입력을 줄 때 생기는 정수 오버플로입니다.
  • 한때 9.8로 표시됐지만, OpenSSL은 ‘낮음’, 현재 CISA 점수는 5.9이고 실제 공격 보고는 없습니다. TLS 연결로 원격에서 건드릴 수 있는 버그가 아닙니다.
  • 수정 버전 4.0.4·4.1.1은 12월 1일 출시 예정입니다. 정기 업데이트에 넣고, 큰 데이터를 직접 인코딩하는 코드가 있다면 길이 제한부터 점검하세요.
  • 점수 하나만 보지 말고 누가, 어떤 가정으로 매겼는지 확인하는 습관이 불필요한 비상 대응과 놓치는 위험을 함께 줄여 줍니다.
