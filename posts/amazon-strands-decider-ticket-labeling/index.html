티켓 분류에 Sonnet 대신 '고르기만 하는 모델'을 썼더니 비용 98% 감소 — Amazon의 Strands Decider 전환기

Amazon이 내부 티켓을 20개 범주로 분류하던 Claude Sonnet 4.6을, 글을 쓰지 않고 정해진 선택지 중 하나만 고르는 '결정 모델'로 바꿔 티켓당 비용을 약 98%, 호출 시간을 약 78% 줄였습니다. 어떻게 바꿨는지, 어디까지 따라 할 수 있는지 정리합니다.

2026년 11월 9일, AWS의 Strands Agents 팀 블로그에 눈에 띄는 사례가 올라왔습니다. Amazon 사내 티켓 시스템에서 티켓마다 범주 라벨을 붙이던 Claude Sonnet 4.6을 ‘Strands Decider’라는 작은 결정 모델로 바꿨더니, 티켓 100만 건당 비용이 약 2만 2,200달러에서 약 500달러로 내려갔다는 내용입니다. 비율로는 약 98% 절감, 약 44배 차이예요.

Hacker News에서도 하루 만에 500점 넘게 받으며 화제가 됐습니다. “LLM을 다 쓰다가 결국 가벼운 분류기로 돌아오는 것 아니냐"는 반응부터 “라벨링 데이터 비용은 왜 빠졌냐"는 지적까지 다양했죠.

이 글은 LLM을 서비스·업무 자동화에 붙여 쓰고 있는 개발자, 그리고 “AI 비용은 왜 이렇게 많이 나오지?“가 궁금한 학생·직장인을 위한 정리입니다.

무슨 일이 있었나

  • 작업: Amazon·AWS 팀들이 쓰는 대형 사내 티켓 시스템에서, 들어오는 티켓(고객 에스컬레이션, 용량 요청, 자동 알람, 보안 발견 사항 등)에 정해진 20개 범주 중 하나를 붙이는 일입니다.
  • 원래 방식: 티켓마다 긴 시스템 프롬프트와 함께 Sonnet 4.6을 호출하고, JSON으로 답을 받았습니다.
  • 바꾼 방식: 티켓을 ‘상황’, 20개 범주를 ‘선택지’로 넘기면 각 선택지의 확률만 돌려주는 Strands Decider(Gemma 4 기반 E4B 빌드)로 교체했습니다.
  • 결과: 호출 시간 약 78% 감소, 티켓당 토큰 약 70% 감소, 비용 약 98% 감소. 원문은 연간 토큰 비용으로 수백만 달러를 아낀다고 밝혔습니다.

핵심 개념: ‘결정 모델’은 뭐가 다른가

  • LLM(대규모 언어 모델): 다음에 올 단어를 하나씩 이어 써서 답을 만드는 모델입니다. 무엇이든 쓸 수 있지만, 쓰는 만큼 시간과 돈이 듭니다.
  • 결정 모델(decision model): 글을 쓰지 않습니다. “상황 + 질문 + 선택지 목록"을 받아 선택지마다 확률과 신뢰도를 한 번에 돌려줍니다. 예·아니오, N개 중 하나 고르기, 점수 매기기 같은 질문만 받습니다.
  • 어떻게 만들었나: 10월 1일 공개된 Strands Decider 2B는 Qwen3.5-2B 모델에서 글자를 생성하는 마지막 층(언어 모델 헤드)을 떼어 내고, 선택지마다 점수를 매기는 작은 층(포인터 헤드, 약 100만 개 파라미터)을 붙인 구조입니다. 그래서 출력은 ‘선택 1개’뿐이에요.
  • 문맥 창(context window): 모델이 한 번에 읽을 수 있는 입력 길이입니다. Strands Decider는 4,096토큰(토큰 = 모델이 글을 쪼개는 단위, 대략 단어 조각)이라 긴 입력에 약합니다.
  • 신뢰도 임계값(threshold): “확률이 이 값 이상일 때만 라벨을 붙인다"는 기준선입니다. 낮으면 많이 붙이지만 틀릴 위험이 커지고, 높으면 정확하지만 ‘모르겠음’이 늘어납니다.

비유하자면 LLM은 서술형 답안을 쓰는 학생이고, 결정 모델은 객관식 OMR 카드에 마킹만 하는 학생입니다. 문제가 객관식이라면 굳이 서술형으로 풀 필요가 없다는 게 이번 사례의 요지입니다.

출력 토큰이 170개에서 1개로 줄어든 점이 눈에 띕니다. LLM은 출력 토큰 단가가 입력보다 5배 비싼데, 결정 모델은 아예 ‘선택 하나’만 내놓으니 그 비용이 사라졌습니다.

계산해 보면: Sonnet 쪽은 6,554 × $3/100만 + 170 × $15/100만 ≈ $0.0222입니다. 결정 모델 쪽은 GPU 서버를 시간 단위로 빌리는 방식이라, 요청 1건에 약 640ms가 걸리면 인스턴스 1대가 시간당 약 5,600건을 처리하고, 이를 시간당 요금으로 나눈 값이 건당 비용이 됩니다.

바꾸면서 손본 것

  1. 모델 고르기: 처음엔 2B 빌드를 시험했지만, 테스트 세트에서 더 나은 E4B(Gemma 4 기반) 빌드로 갈아탔습니다.
  2. 임계값 조정: 라벨을 붙이기 위한 최소 신뢰도를 조정한 뒤, 별도 티켓 묶음에서 운영 중인 Sonnet보다 나은 결과를 확인했다고 합니다.
  3. 라벨 설명 다이어트: 기존 라벨 설명이 4,096토큰 창을 넘었기 때문에, 20개 라벨을 각각 한두 문장짜리 판정 기준으로 다시 썼습니다. 여기에 ‘해당 없음’ 선택지를 하나 더했어요.
  4. 긴 티켓 자르기: 입력은 Sonnet이 받던 것과 같되, 긴 티켓은 가장 오래된 댓글부터 빼서 창에 맞췄습니다.
  5. 입력 순서 고정: JSON 키 순서만 바꿔도 출력 확률이 최대 0.19까지 흔들려서, 지금은 키를 정렬해서 보냅니다.

안전하게 갈아타는 ‘3단 스위치’

이번 사례에서 가장 실무적으로 배울 만한 부분입니다. Lambda가 메시지마다 AppConfig 값을 읽어 세 모드 중 하나로 동작합니다.

모드동작
BEDROCKSonnet만 호출해 라벨링 (결정 모델은 호출 안 함)
DUAL두 모델을 동시에 호출하되 Sonnet 결과만 적용하고, 결정 모델 결과는 비교용으로 기록
DECIDER결정 모델만 호출 (Bedrock은 호출 안 함)

DUAL 모드는 흔히 **섀도 모드(shadow mode)**라고 부르는 방식입니다. 새 시스템을 실제 트래픽에 붙이되 결과는 쓰지 않고 비교만 해서, 사용자에게 영향 없이 검증하는 거예요. 원문에 따르면 Sonnet으로 되돌리는 데는 설정 변경 45초면 충분했습니다.

한계와 주의할 점

  • 회사가 직접 낸 숫자입니다. 모두 Amazon 내부 작업 하나에서 나온 수치이고, 평가에 쓴 티켓 세트는 공개되지 않았습니다. “Sonnet보다 나았다"는 정확도 비교도 구체적인 수치는 원문에 없습니다.
  • 빠진 비용이 있습니다. Lambda 비용은 비교에서 제외됐고, 라벨 기준을 다시 쓰고 임계값을 맞추는 데 든 사람의 시간, 기준 데이터를 만드는 비용도 들어 있지 않습니다. HN에서도 이 점을 지적하는 댓글이 많았습니다.
  • 규모가 커야 의미가 있습니다. 100만 건당 약 2만 달러 차이이니, 연간 수백만 달러를 아끼려면 처리량이 매우 커야 합니다. 하루 수백 건 수준이라면 GPU 인스턴스를 상시 띄우는 비용이 오히려 더 들 수 있어요.
  • 맞지 않는 작업이 분명합니다. 원문 스스로 라벨에 설명문이 필요하거나, 범주 목록이 매주 바뀌거나, 판단에 필요한 문맥이 수천 토큰에 안 들어가는 경우엔 맞지 않을 수 있다고 적었습니다. Strands Decider 소개 자료도 코딩·챗봇·요약에는 부적합하고, 복잡한 문제에선 추론형 모델보다 많이 약하다고 밝힙니다.
  • 입력 형식에 민감합니다. 키 순서 하나로 확률이 0.19까지 흔들렸다는 건, 운영 중 입력 포맷이 조금만 바뀌어도 결과가 달라질 수 있다는 뜻입니다.
  • 꼭 결정 모델일 필요는 없습니다. “전통적인 텍스트 분류기(SVM, BERT 등)로도 충분하지 않냐"는 의견도 HN에서 나왔습니다. 결정 모델의 장점은 라벨 기준을 자연어 문장으로 바꿔 끼울 수 있다는 점이고, 이것이 재학습 비용과 비교해 이득인지는 상황마다 다릅니다.

우리 팀이라면 이렇게 확인해 보세요

단계확인할 질문
1. 작업 성격지금 LLM이 하는 일 중 정해진 목록에서 고르기(분류, 라우팅, 예·아니오 판정)인 것이 있나?
2. 출력 낭비그 작업에서 LLM이 JSON·이유 설명 등 실제로 쓰지 않는 글을 만들고 있지 않나?
3. 규모 계산하루 처리 건수 × 건당 비용으로 월 비용을 계산했을 때, 별도 모델을 띄울 만한 크기인가?
4. 기준 정리각 라벨을 한두 문장 판정 기준으로 쓸 수 있나? 못 쓴다면 사람도 헷갈리는 라벨일 수 있다
5. 정답 세트기존 결과와 비교할 라벨이 달린 티켓 묶음이 있나?
6. 섀도 검증기존 모델 결과만 쓰고 새 모델은 비교만 하는 DUAL 같은 단계를 둘 수 있나?
7. 되돌리기설정값 하나로 몇 분 안에 원래 모델로 돌아갈 수 있나?
8. 입력 고정키 정렬·필드 순서 등 입력 형식을 고정해 두었나?

1~3번에서 “예"가 많지 않다면, 굳이 바꾸지 않아도 됩니다. 더 싼 LLM(소형 모델)으로 바꾸거나, 애매한 건만 비싼 모델에 넘기는 계단식 구성이 더 간단한 선택일 수 있어요.

정리

  • Amazon은 사내 티켓 20개 범주 분류에서 Sonnet 4.6을 선택지 확률만 내놓는 결정 모델로 바꿔, 비용 약 98%·호출 시간 약 78%를 줄였습니다.
  • 핵심은 모델 자체보다 작업 재정의입니다. 긴 프롬프트·JSON 출력 → 짧은 판정 기준 + 선택 1개.
  • 안전장치로 **3단 스위치(기존/동시 비교/신규)**와 45초 롤백을 둔 점이 실무에서 그대로 참고할 만합니다.
  • 다만 회사 자체 수치이고, 라벨링·개발 비용은 빠져 있으며, 대량·고정 목록·짧은 문맥이라는 조건이 맞아야 효과가 납니다.
