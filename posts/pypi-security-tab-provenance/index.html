PyPI에 '보안' 탭이 생겼다 — pip install 전에 패키지 출처를 30초 만에 확인하는 법

PyPI 프로젝트 페이지에 파일별 출처(provenance) 정보를 모아 보여 주는 보안 탭과 경고 배너가 생겼습니다. 화면에서 무엇을 봐야 하는지, 경고가 뜨면 어떻게 판단할지, 내 패키지에 출처 정보를 붙이는 방법까지 정리합니다.

2026-11-16 · #pypi #python #supply-chain #attestation #trusted-publishing #sigstore #slsa

pip install 한 줄은 남이 만든 코드를 내 노트북과 서버에 그대로 들여오는 일입니다. 그런데 지금까지 PyPI 화면만 보고는 “이 파일이 정말 그 프로젝트의 깃허브 저장소에서, 그 빌드 과정을 거쳐 올라온 것인가"를 알기 어려웠습니다.

파이썬 패키지 저장소 PyPI가 2026년 11월 6일 프로젝트 페이지 개편을 마무리하면서 이 질문에 답하는 보안(Security) 탭과 출처 경고 배너를 붙였습니다. 이 글은 파이썬을 쓰는 학생·취준생부터, 사내 서비스에 오픈소스 패키지를 들이는 실무 개발자, 직접 패키지를 배포하는 메인테이너까지를 위한 정리입니다.

PyPI 공식 블로그(7월 개편 계획 글), PyPI 공식 문서(attestations), Help Net Security 보도, Python 공식 토론장(discuss.python.org) 스레드를 교차 확인해 썼습니다. (2026-11-16 확인 기준)

무슨 일이 있었나

  • 7월 22일: PyPI가 프로젝트 페이지를 몇 달에 걸쳐 단계적으로 바꾸겠다고 예고했습니다. 사이드바 메뉴를 가로 탭으로 옮기고, 데이터마다 “PyPI가 만든 정보인지, 메인테이너가 적은 정보인지"를 구분해 표시하는 내용이었습니다.
  • 11월 6일: 마지막 단계로 보안 탭과 출처 경고가 적용됐다고 PyPI 블로그가 밝혔습니다. 보안 매체 Help Net Security도 11월 9일 이를 보도했습니다.
  • 11월 7일~: 공식 토론장에서 “출처 정보가 없다는 표시가 너무 겁을 준다”, “특정 CI만 쓸 수 있어 불공평하다"는 문제 제기와 반론이 오가고 있습니다. (아래 ‘한계’ 절에서 다룹니다.)

메인테이너가 따로 할 일은 없습니다. 이미 올라간 출처 정보는 새 화면에 자동으로 표시됩니다.

먼저 용어 몇 가지

  • 공급망 공격(supply chain attack): 내 코드를 직접 노리지 않고, 내가 가져다 쓰는 라이브러리·빌드 도구를 오염시켜 들어오는 공격입니다.
  • 출처 증명(attestation): “이 파일은 누가, 어디서, 어떤 과정으로 만들었다"는 내용을 전자 서명으로 묶은 기록입니다. PyPI에서는 파일마다 붙습니다.
  • 출처(provenance): 파일이 만들어지기까지의 이력입니다. PyPI 화면에서는 출처 증명이 얼마나 붙어 있는지를 이 단어로 보여 줍니다.
  • 신뢰할 수 있는 게시자(Trusted Publishing): 비밀번호나 API 토큰 대신, 깃허브 액션 같은 CI가 발급하는 짧은 수명의 신원 토큰으로 PyPI에 업로드하는 방식입니다. 토큰이 유출될 걱정이 줄어듭니다.
  • 투명성 로그(transparency log): 서명 기록을 누구나 볼 수 있게 추가만 가능한 장부에 남기는 공개 기록소입니다. PyPI의 출처 증명은 Sigstore라는 오픈소스 서명 체계의 로그를 씁니다.
  • SLSA: 소프트웨어 빌드 과정의 신뢰도를 단계별로 정의한 업계 기준입니다(살사로 읽습니다).

새 화면에서 무엇이 바뀌었나

위치바뀐 점독자가 볼 것
보안 탭 (새로 생김)릴리스 파일마다 출처 증명이 있는지, 상세 내용과 투명성 로그 링크어느 저장소·어느 워크플로에서 올라왔는지
페이지 상단 배너출처 경고가 삭제(yank)·보관(archived)·사전 공개 표시와 함께 상단에 표시. 격리(quarantine)된 경우엔 격리 배너만 표시배너가 있으면 설치 전에 한 번 멈추기
오른쪽 사이드바모든 파일에 증명이 있거나 경고가 있을 때 상태 표시와 보안 탭 링크“전체 출처 있음” 여부
릴리스 파일 탭내려받을 파일 검색·필터, 파일별 출처 상태내 OS·파이썬 버전용 휠에 증명이 있는지
릴리스 이력 탭버전별 파일 수, 출처 상태, 릴리스 상태를 나란히 비교어느 버전부터 출처 정보가 바뀌었는지

출처 증명은 두 종류

종류담는 내용의미
PyPI Publish파일을 올린 신뢰할 수 있는 게시자(예: 특정 깃허브 저장소의 특정 워크플로)“누가 올렸나”
SLSA Build Provenance소스 커밋, 빌드 플랫폼, 빌드 지시 내용“무엇으로부터 어떻게 만들었나”

PyPI 문서에 따르면 파일 하나에 위 두 종류를 각각 하나씩, 최대 2개까지 붙일 수 있습니다.

경고는 언제 뜨나

Help Net Security 보도와 공식 토론장 내용을 종합하면, PyPI는 다음 상황에서 경고를 띄웁니다.

  1. 일부 파일만 증명이 있다 — 한 릴리스의 휠 중 몇 개만 서명됨
  2. 같은 릴리스 안에서 파일들의 저장소·빌드 시스템이 서로 다르다
  3. 이전 버전과 다른 저장소·워크플로에서 올라왔다
  4. 전에는 증명을 붙이던 프로젝트가 이번 릴리스부터 안 붙였다

반대로 처음부터 한 번도 증명을 붙인 적 없는 프로젝트는 경고가 아니라 중립 상태로 표시됩니다. 오래된 패키지 대부분이 여기에 해당합니다.

경고를 봤을 때 판단하는 법

경고가 곧 악성 코드라는 뜻은 아닙니다. 조직 이름이 바뀌었거나 저장소를 옮겼거나, 메인테이너가 특정 플랫폼용 휠만 손으로 빌드해 올렸을 수도 있습니다. 반대로 빌드 파이프라인 침해나 계정 탈취의 신호일 수도 있습니다. PyPI 측도 증명이 없다는 것은 “출처를 암호학적으로 확인할 수 없다"는 뜻일 뿐이라고 설명합니다.

그래서 경고를 보면 이렇게 확인해 보세요.

  • 프로젝트 깃허브 저장소의 릴리스 노트·이슈에 저장소 이전이나 배포 방식 변경 안내가 있는지
  • 릴리스 이력 탭에서 어느 버전부터 상태가 바뀌었는지, 평소 배포 주기와 다르게 갑자기 올라온 버전은 아닌지
  • 메인테이너 계정과 커밋 활동이 평소와 같은지
  • 확신이 안 서면 경고 전 버전에 고정해 두고 상황을 지켜보기

독자가 할 일

1. 패키지를 쓰는 사람

  • 새 의존성을 들일 때 PyPI 페이지의 보안 탭을 한 번 열어 보는 습관을 들입니다. 저장소 링크가 내가 알던 그 저장소인지가 핵심입니다.
  • 출처를 명령줄에서 직접 검증하고 싶다면 PyPI 공식 문서에 나온 pypi-attestations 도구를 쓸 수 있습니다. 문서 예시는 다음과 같습니다(휠 파일의 직접 다운로드 주소와 기대하는 저장소를 넣습니다).
python -m pip install pypi-attestations

pypi-attestations verify pypi \
  --repository https://github.com/pypa/sampleproject \
  https://files.pythonhosted.org/packages/d7/73/c16e5f3f0d37c60947e70865c255a58dc408780a6474de0523afd0ec553a/sampleproject-4.0.0-py3-none-any.whl

문서 설명에 따르면 이 명령은 휠과 출처 정보를 내려받아, 서명한 게시자가 --repository로 준 저장소와 일치하는지 확인하고 파일을 암호학적으로 검증합니다. (이 글을 쓰며 직접 실행해 보지는 않았고, 공식 문서 예시를 그대로 옮겼습니다.)

  • pip·uv 같은 설치 도구가 출처 증명을 필수로 요구하지는 않을 것이라는 게 토론장에서 나온 PyPI 쪽 기여자의 설명입니다. 즉, 확인은 아직 사람 몫입니다.

2. 패키지를 배포하는 사람

  • 깃허브 액션에서 공식 액션 pypa/gh-action-pypi-publish와 신뢰할 수 있는 게시자로 배포하고 있다면, 공식 문서 기준 출처 증명이 기본으로 자동 생성·업로드됩니다. 이미 이렇게 배포 중이라면 따로 할 일이 없습니다.
  • GitLab CI/CD·Google Cloud는 자동이 아닙니다. 공식 문서는 pypi-attestations sign으로 서명한 뒤 twine upload --attestations dist/*로 올리는 단계를 추가하라고 안내합니다. 이때 서명 신원은 신뢰할 수 있는 게시자여야 하고, 그 외 신원은 업로드 때 거부됩니다.
  • 신뢰할 수 있는 게시자 중 ActiveState는 아직 출처 증명을 만들지 않는다고 문서에 적혀 있습니다.
  • 가장 흔한 경고 원인은 “일부 플랫폼 휠만 손으로 빌드해 올리기"입니다. 가능하면 모든 배포 파일을 같은 CI 워크플로에서 빌드·업로드하세요.

한계와 반론

  • 쓸 수 있는 CI가 정해져 있다: 지금 출처 증명은 신뢰할 수 있는 게시자 위에서만 만들 수 있고, 공식 문서 기준 서명 가능한 곳은 깃허브 액션·GitLab CI/CD·Google Cloud입니다. Codeberg 같은 다른 코드 호스팅을 쓰는 프로젝트는 ‘전체 출처 있음’ 표시를 받을 길이 없어 “상용 CI 쪽으로 몰아간다"는 비판이 토론장에서 나왔습니다. 이메일 기반 증명을 검토 중이라는 언급이 있었지만, 확정된 계획은 확인하지 못했습니다.
  • ‘출처 없음’ 표시의 인상: PyPI는 회색·파란색 같은 중립 색을 쓰고 한 번도 증명을 안 붙인 프로젝트는 경고하지 않는다고 하지만, 일부 아이콘이 부정적으로 읽힌다는 의견도 있습니다. 표시 문구는 앞으로 바뀔 수 있습니다.
  • 출처가 곧 안전은 아니다: 출처 증명은 “이 저장소의 이 워크플로가 만들었다"를 보장할 뿐, 그 저장소의 코드가 안전하다는 뜻은 아닙니다. 메인테이너 저장소 자체가 털리면 서명도 정상으로 붙습니다. 또 깃허브 같은 CI 제공자 자체를 얼마나 믿을 수 있느냐는 질문도 남아 있습니다.
  • 오래된 릴리스는 대부분 ‘출처 없음’: 기능이 생기기 전에 올라온 파일에는 증명이 없습니다. 출처 없음만으로 오래된 버전을 의심할 필요는 없습니다.

정리

  • PyPI 프로젝트 페이지에 보안 탭이 생겨, 파일마다 누가 어디서 만들어 올렸는지를 한곳에서 볼 수 있습니다.
  • 경고는 일부 파일만 서명됨, 파일끼리 출처가 다름, 이전 버전과 출처가 다름, 서명을 하다가 멈춤의 네 경우에 뜹니다. 경고는 ‘악성 확정’이 아니라 ‘확인해 보라’는 신호입니다.
  • 쓰는 사람은 새 의존성의 보안 탭을 한 번 보고, 배포하는 사람은 모든 파일을 한 CI 워크플로에서 신뢰할 수 있는 게시자로 올리는 것이 가장 간단한 대응입니다.
