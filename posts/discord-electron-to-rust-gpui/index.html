Discord가 Electron을 버리고 Rust로 간다: 1GB 넘던 데스크톱 앱이 290MB가 된 이유

Discord가 데스크톱 앱을 Electron에서 Rust·GPUI 기반 네이티브 앱으로 다시 만들고 있습니다. 초기 빌드의 메모리 사용량은 290MB였어요. 웹 기술로 만든 데스크톱 앱이 왜 무거운지, 앱 프레임워크를 고를 때 무엇을 따져야 하는지 정리합니다.

2026년 11월 4일, Discord 공동 창업자이자 CTO인 스타니슬라프 비시네프스키(Stanislav Vishnevskiy)가 X에 데스크톱 앱을 Rust로 다시 만들고 있다고 밝혔습니다. 함께 올린 윈도우 작업 관리자 화면에는 “Discord Phoenix"라는 이름의 초기 빌드가 약 290MB의 메모리를 쓰고 있었어요. 지금의 Discord 윈도우 앱은 서버 몇 개만 들어가도 1GB를 쉽게 넘긴다는 보도(The Verge)가 있으니, 체감 차이가 클 수 있습니다.

다음 날 The Verge 등이 보도하면서 해커뉴스와 긱뉴스에서도 크게 화제가 됐습니다. “메신저 하나가 왜 1GB를 먹지?“라는 의문은 Slack, Teams, VS Code를 쓰는 사람이라면 한 번쯤 해 봤을 거예요. 이 소식을 계기로 웹 기술 기반 데스크톱 앱이 왜 무거운지, 그리고 앱 프레임워크를 고를 때 무엇을 따져야 하는지 정리해 봅니다.

여러 보도를 교차 확인한 내용만 추리면 이렇습니다.

정리하면 “방향은 확정, 일정은 미정” 입니다. 아직 누구나 써 볼 수 있는 상태는 아니에요.

먼저 용어 몇 가지

  • Electron: 웹 페이지(HTML·CSS·자바스크립트)를 데스크톱 앱처럼 실행해 주는 프레임워크. 앱마다 크로미움 브라우저 엔진과 Node.js를 통째로 싣고 다닙니다. Slack, VS Code, 지금의 Discord가 이 방식이에요.
  • 크로미움(Chromium): 구글 크롬의 바탕이 되는 오픈소스 브라우저 엔진. 탭·확장마다 프로세스를 나눠 안정성을 얻는 대신 메모리를 많이 씁니다.
  • React Native: 자바스크립트(React)로 iOS·안드로이드 앱을 함께 만드는 프레임워크. 화면은 각 OS의 네이티브 부품으로 그립니다.
  • Tauri: Rust로 만든 데스크톱 앱 프레임워크. 크로미움을 싣지 않고 OS에 이미 깔린 웹뷰(윈도우 WebView2, macOS WKWebView 등)를 빌려 씁니다. 그래서 앱 용량이 작지만, 화면은 여전히 웹 기술로 그려요.
  • GPUI: 코드 에디터 Zed를 만든 팀이 개발한 Rust UI 프레임워크. 브라우저 엔진 없이 GPU로 화면을 직접 그립니다.
  • RSS(상주 메모리): 프로그램이 지금 실제 메모리(RAM)에 올려 두고 쓰는 양. 작업 관리자의 “메모리” 숫자가 대략 이것입니다.

왜 Electron 앱은 무거울까

Electron 앱은 실행하면 프로세스가 여러 개 뜹니다. 앱 전체를 관리하는 메인 프로세스, 화면을 그리는 렌더러 프로세스, 그 밖에 GPU·네트워크를 맡는 보조 프로세스들이에요. 각각이 크로미움의 일부를 들고 있으니, 앱이 아무 일을 하지 않아도 기본으로 깔고 가는 메모리(바닥값) 가 생깁니다.

여기에 채팅 앱 특유의 부담이 더해집니다. 서버·채널이 늘수록 메시지 목록, 이미지, 이모지, 미리보기가 자바스크립트 객체와 DOM(웹 페이지의 화면 구조)으로 쌓이고, 가비지 컬렉터(안 쓰는 메모리를 자동으로 치우는 장치)가 회수하기 전까지 메모리를 차지해요. 그래서 오래 켜 둘수록, 들어간 서버가 많을수록 사용량이 불어나기 쉽습니다.

Rust 네이티브 앱은 이 구조가 다릅니다.

비교ElectronTauriRust + GPUI (Discord 새 앱)
화면을 그리는 방식내장 크로미움OS 웹뷰GPU로 직접 그림
앱 로직 언어자바스크립트/타입스크립트Rust + 웹 프론트엔드Rust
메모리 바닥값큼 (브라우저 엔진 포함)중간 (웹뷰는 OS가 제공)작음
웹 개발 인력 재사용매우 쉬움쉬움어려움 (UI를 새로 짜야 함)
OS별 화면 차이거의 없음웹뷰 차이로 생길 수 있음프레임워크가 책임짐
생태계 성숙도매우 높음높아지는 중아직 젊음

메모리를 줄이는 핵심은 “Rust라서 빠르다"보다 브라우저 엔진이라는 바닥값을 아예 없앴다는 데 있습니다. 같은 Rust라도 Tauri를 택했다면 웹뷰 비용은 남았을 거예요. Discord가 굳이 “Tauri가 아니라 GPUI"라고 짚은 이유도 여기에 있습니다.

290MB, 그대로 믿어도 될까

기대할 만한 소식이지만, 숫자를 읽을 때 주의할 점이 있습니다.

  • 스크린샷 한 장입니다. 서버를 몇 개 열었는지, 음성 채널·화면 공유를 켰는지 같은 조건이 공개되지 않았어요. 공식 벤치마크가 아닙니다.
  • 기능이 다 들어간 빌드인지 모릅니다. 초기 빌드는 기능이 적을수록 가볍기 마련이에요. 기능이 붙으면서 숫자는 올라갈 수 있습니다.
  • 리눅스 지원과 모드(mod) 생태계가 걱정거리입니다. 긱뉴스 토론에서는 재작성 과정에서 리눅스 지원이 밀리지 않을지, 웹 기술에 기대던 Vencord 같은 비공식 테마·플러그인이 계속 동작할지 우려하는 의견이 나왔어요.
  • GPUI는 아직 젊은 프레임워크입니다. 안정성·접근성(스크린 리더, 키보드 탐색 등)·입력기(IME) 지원 수준은 실제 출시 빌드로 확인해야 합니다. 한국어 입력이 매끄러운지는 국내 사용자에게 특히 중요한 확인 포인트예요.
  • 재작성은 위험한 결정입니다. 큰 앱을 처음부터 다시 만드는 일은 버그와 기능 누락을 부르기 쉽습니다. 레딧 등에서는 AI가 생성한 코드가 많이 들어가지 않을지 걱정하는 반응도 있었어요.

반대로 “Electron 자체가 느린 게 아니라 앱을 무겁게 만든 것"이라는 반론도 있습니다. VS Code처럼 Electron으로도 잘 최적화된 앱이 있으니, 프레임워크만 바꾼다고 모든 문제가 풀리는 건 아니라는 지적이에요.

독자가 해 볼 것

사용자라면

  • 지금 쓰는 데스크톱 앱이 메모리를 얼마나 쓰는지 윈도우 작업 관리자나 macOS 활성 상태 보기에서 확인해 보세요. Electron 앱은 같은 이름의 프로세스가 여러 개로 나뉘어 보이니 전부 더해야 실제 사용량이 나옵니다.
  • 새 Discord 앱이 테스트에 들어가면, 같은 서버 구성에서 기존 앱과 나란히 비교해 보는 게 가장 정확합니다.

개발자라면 (특히 사이드 프로젝트로 데스크톱 앱을 고민하는 취준생·대학생)

  • 프레임워크는 “가장 빠른 것"이 아니라 팀이 가진 기술과 제품의 요구로 고르세요. 웹 개발자 위주의 작은 팀이면 Electron이나 Tauri가 출시까지 훨씬 빠릅니다.
  • 메모리가 제품 경쟁력인 앱(항상 켜 두는 메신저, 저사양 PC 사용자가 많은 서비스)이라면, 처음부터 메모리 바닥값을 설계 기준에 넣어 두세요.
  • 재작성을 고민하기 전에 측정부터 하세요. 메모리를 실제로 잡아먹는 곳이 프레임워크 바닥값인지, 앱이 쌓아 둔 데이터인지에 따라 해법이 완전히 달라집니다. Electron 앱이라면 크로미움 개발자 도구의 Memory 패널로 힙 스냅샷을 떠 볼 수 있어요.

정리

  • Discord가 데스크톱 앱을 Electron에서 Rust + GPUI 네이티브 앱으로, 모바일은 React Native에서 Rust 공유 로직으로 옮기고 있습니다.
  • 초기 윈도우 빌드는 약 290MB를 썼지만, 조건이 공개되지 않은 스크린샷 한 장이라 출시 빌드로 다시 확인해야 합니다.
  • 핵심은 언어보다 브라우저 엔진이라는 메모리 바닥값을 없앤 구조 변화입니다. 대신 개발 속도·생태계·리눅스 지원이라는 대가를 치를 수 있어요.
  • 우리 프로젝트에서는 재작성보다 측정이 먼저입니다.
